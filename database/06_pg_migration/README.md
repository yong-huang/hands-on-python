# 06 · PostgreSQL 上手与 SQLite 迁移:第一次进工业级数据库

> 把实验 02 的三表数据整体搬进容器里的 PostgreSQL:逐表行数对账、关联查询
> 抽查,再实测三种 SQLite 没有的类型——JSONB、数组、NUMERIC 的精度承诺。
> 读完本篇,你能用一条命令管理一个数据库容器,知道跨库迁移要对哪些账、
> IDENTITY 与参数化搬运怎么写,10 项断言跑成全绿。

## Background

前五个实验都在 SQLite 里:它把整个数据库装进一个文件,随开随用,但一个人
守着一个文件的世界没有并发可言——两个进程同时写要排队,远程机器想连进来
没有门,数据量过 GB 后文件锁的粒度也开始吃亏。

生产系统的数据库要服务几十上百个同时读写的连接:有人改库存、有人查订单、
有人跑报表,互不阻塞;还要按用户管权限、按天做备份、崩了能恢复。这些能力
SQLite 一概没有,PostgreSQL(开源的服务型关系数据库,常称 PG)是工程界
最常用的默认答案——它作为独立进程常驻,客户端通过网络协议连进来。

容器是把"装数据库"变成一条命令的工具:Docker 从官方镜像(打包好 PG 的
现成只读模板)拉起一个隔离的 PG 进程,用完即弃,不污染本机。本实验起一个
PG 16 容器,把 SQLite 的家底搬进去,顺路验收三种 PG 才有的类型。

## What

**定义**:psycopg 3 是 PG 的官方 Python 驱动——把 SQL 与参数通过 TCP
协议发给独立的数据库服务进程,再用 Python 对象接回结果。与 SQLite 驱动
最大的差别:连接跨越网络,事务(要么全生效、要么全不算的操作组)与类型
的责任边界都更严格——没提交的一批写入,连接中断即整体作废。

PG 连接串(host/port/dbname/user/password)替代了"一个文件路径";端口
映射 55432:5432 表示宿机 55432 转到容器内 5432。建表主键改用 IDENTITY
(GENERATED BY DEFAULT AS IDENTITY:不给 id 就自动编号,给了就用你的)。

| 差异点 | SQLite | PostgreSQL |
|:--|:--|:--|
| 服务形态 | 进程内嵌,一个文件 | 独立服务进程,TCP 接入 |
| 连接方式 | `connect(路径)` | host/port/user/password 五元组 |
| JSON | TEXT 里塞字符串 | JSONB 专有类型 + GIN 索引(加速包含查询) |
| 数组 | 没有数组列 | `text[]` 原生数组 |
| 小数 | REAL(二进制浮点) | NUMERIC(十进制精确) |

迁移路径:SQLite 取数 → psycopg 参数化搬运 → PG 落表对账,容器边界内
即抛即弃。

## When to Use

**典型场景**。多用户业务系统:Web 服务与脚本同时读写一张表。数据要长期
演进:迁移工具、备份恢复、主从复制(把一台库的数据实时同步到另一台库)都建立在
服务型库上。需要强类型约束:
金额用 NUMERIC、标签用数组、半结构化用 JSONB,建表时就锁死。

**何时不用**。单机工具、移动应用内嵌、测试内存库仍是 SQLite 的地盘——
为一个配置文件起容器是杀鸡用牛刀。本系列从本实验起默认 PG,SQLite 退居
对比与教学。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| SQLite | 零部署,单写者 | 单机工具、原型、测试 |
| PostgreSQL(容器) | 一条命令起停,版本可控 | 本机开发与实验的标准形态 |
| PostgreSQL(独立部署) | 运维自理,性能更强 | 生产环境 |

## Quick Start

前置条件:Docker(OrbStack)在跑、镜像 postgres:16-alpine 已就位、系列
venv 装好 psycopg(命令见清单环境配置)。一条命令跑完整生命周期:

```bash
cd database/06_pg_migration && ./pg_migration.sh all
```

真实输出(节选,完整 10 项断言以实跑为准):

```text

    students: SQLite 4 行 -> PG 4 行

    ...

  [PASS] 迁移后内容抽查: 张教授 3 条选课

    ...
```

用 `docker exec -it lab06-pg psql -U postgres -d lab` 进交互终端自己逛。

## How It Works

### 迁移对账:数行数,也抽查内容

行数对账逐表 COUNT(*) 比对(SQLite 4/4/6 行,PG 必须相同);但行数相同
不等于内容正确——id 错位、字段串行的迁移行数也对得上。所以第二条腿是
内容抽查:在 PG 上重跑实验 02 的关联查询,"数学分析=张教授、3 条选课"
原样复现,才算真的搬对了。

### 三种类型的精度承诺

NUMERIC(10,2) 按十进制存数字,写入 Decimal("329.99") 读回还是 329.99,
不吃二进制浮点的暗亏(实验 01 坑 2 的根治);JSONB 把 JSON 解析成二进制
结构存档,GIN 索引(倒排式)让 `@>` 走索引;`text[]` 原生数组,
写入 list 读回 list。

### 容器生命周期:三个实际撞过的坑

`docker run --rm` 拉起即声明"用完即弃",stop 时数据随之蒸发;同名残留
容器会撞 run 冲突,启动前 `docker rm -f` 兜底可重入。

容器首启要 initdb(初始化数据目录),期间会先起一个用于初始化的临时实例,
它会骗过 pg_isready(PG 自带的就绪探测命令)——脚本的等待窗口与 Python
侧连接重试就是为它准备的。

## Pitfalls & Q&A

**坑 1:占位符(在 SQL 模板里给值留的空位)风格换了**。SQLite 用 `?`,
psycopg 3 用 `%s`;参数要走参数化通道——SQL 模板里只放 %s,值由驱动单独
递给数据库。拼接字符串也能跑通,但值不转义、不查类型,是 SQL 注入的入口:
参数化是纪律,不是语法限制。

**坑 2:psql(PG 自带的命令行客户端)非交互输出在 stderr**。`psql -c '\dt'`
(\dt 是列出表清单的元命令)的空库提示
"Did not find any relations." 不在 stdout,脚本捕获时要把 stderr 一起
收;交互终端里看不出差别,一进管道就现形。

**坑 3:IDENTITY 的两副面孔**。`GENERATED ALWAYS` 强制自动编号,插入老
数据会被拒;迁移要 `GENERATED BY DEFAULT`,显式 id 与自动编号都收。

**Q1:端口为什么要映射?** 容器是隔离网络,5432 只在容器内可见;宿主机
55432 映射进去才连得上。用高位端口是为了避开本机可能常驻的 5432。

**Q2:数据在容器里,停了不就没了吗?** 对,`--rm` 就是故意的——实验库
即抛即弃,重跑永远干净。生产数据要用数据卷(volume)挂出来,容器生死
不影响数据,实验 14 备份时会用到。

**Q3:为什么用 psycopg 3 而不是 psycopg2?** psycopg 3 是当代官方推荐:
原生支持 PG 的新协议、服务端参数绑定(参数在数据库一侧才拼进查询)与
异步;psycopg2 是历史包袱,新项目没有理由再选它。
