# 14 · 备份与时间点恢复:误删之后,把库开回昨天的门口

> pg_dump 逻辑备份重建后行数对账一致;pg_basebackup 打物理基础备份,
> 写入 500 行 treasure 后模拟误删 TRUNCATE(清空整张表的 SQL),再用基准 + WAL 归档重放到
> 误删前一秒——500 行 100% 找回、误删后的 50 行新写入被回退。8 项断言全绿。

## Background

没有备份体系的数据库生产事故只有两种结局:有备份,恢复;没备份,写检讨。
但"有备份"也分档次:每天凌晨的 pg_dump 只能回到"昨天晚上",白天写进的
数据照样丢;真正的救命稻草是 PITR(时间点恢复):物理基础备份加上持续
归档的 WAL,可以恢复到任意一秒——误删前一秒。

两套工具分工不同:pg_dump 是逻辑备份(把表结构数据导成 SQL 文本,跨版本
可读,恢复即重放 SQL);pg_basebackup 是物理备份(把数据目录原样拷成
一致性快照,配合 WAL 归档才能追上任意时间点)。本实验两者都做:前者对账,
后者上演"误删找回"全剧。

## What

**定义**:WAL 归档指主库把写满的 WAL 段用 archive_command 拷到安全
位置(本实验挂到宿主机 /bk/archive);PITR 三件套=基础备份 + 归档 WAL
+ 恢复目标(recovery_target_time),恢复容器按目标时刻重放 WAL 后
promote(结束恢复态,转为可写)。

可以把 PITR 想成游戏存档:基础备份是"存档点",归档 WAL 是之后的操作
回放记录,读档=载入存档点再按记录重放,停在误删操作之前的那一格。但和
游戏存档不同的是,回放有严格时序——恢复目标时刻必须晚于基础备份、早于
误删,时钟是用宿主机的表对齐的。

| 工具 | 备份内容 | 恢复能力 | 本实验实测 |
|:--|:--|:--|:--|
| pg_dump | SQL 文本(逻辑) | 回到备份时刻 | 100/1000 行对账一致 |
| pg_basebackup | 数据目录(物理) | 配 WAL 可到任意时刻 | 误删 500 行全找回 |
| WAL 归档 | 每个写满的段 | 追平任意时间点 | 已攒 5 个 WAL 段 |

## When to Use

**典型场景**。例行防线:每日 pg_basebackup + 持续 WAL 归档,PITR 兜底
任何"误删/误更新/损坏";变更前保险:大版本升级或危险 DDL(改表结构的操作,如 ALTER TABLE)前
先打一个
基础备份;审计需要:逻辑备份的 SQL 文本人可读、可比对。

**何时不用**。数据量太小(几百行)直接 pg_dump 秒级全量,不必上物理备份;
能靠从库延迟副本(另一台库持续同步主库、故意延迟几分钟才应用)解的
场景(实验 15)不必每次全量恢复。

| 手段 | 粒度 | 恢复时长 | 什么时候选它 |
|:--|:--|:--|:--|
| pg_dump | 库/表级 | 随数据量线性 | 小库、跨版本迁移 |
| basebackup+归档 | 集群级 + 任意时刻 | 重放时长决定 | 生产主力防线 |
| 只靠从库延迟 | 准实时 | 切换分钟级 | 误删刚发生时 |

## Quick Start

前置条件:Docker(OrbStack)在跑、镜像 postgres:16-alpine 就位、venv 装好
psycopg。一条命令跑完整生命周期(含主库一次启停与恢复容器启动,约 60 秒):

```bash
cd database/14_backup_pitr && ./backup_pitr.sh all
```

诚实预期:误删前的目标时刻取宿主机时钟减 1 秒,时钟偏差过大时恢复点

55441,主库容器此刻已下线——这正是"恢复期间业务不可写"的实景。

## How It Works

### 三段式时间线:备份、事故、重放

基础备份那一刻之前的历史已凝固在 /bk/base;之后的一切改动以 WAL 段
持续归档。误删发生时,破坏也进了 WAL——但归档里的每条记录都带时间。

恢复容器从基础备份起步,重放 WAL 直到 recovery_target_time 便停,
promote 成可写库。50 行误删后的新写入被回退,正因为重放在它们之前就
停了:它们只存在于"未来"。

### 恢复容器:为什么不救主库、另起炉灶

主库的数据目录已被误删后的状态覆盖,原地恢复要停库换文件,而 docker
exec 无法操作已停止的容器。

更稳的做法是另起恢复容器:把基础备份还原进它自己的数据目录,写上
recovery.signal(宣告进入恢复模式)与 restore_command(从归档拉 WAL),
再由官方入口脚本启动 postgres。恢复完成 promote,主库旧容器弃用。

### 归档的节奏:写满才走,抢救要等

archive_command 在 WAL 段写满(16MB)或 archive_timeout 到点时才拷贝。
实验设 archive_timeout=2s 并手动 pg_switch_wal() 强制切段。

这样误删前 treasure 的改动已落进归档;否则重放停在旧段,找回的是半截。

## Pitfalls & Q&A

**坑 1:目标时刻取"误删前",不是"误删后"**。脚本在 TRUNCATE 之前记录
时钟,恢复目标 = 该时刻减 1 秒;取错一边,找回的就是"被删空之后"的库。

**坑 2:恢复配置写进 postgresql.auto.conf 要防 shell 吞字符**。用
heredoc 原样落盘(shell 不解释 %,脚本里的 <<CFG 即可),printf 的
%f/%p 会被当格式符吃掉,
PG 直接报配置文件语法错误起不来。

**坑 3:docker exec 不能操作已停止的容器**。文件手术必须在容器自己的
入口脚本里完成(先 rm/cp 再 exec docker-entrypoint.sh),或用 docker cp
送到未启动的容器。

**Q1:逻辑备份和物理备份留哪个?** 都留。逻辑备份跨版本、可读、可单表
抽取;物理备份是 PITR 的地基。生产惯例:每日物理全备 + 持续归档,
每周外加一次逻辑备份做可读性保险。

**Q2:恢复期间业务停多久?** 重放时长取决于要追多少 WAL。本实验追 5 个
段秒级完成;真实事故可能重放几十 GB——所以 RTO(恢复时长目标)要靠
频繁的 basebackup 缩短重放起点距。

**Q3:promote 之后还能再恢复吗?** 不能在同一数据目录上回退——promote
后产生新的时间线,旧的恢复现场已被消费。要再演一次,从头再取一次
基础备份(本实验 clean 后重跑即全重来)。
