# 05 · 事务与 SAVEPOINT:kill -9 也撕不碎的"要么全做"

> 用一笔两步转账把事务的四件套跑成断言:ROLLBACK 全部作废、COMMIT 落盘
> 守恒、SAVEPOINT 回到存档点重写、子进程未提交时 kill -9 后分文未动,
> 再实测"未提交不可见"与 python 隐式事务陷阱。13 项断言跑成全绿。

## Background

没有事务的年代,多步写操作只能顺序执行:转账程序先给 A 扣款、再给 B 加钱,
若第二步执行前程序崩溃或断电,A 的钱已经扣了、B 没收到——账目从此不平,
只能靠人工对账找出这半截操作,再把账目手工补平。

这类"改到一半"的状态是数据系统的灾难:库存扣了订单没建、级联更新改了一半
表和另一半对不上。数据库引擎为此内置了事务(transaction,把多条语句打包成
一个整体的执行单位),SQLite 也一样:任何一组语句都能声明为"要么全生效、
要么当没发生过",且一旦提交,断电也不丢。

本实验用两步转账把这套承诺逐条压测:显式回滚、存档点部分回滚、真杀进程
验证崩溃恢复,最后实测未提交数据的可见性与 python 驱动的隐式事务行为。

## What

**定义**:事务由 BEGIN 开启、COMMIT 提交或 ROLLBACK 撤销,保证原子性
(组内语句全做或全不做)与持久性(提交后断电也已生效);SAVEPOINT 在
事务内部设存档点,`ROLLBACK TO 存档点` 只撤其后的语句,之前的保留。
实验还实测到默认隔离行为:未提交的改动对另一连接不可见。

可以把事务想成草稿箱:改动先落在草稿里,自己看得见,COMMIT 才正式发表,
ROLLBACK 则整箱作废。但和草稿箱不同的是,草稿对别人完全隐身——另一连接
在提交前读到的永远是旧数据,这是下一根柱子"隔离性"的入门体验。

| 关键词 | 作用 | 本实验的断言 |
|:--|:--|:--|
| BEGIN | 开启事务 | 两步改动事务内自己可见 |
| ROLLBACK | 整体撤销 | 转账原地蒸发,余额分文不动 |
| COMMIT | 提交落盘 | (900, 1100) 总额守恒 |
| SAVEPOINT / ROLLBACK TO | 设存档点并回到该处 | 手滑的 +1000 被吞,外层照常提交 |
| kill -9 | 不给清理机会的崩溃 | 重开库总额守恒,未提交改动消失 |

崩溃路径的完整时序:改动落库前旧值先进日志,进程死亡后重开库,引擎发现
残留日志即回放撤销——这就是"要么全做"的物质基础。

## When to Use

**典型场景**。资金与库存:转账、扣库存加订单,两步必须同生共死。多表联动:
主表和明细表、流水表的批量写入。凡是"改到一半不可接受"的写路径都该包事务。

**何时不用**。单条 UPDATE 天然原子,无需显式包裹;大批量导入宜分批提交,
一个横几分钟的长事务会持着写锁堵住其他连接。

| 写法 | 行为 | 什么时候选它 |
|:--|:--|:--|
| 显式 BEGIN/COMMIT | 边界完全自控 | 多步业务写,本实验主线 |
| pysqlite 隐式事务 | DML 自动开事务 | 默认行为,需知道它的存在 |
| isolation_level=None | 全自动提交 | 单语句工具脚本 |

## How It Works

### 崩溃原子性靠回滚日志:先记旧值,再改新值

引擎改动任何一页之前,把该页旧内容写进旁置的 `-journal` 文件,提交时刻
删除它。进程在提交前死亡,库文件里是"改了一半"的状态,但日志完好——
下一次打开数据库时,引擎发现残留日志,把旧值回放回去,仿佛什么都没发生。
实验里两步转账的死进程留下的正是这样一份日志,重开后 (1000, 1000)。

### SAVEPOINT 是事务内的栈

`SAVEPOINT 名字` 压入存档点,`ROLLBACK TO 名字` 把该点之后的改动撤掉
但事务仍开着,可继续写、最终一次 COMMIT 落盘;`RELEASE 名字` 则弹出
存档点并保留其后改动。实验的手滑演示:扣款后存档,加错 1000 回滚到存档点,
改成正确的 100,外层 COMMIT 一次生效。

### pysqlite 的隐式事务:看不见的 BEGIN

默认 isolation_level="" 下,驱动(pysqlite,即 sqlite3 模块)在
第一条写语句前自动 BEGIN,所以
in_transaction 已是 True,再手写 BEGIN 会撞上
"cannot start a transaction within a transaction"(实验实测)。

要完全自控就 isolation_level=None(全自动提交);留在默认档就要记得
commit(),否则连接关闭时草稿整箱作废。

## Pitfalls & Q&A

**坑 1:忘 commit,连接一关全蒸发**。隐式事务没提交,关闭连接等于 ROLLBACK。
自查习惯:写完看一眼 `conn.in_transaction`,为 True 就说明还有草稿没发表。

**坑 2:ROLLBACK TO 之后事务还开着**。回到存档点不是结束,忘掉最后的
COMMIT,前面正确的那部分也不会生效;只保留存档点前改动用 RELEASE。

**坑 3:长事务堵库**。事务持写锁期间,其他连接的写操作报
`database is locked`;事务应短平快,批量任务分批提交。

**Q1:kill -9 和真断电有区别吗?** 对 SQLite 恢复路径而言没有:两者都让
进程没机会删 `-journal`,下次打开都会回放日志;真断电还考验 fsync(强制
把改动真正刷到磁盘的系统调用)的时序,那是实验 13 的主题。

**Q2:为什么另一连接读不到未提交数据?** 隔离性的默认表现:读操作只认
已提交版本。SQLite 的隔离级别固定在最严格的一档,不存在读未提交之类
较松的档位。

**Q3:一条语句违反约束,会连坐整个事务吗?** 默认不会。ABORT 策略只回滚
当前语句,事务里它之前的语句仍然有效——语句级原子与事务级原子是两层,
实验 01 的 Q2 已埋过伏笔。
