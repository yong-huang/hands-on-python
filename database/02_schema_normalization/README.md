# 02 · 表设计与三范式:同一份数据的三种设计与三类异常

> 把同一份"学生选课"数据交给三种表设计:单表塞全部、只修原子的平铺表、
> 3NF 三表加外键(跨表引用的约束,What 节展开)。读完本篇,你能说清更新、
> 插入、删除三类异常为什么同源,判断设计违反哪级范式(normalization
> form,表结构好坏的分级标准),并把删除行为交给数据库引擎,12 项断言全绿。

## Background

没有范式标准的年代,程序按"一个系统一张大表"来存数据:字段想到什么加什么,
选课登记表里每行同时写着学生姓名、课名、授课教师——思路接近纸质台账,
一行就是一条完整记录。

这类设计在数据被第二次登记时撞墙。课程信息在每条选课行里重复出现,教务处
把"高等数学"改名"数学分析",登记员要逐行核对修改,漏掉一行,同一门课
在系统里从此有两个名字;新课还没人选,登记表里竟没有地方安放它。

E. F. Codd 在 1970 年提出关系模型(用二维表承载数据的数据模型)时一并给出
范式:用分级规则约束表设计,每升一级消除一类重复,业务库多以 3NF 为终点。
本实验用 SQLite(免安装、整库存成单文件的内嵌数据库,标准库 sqlite3 即其
驱动)把"从单表到 3NF"的每一步跑成可断言的证据。

## What

**定义**:范式是表结构的分级设计标准。第一范式(1NF)要求每个格子只存
一个值;第二范式(2NF)要求非主键列完全依赖整个主键(主键:唯一标识一行
的列或列组,如选课的"学生+课程");第三范式(3NF)要求非主键列只依赖
主键,不依赖其他非主键列。

判定的底层工具是函数依赖(一列的值能确定另一列的值,如课名一旦确定,
授课教师随之确定)。**例**:选课关系若靠"学生+课程"两列合起来定位一行,
"授课教师"却只由课程一边就能确定,和是哪个学生无关——它没依赖到整个
主键,这正是 2NF 要消除的形态,也是后续拆出 courses 表的依据。

可以把 3NF 想象成户籍管理:出生地只登记在你的档案里,别处引用身份证号即可,
改出生地只动一处。但和户籍不同的是,数据库用外键(声明"这一列的值必须
在对方表里存在"的约束)把引用正确性交给引擎强制执行,而非靠人工保证。

| 异常 | 单表设计的表现 | 3NF 三表的表现 |
|:--|:--|:--|
| 更新异常 | 改课名要动 N 行,漏改即脏数据 | 课名只存一处,改 1 行 |
| 插入异常 | 新课没人选,只能伪造占位学生行 | 新课独立成行,0 人选也合法 |
| 删除异常 | 删掉唯一选课人,课的信息跟着蒸发 | 选课行删除,课程档案还在 |

设计的演进路径:从单表拆出原子值,再拆出重复的事实,最后由外键兜住引用。

## When to Use

**典型场景**。业务交易库(记录随时在读写的在线业务数据)默认 3NF 起步,
写路径只改一处,数据天然一致。复查已有系统时,把"这张表里哪些列
在重复别人的事实"当作体检项,重复越多,异常越多。

**何时不用**。报表与统计分析场景常有意反范式(为读性能故意保留冗余):
把课名、教师直接复制进选课报表表,查询时不用再按外键把多张表拼接对齐
(多表连接),代价是写入端要多维护一致性。

| 设计 | 一句话特征 | 什么时候选它 |
|:--|:--|:--|
| 单表塞全部 | 一个格子多值,事实大量重复 | 只活一天的临时台账 |
| 平铺表 | 格子原子了,事实仍逐行重复 | 过渡形态,不建议停留 |
| 3NF 三表 | 每个事实只登记一处 | 业务库默认选择 |
| 故意反范式 | 冗余换读速度 | 读多写少的报表层 |

## How It Works

### 三类异常同源:一个事实被登记在多处

单表设计里,同一门课的信息随每条选课行重复:3 人选高等数学,课名就被
登记 3 次。改它要动 3 行(更新异常),课没人选就没有行可挂(插入异常),
删光行事实就消失(删除异常)——三类异常是同一个病灶的三种发作。

### 只修 1NF 不够:重复还在,只是换了位置

平铺表把逗号拆开,每个格子都原子了,但"授课教师"仍随每条选课行重复。
换一次教师,`UPDATE` 依旧命中 3 行。真正的分水岭在依赖:教师依赖的是课,
不是选课记录,所以教师列必须跟着课走——拆出 courses 表,这正是 3NF 的
"非主键列只依赖主键"。

### 外键把删除策略交给引擎

三表设计的选课表声明两条外键,删除行为各不相同:

```sql
student_id INTEGER NOT NULL REFERENCES students(id) ON DELETE CASCADE,
course_id  INTEGER NOT NULL REFERENCES courses(id) ON DELETE RESTRICT
```

CASCADE(级联:删主档,从属记录跟着自动清除)适合从属数据——学生退学,
他的选课行没有独立意义;RESTRICT(拒绝:还有引用就不许删)适合被依赖的
主档——还有人选的课不允许消失。两种行为都要求连接先执行
`PRAGMA foreign_keys = ON`,忘了这一句,声明只是注释。

## Pitfalls & Q&A

**坑 1:SQLite 的 rowcount 统计"匹配行"而非"值变化的行"**。不带 WHERE 的
`REPLACE()` 更新,没变的行也计入:对单表那 4 行直接执行,它报 4(赵六那行
实际没变);演示脚本加了 WHERE 才命中 3 行。别把 rowcount 当"实际修改数"用。

**坑 2:选课关系要防重**。同一学生选同一门课两次就是脏数据,表定义加
`UNIQUE (student_id, course_id)` 复合唯一约束(两列组合不允许重复)。

**坑 3:PRAGMA foreign_keys 是连接级开关**。每个连接(一次 sqlite3.connect()
得到的会话)都要重新执行;事务(把多条写操作打包成整体生效/整体回滚的机制)
内执行它会静默失效,先 commit() 再开。

**Q1:3NF 是终点吗?** 不是。BCNF 等更严范式处理主键列内部的依赖,业务库
极少需要;3NF 之后继续拆的收益,通常小于多一次连接的代价。

**Q2:什么信号说明该反范式了?** 查询端反复多表连接且数据只读多写少,
再加一个可容忍的一致性窗口(如计数延迟),冗余列才是合理交换。

**Q3:批量改名在 3NF 里也快吗?** 快。`UPDATE courses SET name=...` 只动
1 行,引用它的选课行靠外键关联,无需同步——这正是"事实只登记一处"的红利。
