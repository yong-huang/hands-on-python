# 22 · MongoDB 文档建模与 CRUD:内嵌一次拿全 vs 引用随取随查

> 同一个博客需求(20 篇文章 x 每篇 5 条评论)建两套集合:内嵌版读一篇文章
> 带全部评论只要 1 次查询,引用版是 1+N 形态;改作者昵称时内嵌版要改 20
> 篇(读写放大),引用版只改 1 处。CRUD 与 filter 语法顺带验收,含字符串
> id 字典序的经典坑。13 项断言跑成全绿。

## Background

关系库的建模纪律是"别重复":评论拆表、外键关联、JOIN 取回。MongoDB 的
文档模型给了另一个维度——评论可以直接内嵌在文章文档里,一篇连评论带的
完整 JSON 一次读回。两种模型没有对错,只有取舍:内嵌省查询但复制了数据,
引用不冗余但要多轮往返。

选错方向的代价是真实的:读多写少的评论场景用了引用,每次读文章都要多
几轮查询(N+1);写频繁的作者信息用了内嵌,改一次昵称要扫全集合逐篇改
(读写放大)。建模前先数"哪类操作更高频",是文档建模的第一课。

本实验把同一需求建两套集合,读和写各实测一遍,数字直接回答"选哪套"。

## What

**定义**:MongoDB 是文档数据库——数据以 BSON 文档(类 JSON,带类型)
存储,集合(collection)对应关系库的表但无固定 schema。内嵌指子数据
(评论数组)作为父文档的字段;引用指父子各自成集合、父存子的 id。

pymongo 是官方 Python 驱动,filter 即查询条件字典(如
{"author": "张三"}),操作符以 $ 开头($gt/$or/$set)。

可以把文档模型想成名片夹:内嵌是把联系方式直接印在名片背面(一张名片
全知道);引用是名片上写"档案在 3 号柜"(要看详情得再开一次柜子)。
但名片夹不管一致性——内嵌的数据改了,印出去的名片不会自己更新。

| 操作 | 内嵌版 | 引用版 |
|:--|:--|:--|
| 读文章 + 全部评论 | 1 次查询 | 1 次文章 + 评论查询(N+1) |
| 改作者昵称 | 改 M 篇文章 | 改 authors 1 处 |
| 评论独立分页/检索 | 难 | 易(独立集合) |

## When to Use

**典型场景**。内嵌:子数据总随父出现(订单+订单项、文章+评论)、子数据
生命周期与父一致(删文章评论必删);引用:子数据被多方共享(作者被多
篇文章引用)、子数据量大或独立增长(评论可能上千条分页)。

**何时不用**。需要多条件跨集合查询、事务跨多集合强一致的场景,引用版
配关系的思路更合适;MongoDB 4.0+ 虽有多文档事务,能少用则少用(实验 25
实测其开销)。

| 数据形态 | 建模 | 什么时候选它 |
|:--|:--|:--|
| 子随父读写、数量有界 | 内嵌 | 评论、地址、标签 |
| 子被多方引用、独立分页 | 引用 | 作者、商品目录 |
| 子数据巨大无界 | 引用 | 日志明细 |

## How It Works

### 内嵌与引用的读路径:1 次往返 vs N+1

内嵌版的一篇文章文档里就带着完整评论数组,find_one 一次拿全;引用版
find_one 拿到文章后,评论还要按 post_id 再查(本实验用 count_documents
演示,形态即 N+1)。实验 06 的"逐表对账"
思路在这里变成了"逐查询计数"——往返次数是文档建模的第一性能货币。

### 读写放大:改昵称为什么动了 20 篇

内嵌把作者名复制进了每篇文章。改昵称时 update_many 命中全部 20 篇——
读一次省下的往返,在写路径上连本带利还回来。引用版只改 authors 集合
一行,文章按 id 关联自然呈现新值。判断题只有一个:这类写发生的频率,
值不值得为读省那几次查询。

### 字符串 id 的字典序:字符串比较不认数值

MongoDB 的 _id 若用字符串 "post-2"、"post-15",$gt 按字典序比较:
"post-2" > "post-15"(字符 '2' > '1'),过滤会命中 post-2..9 与
post-16..20 共 13 篇。倒序同理,post-9 排在 post-20 前面。

要么用数字 id,要么补零对齐("post-002")。

## Pitfalls & Q&A

**坑 1:字符串 _id 的字典序**。$gt/$lt/sort 全按字符比较,数值直觉全部
失效(本实验实测 $gt 'post-15' 命中 13 篇而非 5 篇);要么 ObjectId,
要么数字,要么补零。

**坑 2:内嵌数组无上限地增长**。评论写到一万条,单文档触及 16MB 上限,
读写双双劣化;无界增长的子数据必须拆引用(或分页子集合)。

**坑 3:upsert 是 update 的参数不是独立命令**。update_one(filter,
update, upsert=True) 查无则插入。

**Q1:MongoDB 没有 schema 约束,怎么保证字段对?** 应用层校验(pydantic)
或集合级 JSON Schema validator;无 schema 是自由也是责任。

**Q2:内嵌评论能不能单独分页?** 能用 $slice 投影取窗口,但排序过滤
能力弱于独立集合;评论需要搜索/分页/审核流时就该拆出去。

**Q3:同一数据既内嵌又引用,冗余了怎么办?** 这叫"冗余写、引用读"的
混合建模(作者名冗余进文章便于展示,身份信息留 authors 便于修改),
代价是更新要同步多处——本实验的 update_many 演示的就是这个同步动作。
