# 17 · Redis 五大结构与 TTL:每个结构对准一个真实场景

> 一个 Redis 容器跑五个真实场景:Zset 排行榜(并列名次稳定)、Hash 购物车
> (field 级增删)、Set 共同关注(交集运算)、String 原子计数器(100 线程
> 并发 INCR 恰为 100,附非原子读改写丢更新的对照)、TTL 验证码到期自毁。
> 15 项断言跑成全绿。

## Background

业务里有一类数据不需要 SQL 的全部能力,却需要极高的读写速度:排行榜分数、
购物车、点赞关系、验证码。放进关系库,每秒上万次的读写会把表锁和索引
维护推成瓶颈;放进普通内存变量,多进程又共享不了。

Redis(内存键值数据库,靠单线程事件循环——一次只执行一条命令——工作)
填补这个位置:数据全部在内存,命令天然原子(串行执行,没有并发交错),
并且为常见形态内置了专门的数据结构——"按分数排序取前 N"的排行榜,
一个 Zset 就是现成的接口,不用自己写排序。

结构选型是 Redis 开发的核心判断:选对结构,业务逻辑大半由引擎代劳。
本实验五个场景各配一种结构,全部用断言验收。

## What

**定义**:Redis 的键是字符串,值的形态有五种:String(字节串)、List
(双端链表)、Hash(field→value 映射)、Set(无序去重集合)、Zset
(带分数的有序集合)。TTL 是键的生命周期:到期自动删除,验证码、限流
计数器都靠它自清理。

可以把 Redis 想成一支瑞士军刀:五种结构就是五个刀头,场景对上刀头,
一刀下去就是完整功能。但和普通工具不同的是,所有刀头共享"单线程"这一
把柄——每条命令执行期间不会插入其他命令,这正是 INCR(自增命令:把键的数值
加 1)原子性的来源。

| 结构 | 场景 | 关键命令 | 本实验断言 |
|:--|:--|:--|:--|
| Zset | 排行榜 | ZINCRBY/ZREVRANK/ZREVRANGE | 并列稳定、名次、TopN |
| Hash | 购物车 | HSET/HINCRBY/HDEL/HGETALL | 增改删整车读 |
| Set | 共同关注 | SINTER/SUNION/SDIFF | 交并差三运算 |
| String | 计数器 | INCR | 100 线程恰 100 |
| TTL | 验证码 | SET EX/TTL | 到期自毁 |

## When to Use

**典型场景**。高频读写的热点数据:排行榜、计数器、会话、验证码;需要
集合运算的社交关系:共同关注、推荐去重;需要过期语义的一切临时状态:
限流窗口、分布式锁(实验 20)、短期缓存(实验 18)。

**何时不用**。数据需要复杂查询(多条件 JOIN、模糊搜索)或持久是第一
诉求时,关系库仍是主体;Redis 内存贵,全量搬会把成本推上天——主流架构
是关系库为主、Redis 做热数据层(实验 18/19 的主题)。

| 需求 | 更合适的选择 |
|:--|:--|
| 排行榜/计数/队列/缓存 | Redis 各结构 |
| 复杂关联查询、强持久 | 关系数据库 |
| 全文搜索 | 实验出过的检索管线(10 号) |

## How It Works

### 原子性来自单线程,不是来自咒语

100 个线程同时 INCR,结果恰为 100:INCR 是单条命令,单线程事件循环执
行完一条才开始下一条,不存在两个线程同时"读到旧值"。

对照实验把操作拆成 GET-计算-SET 三步,50 个线程跑完只剩 9——丢失更新
发生在两步之间。推论:Redis 里凡是"读一下再改"的逻辑都是危险的,要么
用原子命令,要么用 WATCH(乐观锁:先监视键,提交前若键被别人改过就放弃重试)或锁
(实验 20)。

### Zset 的并列名次是确定性的

分数相同时 Zset 按成员的字典序(按字母/拼音先后)决定位置;排行榜从
高分往低排,故同为 90 分时 alice 与 carol 按字典序倒排——carol 稳定
在前。排行榜若要求"并列同名次",应用层用 ZREVRANGE 的分数
归组即可;引擎给的顺序永远可复现,不会因重跑而抖动。

### TTL 的语义细节

SET EX 2 设置 2 秒过期;TTL 命令对无过期时间的键返回 -1,对不存在的键
返回 -2,应用可以用它区分"永不过期"与"已消失"。过期键由 Redis 内部两种策略删除——惰性(访问到该键时才删)加定期(后
台周期抽样删),到期瞬间与真正消失之间可能有毫秒级延迟——
轮询断言因此按"最终消失"判定。

## Pitfalls & Q&A

**坑 1:redis-py 返回值默认是字节串**。decode_responses=True 让返回
直接是 str;不设时 `b'3' != '3'`,新手最常栽在这。

**坑 2:Hash 的值永远是字符串**。HINCRBY 后 HGET 回来是 '3' 不是 3,
算术要在应用层转 int;要存嵌套结构得序列化成 JSON 字符串。

**坑 3:先 GET 再 SET 的拆分写法是竞态(多个客户端交错执行,最终结果
取决于时序)**。见对照实验;凡是"基于旧值
修改"一律找对应的原子命令(INCRBY/HINCRBY)或加锁。

**Q1:Zset 同分成员的顺序可以自定义吗?** 引擎只保证字典序稳定;业务
要"同分先到先得"可以在分数里编码时间戳(如 score = 分数*1e10 + 时间戳)。

**Q2:TTL 到期就立刻删了吗?** Redis 惰性访问时删 + 定期抽样删,两者
配合;极端情况下已过期键可能短暂可见,精确到期的业务应校验值而非只信
键存在。

**Q3:为什么单线程还这么快?** 全内存 + 每种结构都是为该访问模式优化的
专用实现(Zset 的底层是跳表——给有序链表加多层索引、可快速定位的
结构)——快在数据结构,不在多线程。
