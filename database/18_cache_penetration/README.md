# 18 · 缓存穿透/击穿/雪崩:三类 miss 的数字级对比

> Redis + PostgreSQL 双容器,给 DB 查询装上计数器,把三大经典问题各复现
> 一遍再逐一修复:穿透 1000 次裸奔打到 DB 1000 次,空值缓存后 1 次;击穿
> 50 并发重建 50 次,互斥锁后 1 次;雪崩 200 键集体到期全穿透,随机 TTL
> 错峰后降到 56%。8 项断言跑成全绿。

## Background

缓存的第一原则是"miss 才去查库",但有三类流量专门打穿这条原则:查的
是根本不存在的数据(缓存永远没得拦)、齐打一个刚过期的热点 key(瞬间
全部 miss)、大量键设置了相同的过期时间(同一秒集体 miss)。任何一类放量,数据库都会在毫无防备的情况下承受全部流量。

这三类问题在单体小流量时代无人在意,在缓存承载主读流量的今天,
一次雪崩就能把库打挂。修复手段各有不同,验证方法相同:给 DB 查询装计数器,修复前后各压一轮,
数字必须说话。

本实验用同一个计数器把三类问题逐一复现、逐一修复,每组对比都落成
断言。

## What

**定义**:穿透指查询的数据在缓存与库里都不存在,请求必然穿过缓存打到
库(常见于恶意刷无效 id);击穿指某个热点 key 到期消失的瞬间,大量并发
同时 miss、同时去库重建;雪崩指大批键在同一时刻集体过期,miss 风暴
同时到来。三者共同点:缓存失守的瞬间,DB 直接面对全部请求。

可以把缓存想成景区闸机:正常情况一人一票快速通过。穿透是拿着不存在的
订单硬闯——闸机没有记录只能放去找检票长;击穿是检票口恰好换班,排队
的人一拥而上;雪崩是所有检票口同时换班。但闸机不会"到期失效",缓存键会——这个类比
只覆盖"谁被放行",覆盖不了 TTL;被放去找的检票长对应的就是数据库。

| 问题 | 触发条件 | 修法 | 本实验实测 |
|:--|:--|:--|:--|
| 穿透 | 查询不存在的数据 | 空值缓存(短暂缓存"不存在") | 1000 → 1 次 |
| 击穿 | 热点 key 过期瞬间 | SET NX 互斥,只放一人重建 | 50 → 1 次 |
| 雪崩 | 大批键集体过期 | TTL 加随机偏移错峰 | 200 → 113 次(56%) |

## When to Use

**典型场景**。任何"缓存承载主读流量"的系统上线前,都该过一遍这三问:
无效 id 会不会被刷(接口层校验+空值缓存)、有没有秒杀级热点 key(互斥
重建或逻辑过期)、批量预热的键(上线前先批量写入缓存的数据)是否共用过期时间(随机 TTL)。

**何时不用**。数据量小、全量可放内存的场景没有 miss,三类问题不存在;
读多写少且允许短暂不一致的小系统,加防护的复杂度可能大于收益。

| 防护 | 防什么 | 代价 |
|:--|:--|:--|
| 空值缓存 | 穿透 | 短暂缓存无用键 |
| 互斥重建 | 击穿 | 未持锁者等待 |
| 随机 TTL | 雪崩 | 过期时间不再整齐 |

## How It Works

### 空值缓存:把"不存在"也变成可缓存的答案

穿透的根源是"库里没有"这个事实无法被缓存——每次都 miss。空值缓存的
做法:首次确认库里也没有时,写入一个特殊标记(本实验用 NUL 字符,生产
常用 JSON)并给较短 TTL;后续同 id 请求读到标记直接返回空,1000 次只剩
首次 1 次 DB 查询。

代价是短时间内容忍"新插入的同 id 数据不可见",TTL 就是这个窗口的上限。

### 互斥重建:只放一个人去惊动数据库

击穿的全部伤害来自"N 个人发现 miss 后各自去查库"。SET NX(不存在才
设置,原子操作)充当重建许可证:只有抢到锁的 1 个请求查库回填,其余
请求短暂等待后读到的就是回填好的缓存。锁必须带 TTL——持有者崩溃时
锁自动消失,否则整条热点 key 从此无人重建。

### 随机 TTL:把"同时到期"摊开成"错峰到期"

雪崩的根源是过期时刻的相关性:同一批键同 TTL,就会同一秒死。给每个键
的 TTL 加随机偏移(本实验 2~5 秒),到期时刻摊开成 3 秒宽的窗口,任一
瞬间只有部分键 miss。实测同一时刻齐打,DB 次数从 200 降到 113(56%)
——剩余部分是已过期的键,这正是错峰的语义:削减峰值,而非消灭 miss。

## Pitfalls & Q&A

**坑 1:复现脚本自己会把现场冲掉**。雪崩实验里 hammer 之前误调一次
flushdb,刚重建的键全被清空,数字永远是 200——复现类实验的每个步骤
都要检查"这一步会不会破坏上一步搭好的现场"。

**坑 2:空值标记用 NUL 字符可读性差**。生产建议用 JSON(如 {"null":
true})加短 TTL;同时防止标记把"刚插入的真实数据"也挡在缓存外——
插入数据时应主动删除对应的空值标记。

**坑 3:互斥锁的等待方不能自旋空转**。实验里未抢到锁的请求 sleep 后重读
缓存;生产上要用带超时的重试,避免锁持有者崩溃时等待方无限阻塞。

**Q1:穿透还有别的修法吗?** 有:布隆过滤器(以极小内存回答"绝对不在")
挡在缓存之前,适合无效 id 海量出现的场景;空值缓存是其低配替代。

**Q2:逻辑过期与互斥重建怎么选?** 互斥重建保证新旧一致性但要等;逻辑
过期(值里带过期时间,过期后先返旧值再异步刷新)永不阻塞但要容忍旧
数据。热点 key 秒杀类用后者居多。

**Q3:三类问题会叠加吗?** 会——雪崩引发的 200 路并发里若混着无效 id,
击穿与穿透同时发生;生产的防护通常三层一起上,本实验分开复现只为
归因清晰。
