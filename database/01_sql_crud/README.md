# 01 · SQL CRUD 与约束系统:一条 SQL 的生命周期与五类约束

> 用一个零依赖的"小卖部"数据看一条 SQL(Structured Query Language,操作关系
> 数据库的标准语言)的完整生命周期:从 `execute()` 出发,穿过解析与五类约束
> 校验,要么落盘要么被整体拒绝。读完本篇,你能用标准库 `sqlite3` 完成建表与
> 增删改查,说清参数绑定防注入(把用户输入伪装成 SQL 代码执行的攻击)的原理。

## Background

在数据库引擎普及之前,程序把数据存成文本文件:一行一条记录,读写全靠字符串
切分。设想一个卖键盘的小卖部,商品台账是 `goods.txt`——改价格要找到对应行
改数字,收银和进货两个程序同时写它就会互相覆盖。

文本方案在三类场景撞墙:

- 非法数据拦不住:价格抄成负数,文件照单全收,错账拖到结账才暴露
- 重复数据清不掉:同一件商品抄了两行,改价漏一处,一件商品两个价格
- 写一半崩了:程序在改文件途中断电,文件剩半截,好坏数据分不清

SQLite 在 2000 年为此而生:它是不需要独立服务的进程内嵌库(数据库引擎直接
编译进你的程序,数据就是磁盘上的一个文件),SQL 语句进入引擎后先解析、再
校验、最后落盘,任何一步不合法都整体拒绝。Python 标准库自带驱动
`sqlite3`(驱动即程序与数据库引擎间的适配模块),零第三方依赖。

## What

**定义**:CRUD 是对数据的四种基本操作——增(INSERT)、查(SELECT)、改
(UPDATE)、删(DELETE);约束(constraint,写在表定义上的数据规则)由引擎在每次
写入前强制执行,违反即抛 `sqlite3.IntegrityError`,语句整体不生效。

可以把约束校验层想象成仓库收货员:每件货入库前按单验收,不合格整件退回,
仓库里永远不会有半件货。但和人工验货不同的是,它只认表定义上写明的规则,
表定义之外的复杂业务逻辑它一概不管。

五类约束各拦一种非法写入:

| 约束 | 拦什么 | 本实验的例子 |
|:--|:--|:--|
| PRIMARY KEY 主键 | 重复的行标识 | 两个 id=1 的商品 |
| NOT NULL 非空 | 缺关键字段 | name 为 NULL |
| UNIQUE 唯一 | 重复的业务标识 | 两个 sku=KB-001 |
| CHECK 检查 | 越界的值 | price=-0.01 |
| FOREIGN KEY 外键 | 悬空引用 | 引用不存在的商品 id |

一条 SQL 从应用到磁盘的完整路径:主路径(绿色实线)穿过解析器与约束校验层,
落进 B-tree 存储页(数据库在磁盘上存放表数据的真实结构,一种保持有序的树);
任一约束不满足就走虚线分支,异常原路抛回应用。

## When to Use

**典型场景**。单机工具的本地存储:配置、缓存、草稿这类"一个程序独占、
GB 级以下"的数据。应用原型:先跑通表结构与查询,迁到 PostgreSQL 时 SQL
大多原样可用。测试替身(用假组件顶替真实依赖的手法):单元测试用内存库
`sqlite3.connect(":memory:")`,秒起秒灭。

**何时不用**。多进程高频并发写同一个库时,文件锁会让写入排队,应换独立
服务型数据库;需要按用户远程连接、按库做备份与权限管理时同理。

| 方案 | 差异 | 什么时候选它 |
|:--|:--|:--|
| CSV / JSON 文件 | 无类型、无约束、并发写互相覆盖 | 几十行的只读配置 |
| SQLite | 进程内嵌,零部署,一个文件一个库 | 本实验;单机工具与原型 |
| PostgreSQL | 独立服务,多连接并发,功能完整 | 项目 6 起;生产系统默认选择 |

## How It Works

### 约束校验的时点:在解析之后、落盘之前

每条语句先经解析器(把 SQL 文本转成执行计划,即引擎内部的操作步骤描述),
再由校验层对照表定义逐项检查,最后才写存储页。约束违反发生在"还没写"的
时刻,被拒的语句不留下半行数据——5 次拒绝后,后续改价仍精确命中 1 行、
下架后恰好剩 2 行,库里没有任何被拒数据的残迹。

### 参数绑定:占位符把输入变成数据

拼接写法把用户输入直接并进 SQL 文本,输入里的 `'` 被当成字符串边界,
`OR '1'='1` 让 WHERE 条件恒真,于是全表返回。

参数绑定写法把 SQL 与参数分开递交:占位符 `?` 的值由驱动整体转义,再恶意
的载荷(指注入攻击携带的那段恶意输入)也只是 LIKE 的一个普通子串。两种
写法对合法输入结果一致,差异只出现在恶意输入上——这正是 inject 步断言的三件事。

### PRAGMA foreign_keys:每个连接自己的开关

PRAGMA 是 SQLite 的运行参数读写命令。外键是五类约束里唯一默认关闭的:
新连接必须执行 `PRAGMA foreign_keys = ON`,且只对本连接生效。实验里同一条
悬空引用,开关默认时插入成功、打开后被拒,两种行为都真实演示了。

## Pitfalls & Q&A

**坑 1:外键默认关闭**。不开 `PRAGMA foreign_keys=ON`,建表语句里的外键标注
`REFERENCES products(id)` 只是注释,悬空引用悄悄入库。连接建好后立刻开启。

**坑 2:REAL 浮点误差**。`259.0 * 0.8` 得 `207.20000000000002`,`== 207.2`
为 False。比较前先 `round(x, 2)`;记账类需求改用整型分存储。

**坑 3:executescript 的提交语义**。事务(transaction,把多条语句打包成
"要么全生效,要么全不算"的整体)未提交前可撤销。

`executescript()` 会先替你提交未决事务再跑脚本,混在业务写入里会意外提前
COMMIT(提交,即落盘)。建表用它,业务写入用 `execute()` 加显式 `commit()`。

**Q1:为什么主键推荐 INTEGER PRIMARY KEY?** 它是 SQLite 内部行号 rowid
的别名,按主键查找就是按行号定位;TEXT 主键则要多一层 B-tree 查找。

**Q2:一条语句被拒,同事务里之前的语句还在吗?** 在。约束违反只回滚当前这条
语句,之前已提交的数据不受影响;"要么全生效、要么全不算"的原子性见实验 05。
