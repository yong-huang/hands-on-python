# 19 · 缓存一致性:先删缓存为什么危险,延迟双删怎么救

> 一行商品数据、2000 轮并发读写:先删缓存的写法被并发读回填旧值,实测
> 993/2000 轮终态不一致;标准 Cache Aside(先更库再删缓存)同轮数 0 轮;
> 延迟双删再把对账收紧。4 项断言跑成全绿。

## Background

缓存承载读流量后,"数据更新时缓存怎么办"成为必答题。主流答案 Cache
Aside(旁路缓存)是:读时先查缓存、miss(缓存里没有要的数据)就查库回填;写时先更新数据库,
再删除缓存(是删不是更——让下次读自然回填最新值)。

但"删缓存"的时机暗藏杀机:如果写线程先删缓存、再更新库,中间一个并发
读线程会 miss 后读到库里的旧值并回填——回填完成后,库里已是新值,缓存
里却长期躺着旧值,不一致一直持续到下次写入。这是缓存一致性的第一课:
不一致不是缓存"算错了",而是并发交错把旧值钉在了缓存里。

本实验给这一课配上数字:2000 轮并发竞争,先删缓存的写法实测近半数轮
终态不一致;标准写法同轮数 0 轮;最后实测延迟双删的补救效果。

## What

**定义**:Cache Aside 是应用自己维护两侧的读写模式——读:缓存优先,
miss(缓存里没有要的数据)就查库回填;写:先更新数据库,再删除缓存。不一致指缓存中的值与库中
值不同(缓存为空不算,空只是"待回填")。延迟双删是补救策略:写完成后
延迟一小段时间再删一次缓存,把并发期间被回填的旧值清掉。

可以把缓存与库想成黑板与教科书:写的人先擦黑板再改书,旁听的读者趁
黑板空着抄了旧版书上的内容写上黑板——从此黑板上是错的。延迟双删就是
写的人改完书后回头再擦一次黑板。但擦黑板治标:只要"抄旧值"和"改书"
的先后无法保证,窗口就只能缩小,不能归零——归零要靠过期时间兜底。

| 写法 | 不一致窗口 | 本实验实测(2000 轮) |
|:--|:--|:--|
| 先删缓存,再更库 | 删后到更库完成,且回填值可长期留存 | 993 轮不一致 |
| 先更库,再删缓存 | 极小(读旧值的回填会被随后的删除清掉) | 0 轮 |
| 延迟双删 | 更库前后的短窗口,第二删收紧 | 残留 0 轮 |

## When to Use

**典型场景**。读多写少的热点数据(商品价格、用户资料)用 Cache Aside;
写后短暂不一致可容忍、但终态必须一致的配置类数据用延迟双删或订阅 binlog(数据库把每一行变更按顺序追加的日志流,外部
程序可订阅消费)的异步更新;所有用缓存的写路径都该先问一句:"删与更的顺序,并发下安全吗?"

**何时不用**。强一致诉求(库存扣减、余额)不要指望删缓存——那是锁和
事务的领地(实验 11);写后必须立刻可见且不可容忍任何旧读的场景,直接
读库或用同步双写加分布式锁。

| 策略 | 一致性强度 | 复杂度 | 什么时候选它 |
|:--|:--|:--|:--|
| 先更库再删(Cache Aside) | 终态一致,窗口极小 | 低 | 默认选择 |
| 延迟双删 | 收紧读旧写交错窗口 | 中 | 先删后更的存量改造 |
| binlog 订阅更新 | 与库最终一致 | 高(多组件) | 大规模缓存体系 |

## How It Works

### 先删缓存的窗口:三步交错把旧值钉进缓存

时序拆解:写线程删缓存(①);读线程此刻 miss,从库里读到旧值 100
(②);写线程把库更到 200;读线程把 100 回填进缓存(③)。至此库是新
的、缓存是旧的,而缓存里这个旧值没有任何机制会自动纠正——下一次写入
之前,所有读到它的人都被欺骗。实验用 2000 轮把这类交错捕捉了约一半。

### 为什么"先更库再删"窗口极小

标准写法的危险时刻是"读线程在更库前 miss、在删除后才回填"——回填的
是旧值,但删除发生在回填之前的概率极低(删除紧跟着更库完成,窗口只有
微秒级)。且即便发生,旧值也会在下一次写入被清掉;配合键的 TTL(Time To Live,即前文的过期时间),不一致有了硬上限。工程结论:顺序不能省,兜底不能少。

### 延迟双删:给"在途回填"留出落地时间再清场

延迟双删面向"必须先删"的存量逻辑:更库、删缓存、等一小段(覆盖在途
读线程的查库与回填,本实验 50ms)、再删一次。第二删把并发期间被回填
的旧值清掉,缓存变回"待回填"状态,下次读自然拿到新值。延迟量必须
大于在途读的最大耗时——这不是精确科学,是按接口 P99(99% 的请求耗时不超过此值)估出来的工程数。

## Pitfalls & Q&A

**坑 1:对账脚本把"缓存为空"判成不一致**。Cache Aside 写后删缓存,
空是正确终态(下次读回填);只有"有值且与库不符"才算不一致——判据
错了,实验结论整个反转,本实验首版就栽在这里。

**坑 2:延迟双删不是零窗口方案**。第二删只能清掉"已落地的回填";在
第二删之后才落地的旧值回填依然危险,过期时间是不一致时长的最后兜底。

**坑 3:删缓存失败等于没删**。删除这一步要重试(或进消息队列异步补删);
更新库成功而删缓存失败,不一致会一直留到 TTL 到期。

**Q1:为什么是删缓存而不是更新缓存?** 更新缓存在并发写时会乱序(两个
写线程的缓存写入可能与库提交顺序相反);删除是幂等的(同一操作执行多次与一次效果相同),谁后删谁生效,
下次读永远回填库里的当前值。

**Q2:读写分离场景下回填会更糟吗?** 会。读写分离指主库负责写、从库
(通过复制主库变更提供读服务的副本)负责读的部署;读线程连的是从库,
拿到更滞后的旧值,回填窗口更宽,延迟双删的延迟要按主从延迟(从库落后
主库的时间)来估。

**Q3:能不能两边同时更新做到强一致?** 分布式锁可以让"改库+改缓存"串
行化,但缓存写的失败处理、锁的粒度与死锁都成了新问题;缓存一致性通常
追求"终态一致 + 有界不一致窗口",强一致留给单一事实源。
