# 22 · 模块与导入系统：sys.modules、`__main__` 与循环导入

> `import` 看似一行关键字，背后是一条完整流水线：查 sys.modules（解释器进程内的模块缓存表）
> → 没有就执行模块体（并先入缓存）→ 绑定名字。
> 这决定了三件容易踩坑的事：模块体每个进程只执行一次；直接运行与被导入行为不同
> （`if __name__ == "__main__":` 守卫的原理）；模块顶部互相 import 会拿到"半初始化模块"——循环导入报错的根源。
> 本篇把它们连同包与相对导入，全部做成可断言的实测。

## Background

这节讲在模块机制出现之前代码怎么组织、痛点在哪、Python 用什么规则回答。

在此之前，所有代码挤进一个巨大的 `.py` 文件，或者靠复制粘贴把函数搬到各个脚本里；更早的系统语言（如 C）的 `#include` 是纯文本展开——包含几次就复制几份、重编译一遍。

痛点随规模到来：单文件膨胀到几千行，名字满天飞；复制粘贴的代码改一处漏三处；最麻烦的是"这段顶层代码到底执行了几次"没人说得清——数据库连接、信号注册被反复触发，程序行为全看 import 顺序。

Python 的回答是把"一个文件就是一个模块"定为基本单元，import 系统统一负责查找、执行一次、缓存复用、绑定名字；在这之上又长出包（带 `__init__.py` 的目录）与相对导入，支撑分层项目结构。

"执行一次"这个语义是后面一切的根基：模块因此可以安全地当配置载体、当注册表、当单例入口——本篇的坑与机制也全部围着它转。

## What

这节给出模块与导入的定义，并建立三步心智模型。

**模块**就是一个 `.py` 文件；**包**是带 `__init__.py` 的目录；**import 系统**是"查找 → 执行 → 缓存 → 绑定"的机制。一句话心智模型：**import = 查缓存 → 执行模块体 → 绑定名字**。

可以把 sys.modules 想象成公司的员工名录：第一位新员工来时，HR 走全套入职流程（执行模块体），办完登记进名录；之后同名的人直接按名录发工牌（返回缓存对象），流程不再走。但和员工名录不同的是，模块没有"离职"——进程不重启，缓存一直在。

由这条流水线直接推出三个现象：同一模块二次 import 拿到**同一个对象**（模块体不重跑）；直接运行的模块 `__name__` 是 `"__main__"`，被导入时是模块名；模块顶部互相 import（循环导入，即两个模块互相 import 对方）时，后导入方拿到一个**只执行到一半的模块对象**。

import 到手的是一个**模块对象**：模块体顶层定义的函数、类、变量都挂在它身上成为属性——`counter_mod.get_name()` 这样的调用，本质就是属性访问。

## When to Use

这节讲在做什么事的时候需要这套机制的知识，以及什么时候不值得兴师动众。

典型场景：

1. **在把大脚本拆成多文件/包时**：知道模块体每进程只执行一次，才能决定什么可以放模块级（常量、类定义），什么必须放进函数（连接、副作用）。
2. **在写入口脚本、CLI 工具时**：`__main__` 守卫保证脚本被测试导入、被子进程 re-import 时，入口代码不重放。
3. **在组织包结构时**：相对导入（`from .base import ...`）表达"同包成员"，绝对导入表达"跨包依赖"，模块坐标（如 `shapepkg.circle`）从此有了归属。
4. **在给模块写测试时**：明白"import 即执行一次模块体"，才能理解测试框架的夹具（fixture，测试前置准备）为什么必须先于被测模块的首次导入就位。

何时不用：

- 几十行的一次性小脚本，单文件加守卫就够，不值得建包建目录。
- "函数内 import"是处理循环依赖、可选依赖的工具，不该当隐藏依赖的常态手段（见 Pitfalls Q2）。
- 启动速度敏感的热路径（如 CLI 每次调用都要走的入口）：import 有真实的查找与执行成本，顶层只放必需的 import。

同类方案对比：

| 组织方式 | 差异 | 什么时候选它 |
|---|---|---|
| 单文件脚本 | 无导入开销，直接运行 | 几十行的一次性工具 |
| 平铺多模块 | 同目录 import，无层级 | 中型项目，依赖关系简单 |
| 包（目录 + `__init__.py`） | 有层级坐标，可相对导入 | 需要分层、复用、发布时 |

## Quick Start

这节跑通一个 4 小节的演示脚本，先看命令与真实输出，再逐段读实现代码。只需 Python 3.x 标准库。

```bash
cd core/22_import_system
python3 import_system.py    # 完整演示（4 个小节，内置断言）
```

真实输出：

```

[1] import 只执行一次（sys.modules 缓存）:

  第二次 import counter_mod（静默——缓存命中）：

全部断言通过 ✓ 缓存单次执行、守卫分流行为、循环导入复现与修复、相对导入
```

诚实预期：

- demo 输出**确定性**（循环导入的报错在子进程复现，绝对路径提示已剥离）
- 坏形态的报错文案随版本变化：3.13- 报 `ImportError: cannot import name ... (most likely due to a circular import)`，3.14+ 附加"同名文件改名"提示——语义相同

### sys.modules：缓存命中即同对象

```python
import counter_mod              # 第一次：执行模块体 + 塞进 sys.modules
import counter_mod as again     # 第二次：缓存命中，模块体不重跑

counter_mod is again            # True —— 同一个模块对象
```

这段在做什么：两次 import 同一模块，验证 `is` 为 `True`、模块体只打印一次。模块级副作用（连接、注册、`print`）因此每个进程只发生一次；"配置在 import 时读取"（12-factor——要求配置走环境变量的应用方法论）也源于此：环境变量必须在**首次 import 之前**就位。

### `__name__ == "__main__"`：直接运行与被导入分流

```python
if __name__ == "__main__":
    main()     # 直接运行才执行；被 import 时 __name__ 是模块名，整段跳过
```

这段在做什么：一行守卫，把"直接运行"和"被导入"两种命运分开。

直接运行 `python3 greeter.py` 时 `__name__ == "__main__"`，守卫块触发；被 import 时 `__name__ == "greeter"`，守卫块跳过但函数照常可用——测试导入、spawn 子进程 re-import 靠这条分流保证入口代码不重放。

### 包与相对导入

```python
# shapepkg/circle.py
from .base import Shape        # 相对导入：同包成员

class Circle(Shape): ...
```

这段在做什么：目录 + `__init__.py`（标记文件，Python 看到它才把目录当包）组成包；`from .base import Shape` 引用同包模块，模块坐标是 `shapepkg.circle`。

## How It Works

这节拆开循环导入的病根，并把输出里各现象对应到流水线的具体环节。

循环导入的病根是"import 时的半初始化模块"：

```python
# 坏形态：bad_a 顶部 from bad_b import shout，bad_b 顶部 from bad_a import Loud
# → 两边互相等待对方"初始化完成"，后到者拿到只执行到一半的模块
# → ImportError: cannot import name 'Loud' from 'bad_a'

# 修好的形态：把 import 挪进函数体，调用时两个模块都已初始化
def speak():
    from good_b import shout
    return "LOUD!" + shout()
```

模块 A 顶部 import B，B 顶部 import A——解释器先把 A 塞进 `sys.modules`（此时 A 的名字一个都没定义），执行到 B 的 `from bad_a import Loud` 时去 A 里找 `Loud`，找不到就报 `ImportError`。

三种解法按优先级：① 重新划分模块消除循环（治本）；② 把 import 挪进函数体（延迟到调用时，两个模块都已就绪）；③ `import bad_a` 整模块引用而非 `from` 取名（引用半成品模块对象不报错，但访问未定义名字仍会炸——只是把错误推迟）。

对照 Quick Start 的输出：[1] 里"两次 import 拿到同一对象: True"，来自流水线第一步的缓存命中；[3] 的 `ImportError` 来自这里的半初始化模块；[2] 的守卫分流来自 `__name__` 在两种启动方式下的取值差异。

[4] 的模块坐标 `shapepkg.circle` 则是包机制给模块的完整地址。

再往底一层：执行模块体之前，import 系统先要**找到**文件——查找器（finder，按 `sys.path` 逐个目录定位模块）与加载器（loader，读文件并执行模块体）分工完成。

应用代码很少直接碰它们，但"脚本名遮蔽标准库"的坑正发生在查找阶段：`sys.path[0]`（脚本所在目录）排在最前，见 Pitfalls 第 3 条。

## Pitfalls & Q&A

这节先列四个真实踩坑（现象、原因、解法），再回答三个取舍问题。

1. **模块级副作用**
   - 现象：只是 import 了一下，数据库连接被建立、文件被写、注册被触发。
   - 原因：这些代码写在模块体里，任何 import 者都会执行它。
   - 解法：副作用要么包进函数，要么挪进 `__main__` 守卫。

2. **环境变量注入晚于 import**
   - 现象：模块读到的配置是空值或旧值（web 系列 web/19_url_shortener 的 SHORTENER_DB 即此坑）。
   - 原因：读配置的模块在被 import 那一刻就绑定了值，之后再注入为时已晚。
   - 解法：环境变量注入必须先于首次 import。

3. **脚本名遮蔽标准库**
   - 现象：标准库行为诡异，报错出现在毫不相干的 import 处，极难排查。
   - 原因：`sys.path[0]` 是脚本所在目录，实验目录里自建的 `random.py`/`json.py` 会遮蔽同名标准库。
   - 解法：不拿标准库的名字给脚本命名。

4. **`from x import *`**
   - 现象：一个名字来源不明，改错人的时候不知道改到了谁的。
   - 原因：星号导入把公开名字全部灌进当前命名空间，LEGB 分析失效。
   - 解法：显式列出要用的名字。

**Q1: spawn 子进程为什么会重放入口代码？**
spawn 启动的新解释器要 import 主模块来定位可 pickle 的目标；`__main__` 模块被重新执行，顶层的 `p.start()` 等入口代码就会重放——`__main__` 守卫正是为此存在（见 concurrency/05 的实测）。

**Q2: 为什么"函数内 import"不算坏味道？**
顶层 import 是依赖声明，函数内 import 是延迟解析：处理循环导入、可选依赖（缺了只在用到时报错）、昂贵模块的按需加载。代价是每次调用有一次 `sys.modules` 查表——缓存命中，成本可忽略。

**Q3: `if __name__ == "__main__"` 里的代码能被测试吗？**
不能直接测（它只在直接运行时执行）。可测的做法：逻辑放函数，守卫块只调 `main()`——这也是所有实验脚本"逻辑与入口分离"的原因。

**Q4: 改了模块代码，`importlib.reload` 能热更新吗？**
能重新执行模块体，但只换掉 `sys.modules` 里的对象：已经 `from x import y` 拿到手的名字仍指向旧对象，reload 后新旧对象会短暂共存——热更新远比看起来麻烦，常规做法还是重启进程。
