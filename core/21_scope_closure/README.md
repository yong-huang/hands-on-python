# 21 · 作用域与闭包：LEGB、cell 与迟绑定

> 函数能"记住"上一次调用时的值、缓存装饰器的存储能活过函数返回——靠的正是闭包。
> 但这块知识经常缺一半：只知道"内层函数能用外层变量"，不知道名字按
> LEGB（Local → Enclosing → Global → Built-in，Python 的名字查找顺序）就近遮蔽；
> 只知道闭包"记住了值"，不知道它记住的是变量本身——循环里造闭包的经典 bug 由此而生。
> 本篇钉死这套机制：查找顺序、cell 存储、迟绑定（函数体到调用那一刻才去读变量），以及各自的修法。

## Background

这节回答三个问题：在清楚划分作用域之前，"函数记住状态"靠什么做？痛点在哪？Python 用什么规则回答了这个问题？

脚本起步时的常见做法：状态随手放全局变量。要一个函数记住"被调用过几次"，就在模块级写 `count = 0`，每个函数都来改它。

程序一大，全局状态开始失控：模块里多个函数共享一个 `total`，任何一处手滑赋值都会污染它，数值对不上时不知道该追哪个调用方；想给三个接口各配一个互不干扰的计数器，一份全局变量做不到，只能为每个计数器写一个类——五行样板只为一个数字。

回调场景还会再撞一次墙：把同一个处理函数注册到三个定时器，想让它们各自统计触发次数——全局变量只此一份，函数参数又带不回状态，两头堵。

Python 的回答是两条语言规则：名字按固定顺序分层查找，查到即停；内层函数可以把引用到的外部变量随身带走，外层函数返回后变量继续存活。这两条规则正是本篇的主题，也是看懂装饰器、回调、偏函数的前提。

## What

这节给出作用域与闭包的定义，并配两个可以带走的心智模型。

**作用域**（scope，一个名字在代码某处指向谁的有效范围）决定一个名字在某处指向谁：Python 按 **LEGB** 顺序查找——Local（函数内）→ Enclosing（外层函数）→ Global（模块级）→ Built-in（内建），同名就近遮蔽。

**闭包**（closure）是"内层函数 + 它引用的外层变量（自由变量）"的打包对象：外层函数返回后，自由变量活在 `__closure__` 的 cell（包装自由变量的小对象）里，内层函数每次调用都能读写它。

可以把 LEGB 查找想象成在办公楼里找人：先看本工位（Local），找不到问本部门（Enclosing），再问全公司（Global），最后查外包服务商名录（Built-in），同名者就近优先。

但和找人不同的是：这套顺序只管"读"；"写"（赋值）不按它找——赋值直接在当前层创建新名字，这是下文 `nonlocal` 存在的原因。

可以把闭包想象成贴身口袋：内层函数"出厂"时，把引用到的外层变量装进口袋（cell），函数传到哪口袋跟到哪。但和口袋里揣着现金不同的是，装的是盒子（变量本身）而不是值快照——盒子里的数被改了，函数下次读到的就是新值。

还要分清遮蔽（shadowing）与修改：内层的同名赋值只是"挡住视线"，外层变量原值不动——输出 [1] 里外层自己的 `value` 仍是 `'enclosing'`，正是这个道理。

## When to Use

这节讲什么场合值得用闭包携带状态、什么场合该换别的方案。

典型场景：

1. **在需要"函数自带一块私有状态"时**（计数器、累加器、缓存）：闭包比全局变量安全——状态对外不可见；比定义类轻——一个工厂函数（造好内层函数并返回的外层函数，如 Quick Start 的 make_counter）就够。
2. **在写装饰器（接收函数并返回新函数的语法）和回调工厂（批量生成回调函数的工厂函数）时**：装饰器返回的新函数（惯例命名为 `wrapper`）靠闭包携带配置，如重试次数、缓存表；配置活在自己那层作用域里，不污染外部。
3. **在批量生成相似函数时**：循环里造一批 lambda 或闭包，用默认参数快照固定"当时的值"（见 Quick Start 第三段）。

何时不用：

- 状态项多、行为复杂时直接写类：闭包里塞一堆 `nonlocal` 声明，可读性很快崩掉。
- 状态需要全局共享时才用 `global`——真实代码里这应该极少发生。
- 一次性简单逻辑不值得嵌套函数，平铺直叙更清晰。

同类方案对比：

| 方案 | 与闭包的差异 | 什么时候选它 |
|---|---|---|
| 全局变量 | 模块级人人可见可改，无法多实例 | 真全局的配置、常量时 |
| 类实例 | 状态与行为打包，可多实例可继承 | 状态项多、行为复杂时 |
| 可变默认参数 | 靠默认值对象跨调用存活 | 不推荐：语义陷阱多，能读懂旧代码即可 |

- `[3]` 的 `[2, 2, 2]` 是"迟绑定"本身——lambda 的函数体在**调用时**才读 `i`，而循环结束后 `i` 是 2

### LEGB：就近遮蔽

```python
value = "global"

def legb_demo():
    value = "enclosing"

    def inner():
        value = "local"     # 就近遮蔽：这行删掉，才会读到 enclosing 层
        return value

    return inner(), value
```

这段在做什么：四层各放一个同名 `value`，验证内层读到最近的一层。同时注意"赋值即声明局部名"——内层写 `value = ...` 不会改外层的 `value`，而是新建一个局部名字；要改外层变量必须显式声明（见下段）。

### nonlocal：改 Enclosing 层的变量

```python
def make_counter():
    count = 0

    def counter():
        nonlocal count     # 不写这行，count += 1 视 count 为 counter 的局部变量
        count += 1         # → UnboundLocalError（读的时候还没有值）
        return count
    return counter
```

这段在做什么：一个不写声明就报错的计数器，展示赋值规则的破口。`global` 指向模块级——跨函数人人共享同一个名字；`nonlocal` 只向上找一层层的函数作用域，不碰模块级。

### 循环里造闭包：迟绑定

```python
fns = [lambda: i for i in range(3)]
[f() for f in fns]         # [2, 2, 2] —— 三个 lambda 共享同一个 i

fns = [lambda i=i: i for i in range(3)]
[f() for f in fns]         # [0, 1, 2] —— 默认参数在定义时求值，等于快照
```

这段在做什么：同一批 lambda，带不带默认参数快照，结果在 `[2, 2, 2]` 与 `[0, 1, 2]` 之间切换。闭包记住的是**变量本身**，不是它当时的值；共享机制见下一节，修复方案见 Pitfalls Q3。

## How It Works

这节回答"外层函数都返回了，变量为什么还活着"——证据就在输出 [2] 和 [4] 里。

最核心的证据——闭包变量住在 cell 对象里：

```python
def make_counter():
    count = 0
    def counter():
        nonlocal count
        count += 1
        return count
    return counter

counter = make_counter()
counter.__closure__            # (<cell ...: int object ...>,)
dis.get_instructions(counter)  # 存储指令是 STORE_DEREF（写 cell），不是 STORE_FAST
```

普通局部变量的存储指令是 `STORE_FAST`（读写栈帧上的槽位，函数返回即销毁）；被内层捕获的变量升级为 cell，指令变 `STORE_DEREF`——这就是"外层函数返回后变量仍然活着"的实现。

两个 `make_counter()` 的调用产生两套独立 cell，所以输出 [4] 里两个计数器互不干扰（A=2，B=1）。

输出 [3] 的 `[2, 2, 2]` 也能用 cell 解释：列表推导式里只有一个 `i`，三个 lambda 的 `__closure__` 指向**同一个 cell**，循环做的事只是反复给这个 cell 写新值（0、1、2），函数体调用时读到的自然是最后的 2。

而 `lambda i=i` 的默认参数在 `def` 执行那一刻求值，每个 lambda 各存一份在自己的 `__defaults__` 里——所以是互不影响的快照。

What 节"贴身口袋"的本体就是这串 cell：口袋跟着函数对象走，函数对象被引用多久，cell 里的变量就活多久。

最后补一句全局观：这套分层在编译期就划定了——函数被编译成字节码时，每个名字属于哪层已经确定，`nonlocal` / `global` 声明是显式改变默认归属的出口。

对照 Quick Start：输出 [2] 打印的 `<cell ...: int object ...>` 和 `cell_contents=2`，就是这个 cell 结构本体；输出 [4] 的 `['STORE_DEREF']` 是字节码层面的直接佐证——`count` 的家已从栈帧槽位搬进 cell。

## Pitfalls & Q&A

这节先列四个真实踩坑（现象、原因、解法），再回答三个取舍问题。

1. **循环变量闭包（迟绑定）**
   - 现象：批量生成的回调全部读到循环末值，如输出 [3] 的 `[2, 2, 2]`。
   - 原因：函数体调用时才去读变量，那时循环已结束、变量停在末值。
   - 解法：默认参数快照、`functools.partial` 固定实参，或把循环体包成函数（见 Q3）。

2. **内层赋值不声明 `nonlocal`**
   - 现象：`count += 1` 抛 `UnboundLocalError`（先读后写场景），或赋值后外层变量纹丝不动（"改了个寂寞"）。
   - 原因：赋值即声明局部名，Python 把赋值目标当成内层函数自己的新变量。
   - 解法：要改写外层变量，在函数体第一行显式写 `nonlocal`。

3. **误用 `global` 做计数器**
   - 现象：多个"计数器实例"互相污染，数字对不上。
   - 原因：模块级名字人人可见，所有函数改的是同一个变量。
   - 解法：需要独立状态就用闭包（`nonlocal`）或类实例。

4. **`__closure__` 为 `None`**
   - 现象：检查内层函数的 `__closure__`，拿到 `None` 而不是 cell 元组。
   - 原因：内层函数没有引用任何外层变量，就不构成闭包。
   - 解法：检查自由变量名是否拼错、是否被局部赋值遮蔽。

**Q1: 装饰器为什么必须理解闭包？**
装饰器的 `wrapper` 就是闭包：`retry` 的 `times`、`ttl_cache` 的 `store` 都是自由变量，靠 cell 活过装饰时刻。装饰器的用法见 lab 01，其机制根据就是本篇的 cell 语义。

**Q2: `nonlocal` 和 `global` 可以互换吗？**
不能。`nonlocal` 向外层函数作用域找变量（不碰模块级）；`global` 只指模块级名字。计数器想"实例独立"用 `nonlocal`，想"全局唯一"才用 `global`。

**Q3: 怎么让闭包拿到循环变量的"当时值"？**
三种：默认参数快照（`lambda i=i: ...`）、`functools.partial(fn, i)` 固定实参、或用生成器表达式/函数包一层把 `i` 变成每次循环的局部变量。

**Q4: 闭包会拖住内存不放吗？**
只要闭包对象本身可达，它口袋里的 cell 就不可回收——被捕获的大对象会活到函数对象消亡为止。长生命周期的回调（如常驻的事件监听）引用了大块数据时，不再需要就显式解除注册或置 `None`。
