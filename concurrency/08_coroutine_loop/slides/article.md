# 08 · 协程与事件循环机制：单线程内的并发

> 线程与进程的并发都受"每个任务占一个执行流"的成本约束，asyncio（标准库的异步并发框架）反其道而行：
> **干脆只用一个线程**，靠 `await` 主动让出实现并发。
> 本实验用 0.4 秒验证四件事：协程是惰性的、await 让出的是控制权、一切都在主线程上、
> await 链不并发而 create_task 才并发。

## Background

这节讲异步并发出现之前 Python 怎么处理海量等待、线程方案在哪里撞墙，以及 asyncio 如何应运而生。

在此之前，处理"大量任务在等 IO"的默认答案是线程：让每个等待中的任务各占一个线程，切换交给操作系统。上千个并发连接意味着上千个线程，内存与切换成本随并发数线性上涨。

撞墙点有二：一是成本——海量 IO 等待场景里（比如一万条网络连接大部分时间在等数据），绝大多数线程只是干等，资源全花在"养线程"上；二是不可控——线程是抢占式调度（由内核强制切换，任务自己说了不算），又受 GIL（全局解释器锁，同一时刻只允许一个线程执行字节码）串行化，执行交错无法复现，时序问题难以排查。

异步并发的思路是把切换权从内核拿回用户代码：任务在等待点主动让出，单线程就能同时照看上万条连接。标准库 asyncio 在 Python 3.4 进入，3.5 起有 async/await 语法（PEP 492），是 Python 异步并发的标准底座。

## What

这节给出协程与事件循环的定义，以及一个覆盖全文机制的调度心智模型。

协程（coroutine，用户态的协作式任务——执行到 `await` 处主动暂停、把控制权交出来）是 asyncio 并发的基本单位；事件循环（event loop，单线程内反复"取任务—执行—等事件"的循环体）负责在这些协程之间切换。

一句话心智模型：**协程在 await 处主动交还控制权，事件循环单线程地在协程之间切换，睡眠中的任务挂在定时器堆上，到期再放回可运行队列**——全程没有第二个线程。

可以把事件循环想象成一位独自照看全店的服务员：哪桌菜好了（定时器到期、IO 就绪）就去哪桌上菜，暂时没人喊就先擦别的桌子（跑就绪队列里的协程）。但和多家餐厅不同的是：这家店只有一个服务员，任何一桌让他站着干等（阻塞调用），全店都得跟着停。

注意一对词：并发（多任务在重叠时段内交错推进）不等于并行（多任务在同一瞬间真的同时执行）。asyncio 给的是并发，不是并行。

## When to Use

这节讲协程适合什么负载、不适合什么负载，以及与线程/进程怎么选。

- **海量 IO 等待**：上万条并发连接的抓取器、长连接网关——每任务只占一个协程对象而非一个线程，等待时让出而不是占着执行流干等。
- **需要可复现交错的并发逻辑**：协作式调度（任务在约定点主动让出）让交错序列可断言——本实验的 `A1 B1 A2 B2 A3 B3` 就是例子；线程的抢占式交错做不到。
- **单机任务编排**：几十上百个有依赖关系的异步步骤，用 Task 与 await 组合表达，见 [09_task_orchestration](../09_task_orchestration/README.md)。

何时不用：

- **CPU 密集任务**：协程不让出就会独占循环，别的任务全饿死——真并行要进程，见 [05_mp_accel](../05_mp_accel/README.md)。
- **必须调阻塞库**：没异步接口的库会卡住整个循环，用线程兜底更直接。
- **并发量就几个、逻辑简单**：线程或顺序代码更直观，不值得引入异步生态。

三者对比（一行一个）：

| 方案 | 调度方式与成本 | 什么时候选它 |
|---|---|---|
| `threading` 线程 | 内核抢占式，切换要陷入内核，受 GIL 串行化 | 中低并发 IO；要调阻塞库时兜底 |
| `multiprocessing` 进程 | 多解释器真并行 | CPU 密集负载 |
| asyncio 协程 | 用户态协作式，主动让出（await），切换成本是函数调用级 | 海量 IO 等待 |

CPU 密集两者（协程与线程）都不行——要进程。

## Quick Start

实验只依赖标准库，无需安装第三方包，完整脚本在实验目录的 `coroutine_loop.py`。

```bash
cd concurrency/08_coroutine_loop
python3 coroutine_loop.py      # 四个实测小节 + 全部断言，约 0.5 秒
```

这段命令在做什么：脚本逐条验证协程对象的惰性、await 的让出与单线程事实、await 链与 create_task 的并发差异，最后运行全部断言。

真实输出（节选）：

```
========================================================
[1. 调用协程函数 ≠ 执行函数体]
========================================================
  coro = sample() → <coroutine object sample at 0x1051cf4c0>
  此刻函数体执行痕迹: []（一行都没跑）
  asyncio.run(coro) → 'sample-结果'，执行痕迹: ['body-ran']
  忘记 await 是 asyncio 第一大坑：协程对象被 GC 时会警告'never awaited'

========================================================
[2. await 让出控制权：单线程内的交错]
========================================================
  交错序列: A1 B1 A2 B2 A3 B3（sleep(0) 轮转，精确可复现）
  线程断言：全部协程代码跑在同一个线程上
  协程所在线程: MainThread（asyncio 从不创建新线程）
  并发 ≠ 并行：单线程靠 await 主动让出实现'看起来同时'

========================================================
[4. await 链 vs create_task：差的不是语法是并发]
========================================================
  await 链（顺序）:  203ms  ['s1', 's2']
  create_task（并发）: 101ms  ['c1', 'c2']   (2.01×)
  await coro() 只是带异步语法的函数调用；想同时跑，先 create_task 挂上去
```

诚实预期（本机 3 次实测）：

- **§2 的交错序列精确等于 `A1 B1 A2 B2 A3 B3`**：`sleep(0)` 的让出是确定性轮转，可作断言；换成 `sleep(0.01)` 就不该断言顺序了
- **§4 加速比 ≈ 2.0×**：两个 100ms 任务真并发，理论恰为 2×，实测 2.01×（事件循环自身开销可忽略）
- 全部小节零随机性，任何机器任何负载都该 100% 通过

异步编程的常用入口：

| API | 作用 | 一句话备注 |
|---|---|---|
| `async def` / `await` | 定义协程 / 让出控制权 | 调用协程函数只造对象，不执行函数体 |
| `asyncio.run(coro)` | 建循环、跑完即清理 | 程序主入口用一次 |
| `asyncio.create_task(coro)` | 把协程挂上循环，立刻可被调度 | 真并发的入口 |
| `asyncio.sleep(delay)` | 非阻塞睡眠，让出循环 | 换成 `time.sleep` 会全局停摆 |
| `loop = asyncio.new_event_loop()` | 手动创建事件循环 | `asyncio.run` 的底层部件 |

## How It Works

这节把输出里的三段现象对应到协程的三个机制，再说明实验为什么用 `sleep(0)` 做演示。

### 协程对象：惰性到"一行都不跑"

`sample()` 这样调用协程函数，得到的是一个协程对象——它把函数体、局部变量、执行位置打包起来，**等事件循环驱动才执行**。不 await 就丢弃它，GC（垃圾回收）时会警告 `coroutine was never awaited`。

这是 asyncio 第一大坑：`asyncio.run(main())` 忘了写、或者 `main()` 里调了子协程却没 await，程序什么都没做就"成功"退出。输出 [1] 的执行痕迹 `[]` 与 `'body-ran'` 前后对照，就是这个事实。

### await：主动让出控制权

`await x` 的语义是"我要等 x，先把控制权还给事件循环"。事件循环拿回控制权后调度其他就绪协程——所以两个协程能在**同一个线程**里交错（输出 [2] 实测序列 `A1 B1 A2 B2 A3 B3`，`sleep(0)` 让出是确定性轮转）。

关键推论：**并发 ≠ 并行**——asyncio 从不创建线程，它只是不让 CPU 闲着等 IO。

### 事件循环：一个线程 + 一张调度表

`asyncio.run(main())` ≈ `new_event_loop()` + `run_until_complete()` + 清理（实测两者结果完全一致）——前者只是后者的封装，没有本质区别。

循环维护一张调度表：就绪队列（可立即执行）与定时器堆（`sleep` 到期/IO 就绪再入队）。**一个线程同时只能有一个运行中的事件循环**——在协程里再调 `asyncio.run()` 会直接报错。

### await 链 vs create_task：顺序执行与真并发

```python
r.append(await slow_step("s1", 0.1))   # 顺序：等 s1 完才开 s2（共 200ms）
t = asyncio.create_task(slow_step("c2", 0.1))   # 并发：先挂上任务再收结果（共 101ms）
```

这段代码在做什么：第一行是 await 链——`await coro()` 只是"带异步语法的函数调用"，不并发，只允许中途让出；第二行先 `create_task()` 把协程挂上循环，让它立刻参与调度，`await` 之后只负责收结果。

输出 [4] 的 203ms 对 101ms（2.01×）就是两者的差异：两个 100ms 任务顺序执行与真并发。TaskGroup 是 create_task 的结构化升级版，见 [09_task_orchestration](../09_task_orchestration/README.md)。

### 为什么交错演示用 `sleep(0)`

`sleep(0)` 是"让出但立刻回就绪队列"——事件循环按固定顺序轮转，交错序列精确为 `A1 B1 A2 B2 A3 B3`，可以写成断言。换成真实毫秒级 sleep，定时器精度和系统抖动会让顺序波动——**断言要建立在确定性的机制上**，否则测试自己成了随机失败（flake）的源头。

## Pitfalls & Q&A

这节收集五个常见坑，每条按"现象 + 原因 + 解法"展开——前两条对应本实验开头点名的认知误解。

### 踩坑清单

- **以为调用协程函数就会执行**：现象是程序什么都没做就"成功"退出，GC 时警告 `never awaited`。原因：调用协程函数只造协程对象，函数体要等事件循环驱动。解法：要么 `await` 它，要么 `create_task` 挂上循环（机制见 How It Works 节）。
- **以为 await 创建了新线程**：现象是按多线程心智找"并行"找不到。原因：实测全部协程都在 MainThread——asyncio 从不创建线程，靠让出实现并发。解法：理解单线程交错模型，真并行需求交给进程。
- **把 `await coro()` 当成并发**：现象是总耗时等于各任务之和。原因：await 链是顺序执行，只是带异步语法。解法：先 `create_task` 挂上循环再收结果。
- **在协程里调 `time.sleep()`**：现象是整个事件循环被卡死，所有协程一起停摆。原因：同步阻塞调用不让出控制权。解法：异步世界只准 `await asyncio.sleep()`。
- **把 CPU 密集任务放进协程**：现象是循环被独占，其他协程全部饿死。原因：纯计算不会走到让出点。解法：用 `run_in_executor`（把阻塞活儿丢给线程/进程池执行的桥接接口）移出循环。
