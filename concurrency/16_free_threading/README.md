# 16 · ⚠️ 选做——free-threading 无 GIL 实测：跑进"没有 GIL 的世界"

> Python 有了不带 GIL 的官方构建（PEP 703）。`uv python install 3.14t` 装一个
> free-threading 构建，把同一段 threading 代码在两种构建下各跑一遍：
> **GIL 构建 4 线程 0.97×（串行化），free-threading 构建 3.73×（真并行）**——
> "线程是假并发"的叙事，在这里被正式改写。

## Background

这节讲 GIL 这道几十年的旧约束，以及"移除它"这条路是怎么打开的。

GIL——全局解释器锁，CPython 里同一时刻只允许一个线程执行 Python 字节码的机制。它用一把大锁换来了实现简单与单线程速度，代价是 CPU 密集任务开再多线程也只有一个核在动（lab 14 实测 1.18×）。

在这条路打开之前，Python 程序员要做多核计算只有两个绕法：multiprocessing 开独立进程——共享数据得靠 pickle 序列化（把对象转成字节流才能跨进程搬运、到对面再还原）来回搬运，内存与通信开销随数据量上涨；或把热循环下沉到能释放 GIL 的 C 扩展（numpy 一类）。

"一个 Python 进程吃满多核"始终做不到。

2024 年起 CPython 有了不带 GIL 的官方构建，3.14 起正式受支持：
多核路线从"绕开锁"变成"拿掉锁"。本实验亲手装一个这样的构建、
亲手跑一遍同一份代码，验证三件事——GIL 状态可以关、threading 可以真并行、
扩展比（多线程相对单线程的加速倍数）能到 3.7×。

同时也验证一个新常识：没有 GIL 兜底后，
竞态（race condition，多个执行流交错读写共享数据、结果取决于时序）的面积变大了，
锁该加还得加。

## What

这节定义 free-threading 构建，并给出双构建对照的核心数字。

free-threading 是 PEP 703（移除 GIL 的提案，已落地为官方构建选项）移除 GIL 的
CPython 变体——同一门语言、不同构建：GIL 构建是日常用的默认版。

free-threading 构建在编译期关掉了 GIL，
连 ABI（Application Binary Interface，二进制接口——
C 扩展要按对应 ABI 编译才能被加载）都不同。

一句话心智模型：**同一份 threading 代码，GIL 构建把它串行化（0.97×），free-threading 构建让它 4 核齐跑（3.73×）——换的是解释器构建，不是你的代码**。

上下对照：同一个"4 线程 × 200 万迭代"任务，走进 GIL 构建就排队（0.125s），走进 free-threading 构建就真并行（0.027s）。

可以把 GIL 想象成自习室里唯一的一支麦克风：线程再多，同一时刻也只有一人发言；free-threading 构建给每人发了一支麦克风。但和自习室不同的是，同时发言就需要新的秩序——细粒度锁代替了全屋纪律，该排队的地方仍然要自己排（见 How It Works 的竞态部分）。

## When to Use

这节讲什么情况下值得换构建，以及迁移前的检查单。

适合考虑 free-threading 构建的场景：

- CPU 密集、逻辑天然按线程分块（分片计算、共享大块只读数据）的服务——免去 multiprocessing 的序列化搬运；
- 现有架构里"进程池 + 共享状态"的胶水代码一大堆、想简化成单进程多线程的系统。

何时不用：依赖长尾 C 扩展的团队——wheel（Python 包的预编译分发格式）要按 cp314t 这个独立 ABI 单独提供，缺了就装不上；单线程延迟敏感的服务——free-threading 单线程比 GIL 构建慢 ~5-10%；纯 IO 密集服务——GIL 对 IO 等待本就放行，收益有限。

迁移检查单（生态现状，2026 年）：主流科学栈（numpy / pydantic 等）已提供 cp314t wheel，长尾库仍有缺口。顺序是：确认依赖 wheel 覆盖 → 压测单线程回退 → 竞态审计（竞态与同步原语的作业全部重做）。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| GIL 构建 + multiprocessing | 真并行；参数经序列化，进程崩溃互相隔离 | 当前默认；CPU 密集的稳妥解 |
| GIL 构建 + threading | CPU 密集被串行化（1.18×）；IO 可用 | IO 并发，或生态未备好前的等待区 |
| free-threading 构建 | 真并行 + 共享内存；需 cp314t wheel；单线程慢 5-10% | CPU 密集 + 线程模型 + 依赖齐备 |

## Quick Start

这节装上 free-threading 构建并跑一次双构建对比。uv（一个 Python 版本与包管理工具）装构建是一次性的。

```bash
# 前置（一次性）：uv python install 3.14t   # 本机已装 3.14.3t ✅
cd concurrency/16_free_threading
python3 free_threading.py             # 自动探测 python3.14t，双构建对比 + 断言
```

真实输出（节选）：

```
========================================================
[1. 双构建对比：4 线程 × 2,000,000 次迭代]
========================================================
  构建               版本         GIL         1线程      4线程      扩展比
  GIL              3.13.9     开        0.030s   0.125s    0.97×
  free-threading   3.14.3     关        0.025s   0.027s    3.73×

  结论：GIL 构建 4 线程 0.97×（串行化），free-threading 3.73×（真并行）
  同样的 threading 代码，换了构建就是两倍以上吞吐——这就是 PEP 703 的意义

========================================================
全部断言通过 ✓  验收点：双构建 GIL 状态（§1）、扩展比对照（§1）
提醒：free-threading 下'靠 GIL 兜底的侥幸代码'不再安全——锁该加还得加（见 lab 03）
```

诚实预期（本机 3 次实测）：

- **free-threading 扩展比 3.4~3.9× 波动**：4 线程在 18 核上接近线性；断言线 ≥2.0× 留足余量
- **GIL 构建的 0.97× 是"总功 4 倍、墙钟不变"**（墙钟时间即现实中从开始到结束的耗时）：4 线程各做 200 万次（共 800 万）与单线程 200 万耗时相同——在 GIL 下这不可能，在 free-threading 下这是常态
- **两条断言绑构建类型**：GIL 构建断言 `gil_enabled=True` 且扩展比 <1.3；free-threading 构建断言 `gil_enabled=False` 且扩展比 ≥2.0

## How It Works

这节拆三件事：PEP 703 改了什么、扩展比为什么这样定义、竞态面积如何重算。

### PEP 703：GIL 成为可选项

free-threading 构建从解释器里**移除了 GIL**，改用细粒度锁（把一把大锁拆成保护小范围数据的许多小锁）与引用计数改造保证内存安全——引用计数（对象被引用次数的记账）改为延迟记账，分代 GC（按对象年龄分代的垃圾回收）也做了调整。

`sys._is_gil_enabled()` 是探测开关状态的官方接口；free-threading 构建还允许用 `PYTHON_GIL=1` 临时把 GIL 请回来——兼容模式的逃生门。输出表里"开 / 关"两行，读的就是这个接口。

### 扩展比为什么这样定义

**为什么扩展比的定义是 `T × t(单线程) / t(T 线程)` 而不是 `t(单线程) / t(多线程)`？**

```python
t1 = bench_threads(1, N_ITER)       # 单线程做 n 次
t4 = bench_threads(4, N_ITER)       # 4 线程各做 n 次（总功 4n）
speedup = N_THREADS * t1 / t4       # 串行做 4n ÷ 并行做 4n
```

前者比较的是"同样总功"的耗时——4 线程各做 200 万次的总功等于单线程做 800 万次。

第一版误用"单线程 n 次 ÷ 4 线程 n 次"，理想并行下比值恰好 1.0（分母里的总功也是 4 倍）——**度量定义错了，真正的 4× 并行会被看成 0.95×**。输出表里 0.97× 与 3.73× 两个数，都按这段代码的定义算出。

### 竞态面积的重新计算

GIL 世界里"读-改-写之间没有检查点就不丢"（竞态实验的实测结论）；free-threading 下没有全局锁兜底，**任何非原子的共享读写都是真竞态**——原子指操作的不可分割：要么整个完成、要么整个没发生，中间的半成品状态不会被其他线程看到——无锁实验在这里会从"丢失 78%"恶化到"结果不可预测"。

推论：迁移到 free-threading 构建前，先过一遍同步原语实验——所有共享可变状态都必须有锁（或改为消息传递）。

## Pitfalls & Q&A

这节收录四条踩坑与三个深入追问。

踩坑清单：

- **把 free-threading 当"更快的 GIL 构建"**：现象是 C 扩展装不上、单线程变慢后不明所以；原因是它是不同 ABI（cp314t），C 扩展 wheel 要单独提供，单线程还有 ~5-10% 回退；解法是按新 ABI 准备依赖，迁移前先压测。
- **以为无 GIL = 不用锁**：现象是无锁计数在 free-threading 下错得没有规律；原因是 GIL 从来只保护解释器不保护业务（竞态实验的透支演示），free-threading 下竞态面积更大而非更小；解法是所有共享可变状态加锁或改为消息传递。
- **`sys._is_gil_enabled()` 与 `Py_GIL_DISABLED` 混为一谈**：前者是运行时状态（free-threading 构建也可能被 PYTHON_GIL=1 打开），后者是构建期配置；两处都查才严谨。
- **用 stdin/管道方式跑多进程子命令**：现象是子进程报 `FileNotFoundError`；原因是 spawn 子进程 re-import `__main__` 时 `<stdin>` 无法定位（multiprocessing 的教训在本实验复现）；解法是一切以真实文件入口为准。

**Q1: 怎么判断一段代码在 free-threading 下是否安全？**
三问：共享了什么可变状态？读写之间有没有可能被切换（free-threading 下任意点都可能）？有没有锁/原子/不可变保护？竞态实验的读-改-写在 free-threading 下丢得更狠——用数据说话。

**Q2: 单线程性能为什么有回退？要不要现在迁移？**
移除 GIL 后引用计数与对象头需要额外同步，单线程回退 ~5-10%。策略：IO 密集且依赖阻塞库的先不动；CPU 密集且线程生态完善的服务可以先行，用基准实验（lab 14）的方法论量化迁移收益。

**Q3: 子解释器（PEP 734）与 free-threading 什么关系？**
两条并行的多核路线：子解释器在一个进程内隔离多套解释器状态（每套各有自己的模块空间，通信走显式通道）；free-threading 是全进程共享内存的真并行。前者隔离性好，后者共享方便——按隔离需求选择。
