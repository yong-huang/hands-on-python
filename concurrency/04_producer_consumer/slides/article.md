# 04 · 多线程生产者-消费者流水线：queue.Queue、毒丸与背压

> "共享状态 + 锁"能排险，但每个线程都要自己回答"什么时候安全碰数据"和"什么时候下班"。
> 这一篇换范式：**线程之间不共享，只递消息**——
> `queue.Queue` 把"共享容器 + 锁 + 等待通知"打包成一个原语（开箱即用的最小构件，锁与等待/通知已封装在内）。配套两个工程必需件：
> 下班靠**毒丸**（sentinel——一个真实任务永远不会撞上的标记对象，消费者取到即退出）而不是靠运气，过载靠**背压**（maxsize——队列写满后让上游阻塞的限流机制）而不是靠祈祷。

## Background

这节讲流水线范式从哪里来：没有队列之前，"共享状态 + 锁"的方案长什么样，它在哪几个问题上撞墙。

发现竞态（多个线程交叠读写同一份数据、结果取决于交错时序的缺陷）之后（见 [02_race_gil](../02_race_gil/README.md)
与 [03_sync_primitives](../03_sync_primitives/README.md)）。

标准做法是共享数据加锁：每个线程都直接读写同一份容器，靠 Lock 保证一次一个。

这条路能走通，但每个线程都要自己回答两个问题——
什么时候安全碰数据（锁的边界在哪）、什么时候下班（收尾信号谁发）。

两个问题都靠程序员自觉，撞墙方式很具体：锁的边界一漏就是竞态；收尾靠标志位约定，漏一个分支消费者就永远阻塞在取数据上；生产快于消费时共享 list 无界增长，内存被慢慢吃光。

并发领域由来已久的答案是消息传递：线程之间不共享数据，只递消息。Python 标准库把这套范式打包成一个类——`queue.Queue`，连同锁、等待通知、回执、限流一起内置。

## What

这节给出 `queue.Queue` 的定义、流水线的部件地图，以及"带回执的传送带"这个心智模型。

定义一句话：生产者-消费者是一种并发结构——一组线程（生产者）生成任务，
另一组线程（消费者）处理任务，中间用线程安全队列衔接。

`queue.Queue` 是带回执的传送带——**put 侧满了会被按住
（背压，backpressure——下游来不及消费时把压力反传给上游），
get 侧每取一件要交 task_done 回执（join 的依据），
下班要靠毒丸（sentinel——真实任务永远不会撞上的标记对象）逐个通知**。

本实验流水线从左到右的部件地图：

| 部件 | 职责 |
|---|---|
| 生产者 × 3 | 生成任务汇入传送带 |
| `queue.Queue(maxsize=10)` | 传递任务；满时按住生产者（背压） |
| 消费者 × 2 | `get()` → 处理 → `task_done()`；取到毒丸即退 |
| 计数 dict + Lock | 记账，锁保护更新 |
| main | 投毒丸、`q.join()` 收尾汇总 |

生产侧两个来源（任务、毒丸）汇入同一条传送带，消费者分不清也不需要区分——取到毒丸即退；右侧计数 dict 用锁保护更新，收尾由 main 汇总。

可以把 `queue.Queue` 想象成一条带回执的传送带：上游不停往上放，下游按自己的节奏取。但和真实传送带不同的是，它装满时会"按住"上游而不是让货物堆到地上，而且每件货都要下游签字回执——没有回执，收尾清点（`join()`）就永远数不完。

## When to Use

这节回答什么活儿值得搭流水线，什么时候换更简单的工具。

典型场景——在做什么事的时候：

- **把串行批处理拆成多步流水线时**：下载 → 解析 → 落盘，每步一组线程、一条队列衔接，快慢环节互不拖累（完整实例见 [15_downloader](../15_downloader/README.md)）
- **做任务分发器时**：生产侧发现任务（如爬虫收集 URL）、消费侧处理，两侧速率天然不同，队列吸收波动
- **上游可能过载时**：给队列设 `maxsize`，背压把压力反馈到源头，内存有界

何时不用：

- **简单的一发多收**：批量提交任务、收结果，`concurrent.futures` 更省事，不需要自己管理队列与毒丸
- **数据量小**：几百毫秒能跑完的脚本，收尾协议是多余的复杂度
- **要求结果严格按提交顺序产出时**：多消费者的完成顺序不定，需要有序就单消费者或自行重排

同类方案对比：

| 方案 | 与 `queue.Queue` 的差异 | 什么时候选它 |
|---|---|---|
| `collections.deque` | 无阻塞、无回执，纯数据结构 | 单线程内的先进先出 |
| `multiprocessing.Queue` | 跨进程版本 | 多进程流水线（见 [05_mp_accel](../05_mp_accel/README.md)） |
| `asyncio.Queue` | 事件循环（单线程内循环等待并派发任务的机制）版本 | 协程（可暂停/恢复的函数）流水线（见 [10_async_pipelines](../10_async_pipelines/README.md)） |
| `concurrent.futures` | 提交任务后凭 `Future`（事后收取结果的凭据）收结果，无队列语义 | 批量任务的一发多收 |

## Quick Start

这节把流水线跑起来。三个场景各给出一条确定性证据：不丢不重、背压钳住内存、不发毒丸的下场。

前置条件：只需 Python 3 标准库，无第三方依赖。

```bash
cd concurrency/04_producer_consumer
python3 producer_consumer.py      # 三个场景 + 全部断言，约 2 秒
```

真实输出（节选：省略首行解释器版本横幅与末尾"全部断言通过"汇总行）：

```
========================================================
[1. 流水线：3 生产者 × 2 消费者 × 1000 条任务]
========================================================
  处理总数 = 1000，每条恰好一次（计数 dict 全为 1）
  各生产者归属: {'p0': 334, 'p1': 333, 'p2': 333}
  毒丸发出后 0ms 内全部消费者退出（< 2s）
  注意 q.join() 数的是 task_done 回执：毒丸也必须 task_done，否则 join 永不返回

========================================================
[2. 背压：maxsize=10，快生产、慢消费（每件 3ms）]
========================================================
  采样 1498 次，队列长度峰值 = 10（= maxsize，生产者被按在门外）
  背压下依然 1000 条全部恰好处理一次 —— 丢任务与背压无关，与无锁共享有关

========================================================
[3. 反面教材：不发毒丸，消费者就永远等在 get() 上]
========================================================
  任务处理完、q.join() 也返回了，但消费者 Thread-12 (consume_forever) 还活着（阻塞在 get()）
  若它是非 daemon 线程，主进程退出时会被 threading._shutdown 无限等待
  一发毒丸让它干净退出 —— 收尾协议要从设计时就写进去，而不是等卡住了再补
```

诚实预期（本机 5 次实测）：

- **§1/§2 的"每条恰好一次"是确定性保证**——queue.Queue 的先进先出（FIFO）+ 内部锁，任何机器都不该出现丢失或重复
- **§2 峰值恰为 10**：快生产慢消费下队列必然顶满；若把消费改快，峰值会低于 10（断言也会如实告诉你）
- **§3 的消费者名是 Thread-12 之类**——它是前面场景累积的编号，无碍
- **毒丸退出耗时通常 0ms 量级**：消费者本就阻塞在 `get()`，毒丸一到立刻返回

`queue.Queue` 核心 API 速览：

| API | 行为 |
|---|---|
| `put(item)` | 入队；队列满（设了 `maxsize`）时阻塞 |
| `get()` | 出队；队列空时阻塞 |
| `task_done()` | 消费者交回执，给 `join()` 计数减一 |
| `join()` | 阻塞到回执数 = 入队数 |
| `qsize()` | 返回即刻过期的近似长度，只可观测、不可做业务判断 |

## How It Works

这节拆 `queue.Queue` 打包了什么、回执协议怎么计数、毒丸协议的三个细节，以及"队列安全 ≠ 全程安全"的原因。

**queue.Queue：打包好的"容器 + 锁 + 通知"。** 自己写生产者-消费者需要：
共享 list + Lock + Condition + 状态标志位。`queue.Queue` 全部内置：
`put()`/`get()` 内部持锁并阻塞同步，内部是 FIFO（先进先出）顺序，线程安全开箱即用。

它还有个隐藏身份——**背压阀门**：`maxsize=10` 时队列满，`put()` 自动阻塞，
生产速率被消费速率钳制，内存不再无界增长。

你在输出 §2 看到的"队列长度峰值 = 10（生产者被按在门外）"，
就是这个阀门工作的直接证据。

**task_done / join：回执协议。** 消费者每处理完一件必须调 `q.task_done()`；
主线程 `q.join()` 阻塞到**回执数 = 入队数**。这是"活干完了没有"的权威判据。

两个易断点：漏调 task_done → join 永不返回；
毒丸忘了 task_done → 同样卡死（本实验的毒丸在 `finally` 里交回执）。

输出 §1 的注释"毒丸也必须 task_done，否则 join 永不返回"说的就是第二个易断点。

**毒丸（sentinel）：受控关闭的标准协议。** 毒丸 = 一个所有真实任务都不可能撞上的
哨兵对象（`POISON = object()`）。生产结束后主线程投入**恰好每人一枚**毒丸；
消费者取到即退。

三个细节：数量必须等于消费者数（多发浪费、少发有人永远等）；
毒丸也要走 task_done（配合 join）；消费者用 `if item is POISON: return` 判定——
用 `is` 不用 `==`，身份比较不触发任何业务比较逻辑。

你在输出 §1 看到的"毒丸发出后 0ms 内全部消费者退出"，
是因为消费者本就阻塞在 `get()` 上，毒丸一到立刻返回。

**反面教材：知道"不收尾"长什么样。** 不发毒丸的消费者：任务处理完、`q.join()` 返回，
它仍阻塞在 `get()` 上。

若它是非 daemon（daemon——进程退出时不等待的后台线程）线程，
主进程退出时会被 `threading._shutdown` 无限等待——**进程退不出去，且没有任何报错**。

输出 §3 里"还活着的 Thread-12"就是这一幕。

本实验开发过程中就真实踩中：演示线程忘设 daemon，脚本挂了 120 秒，最终改写为"先展示卡死、再毒丸救援"的完整弧线。收尾协议要从设计时就写进去，而不是等卡住了再补。

**为什么计数要用 dict + 锁，而不是 collections.Counter 裸用？**

```python
with counter_lock:
    results[item] = results.get(item, 0) + 1
```

`results.get(...) + 1` 的读-改-写隔着调用边界（竞态实验的经典形状），queue.Queue 只保证队列自身安全，**管不着你拿到任务之后怎么记账**。"队列安全 ≠ 全程安全"是流水线方案最常见的误读——消息传递缩小了共享面，但没有消灭它。

## Pitfalls & Q&A

这节收录开发过程中真实踩过的坑（现象 + 原因 + 解法）与常见疑问。

踩坑清单：

- **`1000 // 3` 整除丢任务**：现象是总量 999、计数断言当场揭穿。原因是三个生产者各分 333 条，整除丢了余数。解法：分片必须 `divmod` 处理余数
- **毒丸数量 ≠ 消费者数**：现象是少一枚就有一个消费者永远等，多一枚则毒丸留在队列里（无害但脏）。原因是毒丸按消费者人头投递。解法：数量从消费者列表长度取，不要手写数字
- **在消费者里吞异常却不 task_done**：现象是 join 永远等不到回执。原因是异常路径绕过了回执。解法：task_done 放 `finally`
- **用 `q.qsize()` 做业务判断**：现象是判断结果时对时错。原因是返回值即刻过期（文档明示）。解法：采样观测可以，条件判断不行
- **拿 `list` 当队列 + `append/pop`**：现象是队头取出越来越慢、争用面更大。原因是 `pop(0)` 是 O(n) 且与 append 的争用面更大。解法：用 `collections.deque` 或直接 `queue.Queue`

深入问答：

**Q1: queue.Queue 和 list+Lock 比好在哪？**
Queue 内置阻塞语义（空则等、满则停）和条件通知，list+Lock 要自己用 Condition 拼；
Queue 还是 FIFO + 回执协议（task_done/join）+ 背压（maxsize）的现成实现。

性能上 deque 更快，论工程语义选 Queue。

**Q2: maxsize 背压解决什么问题？代价是什么？**
解决"生产快于消费"时的无界内存增长和上游过载。代价是上游被拉慢（put 阻塞）——这正是期望行为：把压力反馈到源头。吞吐由最慢一环决定（本实验慢消费者 3ms/件 → 总吞吐 ≈ 330 件/秒）。

**Q3: q.join() 和 Thread.join() 的区别？**
`q.join()` 等队列里所有项目的 task_done 回执齐了（计数归零），与线程生命周期无关；`Thread.join()` 等线程函数返回。流水线收尾两者都用：先 q.join() 确认活干完，再发毒丸让消费者线程退出。

**Q4: 消费者抛异常会怎样？怎么兜底？**
异常沿消费者线程栈顶终结该线程，队列里未取任务无人处理，join 卡死。

兜底：get 循环内 try/except（异常任务进死信队列——存放无法处理任务的兜底队列），
task_done 放 finally 保证回执必达——
参考 [13_concurrency_patterns](../13_concurrency_patterns/README.md) 的退避重试。
