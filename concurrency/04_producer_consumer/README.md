# 04 · 多线程生产者-消费者流水线：queue.Queue、毒丸与背压

> "共享状态 + 锁"能排险，但每个线程都要自己回答"什么时候安全碰数据"和"什么时候下班"。
> 这一篇换范式：**线程之间不共享，只递消息**——
> `queue.Queue` 把"共享容器 + 锁 + 等待通知"打包成一个原语。配套两个工程必需件：
> 下班靠**毒丸**（sentinel）而不是靠运气，过载靠**背压**（maxsize）而不是靠祈祷。

## What

`queue.Queue` 是带回执的传送带——**put 侧满了会被按住（背压），get 侧每取一件要交 task_done 回执（join 的依据），下班要靠毒丸（sentinel）逐个通知**。从左到右看流水线：生产侧两个来源（任务、毒丸）汇入同一条传送带，消费者分不清也不需要区分——取到毒丸即退；右侧计数 dict 用锁保护更新，收尾由 main 汇总。

## Why

裸锁方案里每个线程都要自己回答"什么时候安全碰数据"和"什么时候下班"；流水线方案里这两个问题分别被 `queue.Queue` 和毒丸协议接管。这是并发架构从"共享内存"走向"消息传递"的第一步——也是后面 asyncio 队列（[10_async_pipelines](../10_async_pipelines/README.md)）、并发下载器（[15_downloader](../15_downloader/README.md)）的基本骨架。本实验用 1000 条任务的流水线给出三条确定性证据：不丢不重、背压钳住内存、毒丸 2 秒收队。

```
  处理总数 = 1000，每条恰好一次（计数 dict 全为 1）

========================================================

  背压下依然 1000 条全部恰好处理一次 —— 丢任务与背压无关，与无锁共享有关

  若它是非 daemon 线程，主进程退出时会被 threading._shutdown 无限等待
  一发毒丸让它干净退出 —— 收尾协议要从设计时就写进去，而不是等卡住了再补
```

诚实预期（本机 5 次实测）：

- **§1/§2 的"每条恰好一次"是确定性保证**——queue.Queue 的 FIFO + 内部锁，任何机器都不该出现丢失或重复
- **§2 峰值恰为 10**：快生产慢消费下队列必然顶满；若把消费改快，峰值会低于 10（断言也会如实告诉你）
- **§3 的消费者名是 Thread-12 之类**——它是前面场景累积的编号，无碍
- **毒丸退出耗时通常 0ms 量级**：消费者本就阻塞在 `get()`，毒丸一到立刻返回

### queue.Queue：打包好的"容器 + 锁 + 通知"

自己写生产者-消费者需要：共享 list + Lock + Condition + 状态标志位。`queue.Queue` 全部内置：`put()`/`get()` 内部持锁并阻塞同步，线程安全开箱即用。它还有个隐藏身份——**背压阀门**：`maxsize=10` 时队列满，`put()` 自动阻塞，生产速率被消费速率钳制，内存不再无界增长。

### task_done / join：回执协议

消费者每处理完一件必须调 `q.task_done()`；主线程 `q.join()` 阻塞到**回执数 = 入队数**。这是"活干完了没有"的权威判据。两个易断点：漏调 task_done → join 永不返回；毒丸忘了 task_done → 同样卡死（本实验的毒丸在 `finally` 里交回执）。

### 毒丸（sentinel）：优雅关闭的标准协议

毒丸 = 一个所有真实任务都不可能撞上的哨兵对象（`POISON = object()`）。生产结束后主线程投入**恰好每人一枚**毒丸；消费者取到即退。三个细节：数量必须等于消费者数（多发浪费、少发有人永远等）；毒丸也要走 task_done（配合 join）；消费者用 `if item is POISON: return` 判定——用 `is` 不用 `==`，身份比较不触发任何业务比较逻辑。

### 反面教材的价值：知道"不收尾"长什么样

不发毒丸的消费者：任务处理完、`q.join()` 返回，它仍阻塞在 `get()` 上。若它是非 daemon 线程，主进程退出时会被 `threading._shutdown` 无限等待——**进程退不出去，且没有任何报错**。本实验开发过程中就真实踩中：演示线程忘设 daemon，脚本挂了 120 秒，最终改写为"先展示卡死、再毒丸救援"的完整弧线。

## Deep Dive

**为什么计数要用 dict + 锁，而不是 collections.Counter 裸用？**

```python
with counter_lock:
    results[item] = results.get(item, 0) + 1
```

`results.get(...) + 1` 的读-改-写隔着调用边界（竞态实验的经典形状），queue.Queue 只保证队列自身安全，**管不着你拿到任务之后怎么记账**。"队列安全 ≠ 全程安全"是流水线方案最常见的误读——消息传递缩小了共享面，但没有消灭它。

踩坑清单：

- **`1000 // 3` 整除丢任务**：第一版三个生产者各分 333 条，总量 999——计数断言当场揭穿。分片必须 `divmod` 处理余数
- **毒丸数量 ≠ 消费者数**：少一枚，一个消费者永远等；多一枚，会留在队列里（无害但脏）
- **在消费者里吞异常却不 task_done**：join 永远等不到回执——task_done 放 `finally`
- **用 `q.qsize()` 做业务判断**：返回值即刻过期（文档明示），采样观测可以，条件判断不行
- **拿 `list` 当队列 + `append/pop`**：pop(0) 是 O(n) 且与 append 的争用面更大——`collections.deque` 或直接 Queue

## Q&A

**Q1: queue.Queue 和 list+Lock 比好在哪？**
Queue 内置阻塞语义（空则等、满则停）和条件通知，list+Lock 要自己用 Condition 拼；Queue 还是 FIFO + 回执协议（task_done/join）+ 背压（maxsize）的现成实现。性能上 deque 更快，但工程语义 Queue 完胜。

**Q2: maxsize 背压解决什么问题？代价是什么？**
解决"生产快于消费"时的无界内存增长和上游过载。代价是上游被拉慢（put 阻塞）——这正是期望行为：把压力反馈到源头。吞吐由最慢一环决定（本实验慢消费者 3ms/件 → 总吞吐 ≈ 330 件/秒）。

**Q3: q.join() 和 Thread.join() 的区别？**
`q.join()` 等队列里所有项目的 task_done 回执齐了（计数归零），与线程生命周期无关；`Thread.join()` 等线程函数返回。流水线收尾两者都用：先 q.join() 确认活干完，再发毒丸让消费者线程退出。

**Q4: 消费者抛异常会怎样？怎么兜底？**
异常沿消费者线程栈顶终结该线程，队列里未取任务无人处理，join 卡死。兜底：get 循环内 try/except（异常任务进死信队列），task_done 放 finally 保证回执必达——参考 [13_concurrency_patterns](../13_concurrency_patterns/README.md) 的退避重试。
