# 01 · 线程生命周期观察器：看得见线程的一生

> 线程的 API 五分钟就能学会，但有三个行为不亲眼看过就一定会踩坑：**交错顺序不可复现**
> （"这个 bug 我怎么测不出来"）、**`run()` 不开线程**（"我启动的线程怎么还在主线程里跑"）、
> **daemon 说死就死**（daemon 即后台守护线程——进程退出时不等待它收尾的线程；"关机钩子怎么没执行"）。
> 本实验把线程对象当成一个状态机（内部状态随固定事件转移的对象）来观察，一次看全这三个行为。

## Background

这节讲线程从哪里来：在它出现之前，人们怎么让一个程序同时推进多件事，那个老办法在哪里撞墙。

没有并发（让程序在同一时间段内推进多件事）手段时，程序从上到下顺序执行，同一时刻只做一件事。遇到网络请求、文件读写这类要"干等"的 I/O（输入/输出）操作，CPU 只能空转——发 10 个请求就得串行等 10 轮。操作系统给出的传统解法是多进程：每个任务一个独立进程，互不干扰。

多进程在"任务之间要共享数据"的场景撞墙：每个进程拥有独立的内存地址空间，共享一个计数器、一份队列都得走进程间通信（IPC，专门用于跨进程交换数据的机制），创建和切换的开销也更大。

线程因此应运而生——由操作系统提供的轻量执行流，同一进程内的多个线程共享同一份内存，
数据天然可达，创建开销更小。但代价随之而来：执行顺序由操作系统的调度器
（决定哪个线程何时上 CPU 运行的系统组件）掌控，程序无法干预。

例如用 10 个线程同时发 10 个网络请求，10 段等待时间相互重叠，总耗时接近最慢的一个——但哪个线程先执行完，程序无法指定。

先后不可复现、共享数据被交叠修改，成了并发代码特有的正确性问题。
本实验把线程对象从创建到销毁的完整行为摆到眼前，把这些"看不见"变成"看得见"。

## What

这节给出 `threading.Thread` 的定义与心智模型，并预告三个必须亲眼见过的运行时事实。

`threading.Thread` 是 Python 标准库里最底层的线程接口——直接对应操作系统线程的类，
更上层的线程池（预先创建一批可复用线程的并发封装）也以它为地基。

一句话心智模型：**Thread 对象是 `start()` 驱动的单次状态机——
NEW → RUNNABLE → TERMINATED 走完即报废；
daemon 属性不改变走法，只改变"进程退出时要不要等它"**。

可以把 Thread 对象想象成一枚烟花：构造出来只是个摆设，`start()` 是点火，烧完（TERMINATED）即报废，想再放只能换新的。但和烟花不同的是，线程可能在燃放途中被"散场"直接掐灭——如果它是 daemon（后台守护线程，进程退出时不等待它收尾）。

三个状态的转移关系（`is_alive()` 的返回值是旁证）：

| 状态 | `is_alive()` | 如何进入 |
|---|---|---|
| NEW | `False` | `Thread(...)` 构造完成，尚未 `start()` |
| RUNNABLE | `True` | 调用 `start()`，线程就绪 |
| TERMINATED | `False` | `run()` 执行完毕返回 |

三个必须亲眼见过才算懂的运行时事实，本篇会逐一用演示验证：

- **交错顺序不可复现**：线程之间的执行顺序由调度器决定，程序无法控制也无法复现
- **`run()` 不开线程**：直接调用 `run()` 只是普通方法调用，线程根本没有创建
- **daemon 说死就死**：daemon 线程的生死挂在主线程上，主线程一退它就被强杀，收尾代码可能执行到一半

## When to Use

这节回答"在做什么事的时候值得直接用 `threading.Thread`"，以及什么时候应该换更简单的工具。

典型场景：

- **需要同时发多个网络请求时**：一个请求一个线程，慢请求的等待时间与其他请求重叠，总耗时接近最慢的那个而不是全部相加
- **需要给服务挂一个常驻后台循环时**：心跳、监控打点、缓存刷新这类"死了无所谓"的辅助任务适合交给 daemon 线程（强杀机制见 How It Works）
- **需要把生产与消费两侧解耦时**：配合 `queue.Queue` 搭建流水线原型，完整模式见 [04_producer_consumer](../04_producer_consumer/README.md)

何时不用：

- **CPU 密集型计算**：受 GIL（全局解释器锁——CPython（Python 的官方参考解释器实现）解释器中同一时刻只允许一个线程执行字节码的锁；字节码是解释器实际执行的中间指令）限制，多线程无法并行执行纯计算，应改用多进程
- **任务量小、串行足够快**：线程的创建、调度与同步都是复杂度成本，几十毫秒就能跑完的顺序代码不值得引入并发

同类方案对比：

| 方案 | 与 `threading.Thread` 的差异 | 什么时候选它 |
|---|---|---|
| `multiprocessing` | 每个任务一个独立进程，绕开 GIL，内存不共享 | CPU 密集型并行计算 |
| `concurrent.futures.ThreadPoolExecutor` | 线程池封装，复用线程、以 `Future`（代表“任务还没出结果”的凭据，任务完成后凭它取回结果）收取结果 | 大量短命任务的批量并发 |
| `asyncio` | 单线程事件循环（在一个线程里循环等待、派发任务的运行机制）+ 协程（可暂停/恢复的函数），单线程内挂起大量任务 | 高并发 I/O 且依赖库支持异步 |

## Quick Start

这节把实验跑起来：运行命令、真实输出、诚实预期，以及一段可逐行执行的状态机演示。

前置条件：只需 Python 3 标准库，无第三方依赖。

```bash
cd concurrency/01_thread_lifecycle
python3 thread_lifecycle.py           # 完整演示（4 个小节，内置验收断言）
python3 thread_lifecycle.py --daemon  # 只跑 daemon 截断演示（验收点 2）
```

真实输出节选（§4 完整输出见脚本，约 25 行逐条打印的过程性输出略）：

```
========================================================
[2. start() vs run()]
========================================================
t.run()          → 函数体执行了，但线程是 MainThread（没有新线程！）
t.start()        → 函数体跑在新线程 born-by-start 里
对已启动的线程再次 start() → RuntimeError: threads can only be started once

========================================================
[3. 交错执行观察（4 线程 × 3 tick，共 3 批）]
========================================================
  批次 0: W1#t0 W3#t0 W2#t0 W1#t1 W0#t0 W2#t1 W1#t2 W3#t1 W2#t2 W0#t1 W3#t2 W0#t2
  批次 1: W0#t0 W3#t0 W2#t0 W1#t0 W2#t1 W0#t1 W1#t1 W3#t1 W0#t2 W2#t2 W1#t2 W3#t2
  批次 2: W3#t0 W1#t0 W2#t0 W0#t0 W1#t1 W2#t1 W3#t1 W0#t1 W3#t2 W0#t2 W2#t2 W1#t2

  3 批出现了 3 种不同的排列 → 线程间顺序不可预测
  但每个线程自己内部的 t0→t1→t2 永远有序 → 无序只发生在线程之间
```

`--daemon` 模式（真实输出节选：省略开头版本横幅、小节标题与"主线程：睡 0.3s 后退出，不 join"说明行）：

```
  daemon 输出 # 1/20
  daemon 输出 # 2/20
  daemon 输出 # 3/20
  daemon 输出 # 4/20
  daemon 输出 # 5/20

  主线程退出！daemon 只来得及打 5/20 条，剩余输出被丢弃
  （验证：本行之后不会有任何 daemon 输出；exit code = 0）
```

诚实预期（本机 5 次实测）：

- **三批的交错排列每次运行都不同**：本机 5 次全部出现 3 种互不相同的排列（断言只要求 ≥2）；你跑出来的具体序列一定和上面不一样——这正是不确定性本身
- **daemon 截断点本机稳定在 5/20 条附近**：主线程只睡 0.3s、每条间隔 0.05s，理论 ≈6 条，调度抖动让它少 1 条；换机器/负载会浮动，但"远小于 20"是稳定的
- **`t.run()` 演示用的是独立线程对象**：手动 `run()` 会消耗掉 `_target`，同一个对象之后再 `start()`，新线程会直接 `AttributeError`（见踩坑清单第 1 条）

下面的演示代码可以逐行执行，观察状态转移：

```python
worker = threading.Thread(target=time.sleep, args=(0.4,), name="worker-A")
worker.is_alive()        # False —— NEW：创建了但没 start
worker.start()
worker.is_alive()        # True  —— RUNNABLE：是否真在跑由 OS/GIL 决定
worker.join()
worker.is_alive()        # False —— TERMINATED：run() 已返回
worker.join()            # 合法且立即返回：对死线程 join 就是"不用等"
```

这段在做什么：构造一个未启动的线程（NEW），`start()` 后进入 RUNNABLE，
`join()` 等它跑完进入 TERMINATED；第二次 `join()` 立即返回，
说明"等待已死的线程"是合法操作。

`threading.enumerate()` 是存活性旁证：RUNNABLE 阶段能看到 `worker-A`，
TERMINATED 后从列表消失。

本实验用到的 `threading` API 速览：

| API | 作用 |
|---|---|
| `Thread(target=, name=, daemon=)` | 创建线程对象，`target` 是新线程要执行的函数 |
| `start()` | 请 OS 创建真实线程并开始执行 |
| `join(timeout=)` | 阻塞调用者，等目标线程终止 |
| `is_alive()` | 是否处于 RUNNABLE 状态 |
| `threading.enumerate()` | 列出当前所有存活线程 |

## How It Works

这节拆开输出背后的机制：`start()` 与 `run()` 的分野、`join()` 的真实语义、daemon 的强杀规则，以及演示为什么用 `events` 列表采集证据。

**`start()` 与 `run()`：一字之差，天壤之别**。`start()` 做两件事：请 OS 创建真正的线程，再在新线程里回调 `run()`。直接调用 `t.run()` 则只是当前线程里的普通方法调用——target 里的代码会执行，但执行者是调用者。

你在输出里看到的 `t.run() → 函数体执行了，但线程是 MainThread（没有新线程！）`，就来自这里。线程也只能启动一次：第二次 `start()` 抛 `RuntimeError: threads can only be started once`，想要"重跑"只能新建 Thread 对象。

**`join()` 的真实语义**：`join()` 是调用者的等待动作，不是对目标线程的操作——它阻塞调用者，直到目标线程 TERMINATED。推论有两个：对已死的线程 `join()` 立即返回；`join(timeout=)` 超时后目标线程还活着时不会被杀，只是调用者不等了。

主函数 `return` 时，解释器会自动对全部非 daemon 线程做一次隐式 join（`threading._shutdown`），所以普通线程"漏 join"不会丢结果，只是失去明确的汇合点。

**daemon：把生死挂在主线程上**。`daemon=True` 必须在 `start()` 之前设置。daemon 线程不改变状态机走法，唯一区别是主线程退出（准确说：全部非 daemon 线程结束）时它被立即强杀——没有清理机会，写到一半的文件就停在半个字节上。

你在 `--daemon` 输出里看到的"只来得及打 5/20 条"，就是强杀的直接结果。适用边界因此清晰：心跳、监控打点、缓存刷新这类"死了无所谓"的后台循环适合它；任何带落盘（写入磁盘）语义的收尾工作都不适合。

**"RUNNABLE"不等于"正在 CPU 上跑"**。单核 GIL 下同一时刻只有一个线程在执行字节码，
其余线程在等锁、等 I/O 或等时间片（操作系统分给每个线程的一小段 CPU 使用权，见 [02_race_gil](../02_race_gil/README.md)）。

`is_alive()` 返回 `True` 只说明线程处于 RUNNABLE，不代表它此刻在计算。

**为什么用 `events.append()` 记录顺序，而不是看 print 输出顺序？**

```python
events: list[str] = []
def worker(idx: int) -> None:
    for tick in range(ticks):
        time.sleep(0.01 + random.uniform(0, 0.03))  # 抖动制造真实交错
        events.append(f"W{idx}#t{tick}")
```

`list.append` 在 GIL 下是单字节码的原子操作（原子操作——不会被线程切换打断的执行单元），跨线程收集事件不会乱序也不会丢；而 `print` 跨线程输出可能被撕裂、受行缓冲（程序攒满一行才把内容真正交给终端输出的缓冲方式）影响，用打印顺序当证据会被 stdout 骗。

断言也设计成两层：批次间 `len({tuple(o) for o in orders}) >= 2` 证明**线程间**不可复现，批次内每个线程自己的 tick 位置严格递增证明**线程内**永远有序——把"无序"精确圈定在线程之间。

## Pitfalls & Q&A

这节收录真实踩过的坑（现象 + 原因 + 解法）与常见疑问。

踩坑清单：

- **手动 `t.run()` 之后对同一个对象 `t.start()`**：现象是新线程一启动就 `AttributeError`。原因是 `run()` 的 `finally` 会删掉 `_target/_args/_kwargs`（CPython 3.13 实测），之后 `start()` 出来的新线程找不到 target。解法：要么只 `start()`，要么给 `run()` 单独一个对象——本实验第一版就真实踩中
- **用 `print` 顺序给多线程行为当证据**：现象是输出的先后对不上真实执行顺序。原因是行缓冲 + 输出撕裂，两头的顺序都不可信。解法：跨线程收集数据用 `queue.Queue`（见 [04_producer_consumer](../04_producer_consumer/README.md)）或原子 `append`
- **在 daemon 线程里做落盘/提交事务**：现象是数据只写到一半进程就退出了。原因是强杀不等待、不通知，半截数据比没数据更糟。解法：需要可靠收尾就用普通线程 + `join()`，或显式发停止信号
- **daemon 设置晚了**：现象是 `start()` 之后再设 `daemon=True` 抛 `RuntimeError`。原因是状态机已经离开 NEW，属性冻结。解法：在 `start()` 之前设置，或直接用构造参数 `Thread(target=..., daemon=True)`

深入问答：

**Q1: `start()` 和 `run()` 的区别？**
机制拆解见 How It Works 开头两段，一句话版本：`start()` 创建真实线程，`run()` 只是当前线程里的普通方法调用。

**Q2: 两个线程同时对 `list` 做 `append` 会坏吗？同时对 `counter += 1` 呢？**
`append` 不会：它是单字节码原子操作，GIL 保证不被打断。

`counter += 1` 会丢更新：它拆成 LOAD/ADD/STORE 多步，线程可在中间被切换——
这是竞态的最小样本，[02_race_gil](../02_race_gil/README.md)
会实测丢失率并用 `dis` 展示字节码。
