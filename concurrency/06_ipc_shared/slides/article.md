# 06 · 进程间通信与共享状态：Pipe / Queue / SharedMemory / Manager

> 进程有独立内存：多进程绕开 GIL（全局解释器锁）拿到真并行，也拆掉了共享内存——谁也改不到谁手里的变量。
> 标准库为此提供四条 IPC（进程间通信）通道，性格各异：Pipe 会聊天、Queue 能吞吐、SharedMemory 不拷贝、
> Manager 什么都能代理但每次都是远程调用。本实验用 10 万条消息、50MB 大数组和 1 万次并发更新，
> 把四条路的性能与纪律一次量清：SharedMemory 比 pickle（Python 对象序列化机制）+Pipe 快 18.5×，Manager 无锁共享 1 万次更新丢 6,404 次。

## Background

这节讲三件事：线程时代共享状态为什么"免费"、多进程时代这个前提如何崩塌、进程间通信设施如何补位。

线程模型里，所有线程共享同一个进程的内存，一个全局计数器所有线程都能直接读写——共享状态是"免费"的。顺着这条思路用多进程时，第一个撞墙点立刻出现：子进程里改一个"全局变量"，改的是自己那份副本，父进程永远看不见。

想让进程协作的常用场景——一个生产数据、一个消费数据，或四个进程共改同一份统计表——在内存隔离下全部失效：互相看不见变量，只能把数据序列化成字节流来回搬运，大对象搬一次就是几百毫秒；硬扛着不通信，就退回单进程，并行白做。

进程间通信（IPC，Inter-Process Communication）不是 Python 的新发明——操作系统早就提供管道、共享内存这类设施。

标准库 `multiprocessing` 把这些设施包装成 Python 对象，给出四条通道：Pipe（点对点对话）、Queue（多对多队列）、SharedMemory（共享内存块）、Manager（共享对象的代理）。通道各有实现路线，代价与纪律必须亲手量过才知道——这正是本实验做的事。

## What

这节给出四条 IPC 通道的定义与心智模型：三条实现路线、一条性能排序、一条纪律排序。

`multiprocessing` 提供的四条通道，是四条实现路线不同的进程间数据通路：

**Pipe/Queue 走"序列化 + 管道"（每字节都要拷贝），SharedMemory 走"同一块物理内存"（零拷贝直读），Manager 走"代理 + RPC"（远程过程调用，这里指把属性访问转发给另一个进程执行；每次访问一个来回）**。

| 通道 | 走的路 | 一句话特点 |
|---|---|---|
| Pipe / Queue | 序列化 + 管道 | 每字节都要拷贝 |
| SharedMemory | 同一块物理内存 | 零拷贝直读 |
| Manager | 代理 + RPC | 每次访问一个来回 |

性能排序即实现排序：零拷贝 > 管道 > RPC。纪律排序相反——Manager 的 dict 最像普通 dict，也最容易让人忘记 get 与 set 之间隔着两次网络式调用。

可以把四个进程想象成四间互相隔音的办公室：互传纸条（Pipe/Queue，内容要先抄写一遍）、共用一块白板（SharedMemory，大家看同一块板面）、雇一位秘书代为跑腿（Manager，每次吩咐都是一趟来回）。

但和办公室不同的是：白板不会阻止两人同时擦写同一格——同步要自己解决；纸条抄写大图纸很慢——大块数据走纸条通道代价按字节计。

## When to Use

这节讲每条通道各自适配的工作形态、什么时候根本不需要通道，以及选型对照。

- **流水线协作**：一个进程持续产出、其他进程持续消费——批量任务分发与结果回收交给 Queue。
- **点对点对话**：父子两进程一来一回的指令与回执——Pipe 最轻。
- **共享大块数据**：50MB 级大数组、帧数据、numpy 缓冲要被多个进程读取——SharedMemory 零拷贝直读。
- **共享结构化状态**：多个进程像改本地对象一样共改一份 dict/list——Manager 加锁，但要接受每次访问一次 RPC 的代价。

何时不用：

- 任务只是"发一次、收一次"：直接用进程池的返回值带回来（见 [05_mp_accel](../05_mp_accel/README.md)），不需要常驻通道。
- 大块数据只读、进程是一次性的：在 fork（复制父进程内存来创建子进程的启动方式，与 spawn 相对）之前把数据放进模块级变量，子进程拿到写时拷贝（只有真正写入时才复制对应内存页）的副本，零通信成本（机制详见 Q3）。
- 单进程或线程就够用的规模：通道的通信成本只在真并行的收益面前才划算。

选型决策表：

| 需求 | 通道 | 一句话理由 |
|:---|:---|:---|
| 父子两进程对话 | Pipe | 双工、轻量、点对点 |
| 批量任务分发/结果回收 | Queue | 多对多、FIFO（先进先出）、可背压（下游处理不动时能反向限流） |
| 大数组/帧数据共享 | SharedMemory | 零拷贝，比序列化快一个量级 |
| 想要"进程级共享 dict" | Manager + Lock | 最顺手，但每次访问都是 RPC，必须配锁 |

## Quick Start

实验只依赖标准库，无需安装第三方包，完整脚本在实验目录的 `ipc_shared.py`。

```bash
cd concurrency/06_ipc_shared
python3 ipc_shared.py      # 四个实测小节 + 全部断言，约 3 秒
```

这段命令在做什么：脚本依次实测 Pipe 双向对话、Queue 十万条消息批量传递、50MB 大数组在两条通道下的传输对比、Manager 加锁与不加锁的并发更新，最后运行全部断言。

真实输出（节选）：

```
========================================================
[2. Queue：100,000 条消息批量传递]
========================================================
  100,000 条分毫不差，耗时 0.39s（≈256,866 条/秒，含 pickle 开销）

========================================================
[3. SharedMemory vs pickle+Pipe：50MB 大数组]
========================================================
  SharedMemory 子进程侧: 20ms（零拷贝直读，父端写 21ms 全程）
  pickle+Pipe  子进程侧: 366ms（序列化+管道+反序列化）
  子进程侧加速 18.5×，两边 CRC32 一致（50MB 数据完好）

========================================================
[4. Manager：4 进程 × 2,500 次并发更新同一 key]
========================================================
  无锁:   最终 count = 3,596（丢失 6,404 次，RPC 窗口被穿插）
  加锁:   最终 count = 10,000（10,000 次分毫不差）
  Manager 的每次属性访问都是一次 RPC——慢，但让'进程级共享对象'成为可能
```

诚实预期（本机 3 次实测）：

- **SharedMemory 加速比 18~30× 波动**：pickle+Pipe 一侧受管道缓冲与调度影响大，断言只锁 ≥5×
- **Manager 无锁丢失率 60%+**：每次 `d["k"] = d["k"] + 1` 是两次 RPC，窗口大到必然被穿插——丢失是常态不是偶发
- **§1/§2 全零失败**：Pipe 双向与 Queue 批量是确定性协议，任何环境都该 100% 通过

写自己的多进程程序时，常用到这几个入口：

| API | 作用 | 一句话备注 |
|---|---|---|
| `Pipe()` | 双端双工（两端都能收发）的点对点通道 | `send`/`recv` 走 pickle |
| `Queue()` | 多生产者多消费者 FIFO | 内部是"Pipe + 锁 + 喂食线程（见 How It Works）" |
| `SharedMemory(size=n)` | 映射一块跨进程共享的物理内存 | 生命周期手动管理 |
| `Manager().dict()` / `.Lock()` | 返回跨进程共享对象的代理 | 每次属性访问都是一次 RPC |

## How It Works

这节把输出里的三段现象对应到三条实现路线，并补上实验里两个基准测试方法论。

### Pipe 与 Queue：序列化管道的两副面孔

`Pipe()` 是双端双工的点对点通道，`send/recv` 走 pickle；`Queue` 是多生产者多消费者的 FIFO，内部是"Pipe + 锁 + 喂食线程（后台辅助线程，把 put 放入的对象搬运到底层 Pipe，让 put 尽快返回）"。

共同纪律：**传的都是 pickle 副本**——改副本不影响原件，大对象的序列化成本按字节计费。

你在输出 [2] 里看到的"≈256,866 条/秒，含 pickle 开销"，开销就来自"每条消息都要序列化 + 管道拷贝"这条路线。

### SharedMemory：唯一的零拷贝通道

`SharedMemory(size=n)` 在两个进程间映射同一块物理内存：父进程写 `shm.buf[:]=data` 是一次 memcpy（内存块的直接复制），子进程 `bytes(shm.buf)` 是另一次 memcpy——**没有序列化、没有管道、没有第三份拷贝**。适用：大数组、帧数据、numpy 缓冲。

纪律有两条：生命周期手动管理（`close()` + `unlink()`，忘 unlink 文件块泄漏到 /dev/shm——基于内存的共享文件系统）；同步靠自己上锁，它只共享内存，不共享原子性（操作不被穿插打断的性质）。

输出 [3] 的 20ms 对 366ms、18.5× 加速，就是"零拷贝直读"对"序列化+管道+反序列化"的直接结果；"两边 CRC32 一致"证明 50MB 数据在零拷贝通路上完好。

### Manager：最方便也最贵

`Manager().dict()` 返回一个代理对象——所有属性访问被转发到一个独立的服务进程执行，再带结果回来。它让"进程级共享 dict/list/Lock"像本地对象一样好写。

但代价真实存在：每次 `d["k"]` 都是两个 RPC 往返，且 `d["k"] += 1` 的读与写是**两次独立 RPC**——窗口大开，实测 1 万次丢 6404 次。修复与线程版一模一样：Manager 自带的 `Lock()` 包住读改写，立刻分毫不差。

输出 [4] 的"无锁 3,596 / 加锁 10,000"就是同一份代码去掉与加上那把锁的对照。

### 基准方法一：校验和探针必须比被测物便宜

为什么 §3 的校验和用 `zlib.crc32` 而不是 `sum(bytes)`？第一版用 `sum(50MB bytes)` 当校验和——5000 万次 Python 迭代要 2 秒以上，两条通道各付一遍，把传输差异完全淹没（实测加速比掉到 1.2×）。

换成 `zlib.crc32`（C 实现的快速校验和，毫秒级）后差异立刻显形。**基准测试的探针必须比被测物便宜**，否则测的是探针。

### 基准方法二：把对称成本从计时里剥掉

为什么子进程要预先 spawn、用 Event（跨进程的开关标志）发车？spawn 一个子进程要 0.3~0.5s，若计入传输耗时，两条通道各付一遍（对称成本），加速比同样被稀释。

子进程先启动、挂载好 SharedMemory、停在 `go_evt.wait()`，父进程发车后只测纯传输——**把对称成本从计时里剥掉，差异才可见**。

## Pitfalls & Q&A

这节收集五个常见坑（现象 + 原因 + 解法）和四个延伸问答。

### 踩坑清单

- **忘了 `shm.unlink()`**：现象是共享内存块在系统里泄漏，重启才清。原因：`close()` 只断开映射不删除。解法：用完显式 `unlink()` 删除。
- **用完的一端不 close**：现象是对端等待数据结束信号永远等不到。原因：Pipe 的对端会以为还有写者，EOF（End of File，数据流结束信号）永远不来。解法：用完的一端显式 `close()`。
- **Manager 代理当本地对象用**：现象是遍历大 dict 慢成灾难。原因：`for k in d:` 每次迭代一个 RPC。解法：先 `d.copy()`（一次 RPC 拷回）再遍历。
- **在 `shm.buf` 上留引用**：现象是 `unlink` 后读到悬空内存、数据错乱。原因：`bytes(shm.buf)` 是拷贝、`shm.buf` 是视图——视图在 unlink 后是悬空内存。解法：要留存数据，先拷成 `bytes`。
- **以为 Queue 传过去的是原对象**：现象是改"传过去"的对象，原件纹丝不动。原因：全是 pickle 副本，改副本不影响原件。解法：要"真共享"用 SharedMemory 或 Manager。

### 深入问答

**Q1: Pipe 和 Queue 怎么选？**

Pipe 双端双工、更轻，适合两点对话；Queue 多生产者多消费者安全（内部有锁），适合任务分发。Queue 的 get 支持超时与毒丸协议（poison pill——投入一个约定好的特殊消息，消费者收到即退出），Pipe 需要自己设计消息边界。

**Q2: Manager 的 dict 为什么会丢更新？**

`d["k"] += 1` 是两次 RPC（取回旧值、写回新值），进程穿插在窗口里就丢更新。它和线程的 `counter += 1` 竞态同构（见 [02_race_gil](../02_race_gil/README.md)），只是窗口宽了几百倍；修法也一样——Manager 的 Lock 包住读改写。

**Q3: 大数组在进程间怎么传最快？**

能不传就不传：SharedMemory 零拷贝共享（写一次读多次）；只读场景也可以 fork 前放进模块级变量（fork 复制父进程内存给子进程，写时拷贝——只有真正写入时才复制对应页）。pickle+Pipe 是最慢但最通用的兜底。

**Q4: Manager 和 SharedMemory 都能"共享"，架构上怎么选？**

Manager 共享的是"对象的代理"（什么都能代理但每次 RPC），SharedMemory 共享的是"裸内存"（最快但只有字节）。高频小状态用 Manager+Lock（可读性优先），大块二进制用 SharedMemory（性能优先），两者常在同一个系统里分工共存。
