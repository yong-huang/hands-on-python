# 12 · 死锁与竞态诊断工坊：复现、验尸、修复

> 死锁人人背得出四个条件，但亲手"造一个、抓一个、修一个"的体验完全不同。本实验
> 在**隔离的子进程**里稳定复现交叉锁死锁，用 `faulthandler` 自动 dump 两个互相等待
> 的线程栈，再用统一锁序修复到连跑 100 次无挂起——外加一条本实验亲自踩出来的教训：
> 死锁演示绝不能放在主进程里。

## Background

这节讲死锁排查为什么是个专门的课题。传统排查"程序卡住"的手段是加日志重跑、对着代码猜，或者干脆重启了事。死锁最不讲道理：**不报错、不退出、只挂起**——日志安静、CPU 空闲、进程健康，唯一的症状是"怎么还不返回"。

更被动的是现场无法事后获取：挂起时没人知道每个线程停在哪一行，日志里自然也不会有。而且这类缺陷是概率性的——竞争窗口小，调度器不一定命中；测试环境偶尔出现一次，之后再想复现怎么也撞不上。

工程实践由此沉淀出一条固定流程：先把概率复现变成必然，再给进程装上"定时拍线程栈"的记录仪，用全局锁顺序从根上拆掉循环等待，最后以守护超时（watchdog timeout：给每次执行设超时上限，超时即判失败强制收尾，防止验证本身被挂起拖死）做回归验证。

Python 标准库自带的验尸工具让这条链路不需要任何第三方依赖，本实验把它完整跑一遍。

## What

这节给出定义与心智模型。死锁（deadlock）指一组线程互相持有对方要的锁、又都在等对方的锁，谁也无法推进的状态。最小模型：**T1 持 A 要 B、T2 持 B 要 A——两条"等待中…"谁也不返回，循环等待成立，死锁即成**。

修复只改一处：全局约定先 A 后 B，T2 的第二条 acquire 永远排在 B 之后，交叉消失。

可以把死锁想象成两个迎面相遇的人各让一步、又恰好挡住对方，于是都停住等对方先走；但和人不同的是，线程没有"嘴"——它们不会协商，会永远等下去，直到外部介入。所以诊断思路不是"劝和"，而是拍下现场、拆掉结构。

本实验建立一套完整的死锁处理流程：

| 步骤 | 手段 |
|---|---|
| 稳定复现 | 两次 acquire 之间 `sleep` 放大竞争窗口 |
| 自动验尸 | faulthandler（标准库"行车记录仪"，定时 dump 所有线程栈） |
| 定位 | 比对两个线程各自停住的行号 |
| 修复 | 全局锁序——所有线程"永远先 A 后 B" |
| 回归验证 | 守护超时循环连跑 100 次 |

## When to Use

这节补判断力：什么场合需要这套"复现—验尸—修复"的流程。主线看两个信号——程序会挂起且 CPU 空闲，以及多把锁存在嵌套获取。

典型场景：

- **多线程服务偶发卡死**：线上每隔几天挂起一批请求，日志无异常、进程还活着——需要预埋现场抓取手段，而不是重启了事。
- **并发测试与教学演示**：要稳定复现死锁或竞态（race condition，结果取决于线程执行时序的缺陷）才能写断言，这需要窗口工程。
- **引入新锁或调整临界区（critical section，访问共享资源时必须持锁执行的那段代码）时**：做锁序评审并跑回归守护，防止修一个死锁、引入另一个。

何时不用：只有一把锁、无嵌套获取，循环等待无从成立；纯 asyncio 协程没有线程式抢占，卡住通常是忘了 `await` 或协程间循环等待，排查手段不同；跨进程、跨主机的分布式死锁，faulthandler 只看得到本进程线程，需要另用分布式追踪。

| 工具 | 差异 | 什么时候选它 |
|---|---|---|
| `faulthandler` | 标准库，预埋后定时 dump 全部线程栈 | 不想加依赖，提前埋点 |
| py-spy（第三方） | 任意时刻 attach 到进程看栈 | 生产环境临时排查，无法预埋 |
| `acquire(timeout=)` | 只检测不预防 | 给"永久挂起"兜底告警 |
| 加日志 / 重启 | 事后猜，死锁时日志是安静的 | 仅适用于普通逻辑 bug |

## Quick Start

前置条件：纯标准库（`faulthandler`、`subprocess` 均内置），无需第三方依赖；脚本约 20 秒，会真的挂起一个子进程再击杀验尸：

```bash
cd concurrency/12_deadlock_workshop
python3 deadlock_workshop.py      # 复现 + 验尸 + 修复，约 20 秒
```

脚本先在子进程里复现死锁并抓取现场，再用统一锁序修复重跑。真实输出（首行 faulthandler 状态行与结尾"全部断言通过"横幅略；§1 两行 File 为 dump 文件摘录——stdout 中过长路径行被截断到 76 字符，看不到行号）：

```
========================================================
[1. 复现死锁，faulthandler 3 秒后抓现场]
========================================================
  子进程死锁成立，faulthandler 在 3 秒时 dump 了全部线程栈
  现场（两个线程都停在 transfer_bad 的锁等待上）：
    File ".../deadlock_workshop.py", line 39 in transfer_bad
    File ".../deadlock_workshop.py", line 44 in transfer_bad
  诊断结论：两个线程分别持有 A/B 并等待对方持有的锁 → 循环等待 → 死锁
  教训：死锁演示必须在子进程里做——挂死线程是非 daemon，主进程会被拖到永远退不出

========================================================
[2. 修复：统一锁序，连跑 100 次无挂起]
========================================================
  100 轮全部正常退出（0.3s）——统一锁序消灭循环等待
  锁排序法则：全局约定'永远先 A 后 B'，谁都不反转 → 死锁四条件的循环等待被拆除
  兜底三件套：acquire(timeout=) / 守护超时 / faulthandler 现场
```

dump 文件里最关键的两行（完整现场见 /tmp/_deadlock_dump.txt）：

```
  File ".../deadlock_workshop.py", line 39 in transfer_bad   ← T1 持 A 后停在 with LOCK_B
  File ".../deadlock_workshop.py", line 44 in transfer_bad   ← T2 持 B 后停在 with LOCK_A
  （两行先后次序可能随调度互换，以行号为准）
```

诚实预期（本机 3 次实测）：

- **死锁 100% 稳定复现**：`sleep(0.01)` 把窗口放大到调度器必然命中——复现死锁不靠运气，靠窗口工程
- **dump 中的行号 39/44 分别对应两个分支的 `with` 语句**：两行行号不同 = 交叉等待的直接证据
- **§2 的 100 轮只要 0.3s**：统一锁序后无争用等待，纯函数调用开销
- 运行结束看到"全部断言通过 ✓"即死锁复现与修复两项全过

输出 §1 是"案发现场"：两个线程的栈都停在 `transfer_bad`，行号一 39 一 44；输出 §2 是"结案报告"：统一锁序后 100 轮全部正常退出。机制在下一节逐条对上。

## How It Works

这节拆四件事：四条件里为什么只能拆循环等待、faulthandler 为什么连挂起进程都能拍、修复的三道防线、以及演示为什么必须在子进程里。

### 死锁四条件：只能安全拆一个

互斥、持有并等待、不可剥夺、循环等待——四个条件**同时**成立才死锁。工程上唯一能安全拆除的就是循环等待：给系统内所有锁定一个全局顺序，所有线程按同一顺序获取。

本项目 `transfer_good` 无论业务方向如何都先拿 `LOCK_A` 再拿 `LOCK_B`——反序调用方只是"业务上反了"，锁序没反。你在输出 §2 看到的"100 轮全部正常退出"，就是循环等待被拆除后的直接结果。

### faulthandler：进程的行车记录仪

`faulthandler.dump_traceback_later(3, file=stderr)` 起一个看门狗线程，3 秒后把**所有线程的 Python 栈**写到指定文件——进程挂起也能写。

为什么挂起也能写：各线程在锁上等待时已释放 GIL（全局解释器锁——CPython 中同一时刻仅一个线程执行字节码），阻塞等锁的线程会让出持有权。

可以把 faulthandler 想象成行车记录仪：平时不碍事，出事时留下事发瞬间的完整影像；但和行车记录仪不同的是，它按预设时间拍快照、不识别事件——所以要靠窗口工程保证"3 秒到点时死锁已发生"。

dump 出两行 `transfer_bad` 且行号不同，就是"互相等待"的实锤，对应 Quick Start 摘录的两行。同类工具：`threading.enumerate()` 看活着谁、`acquire(timeout=)` 探测锁、py-spy（第三方）看任意时刻栈。

### 修复工具箱：三道防线

1. **预防**：统一锁序（治本）；或干脆少用多锁——把临界区合并成一把锁保护
2. **检测**：`acquire(timeout=0.5)` 拿不到就报警而不是无限等；配合 faulthandler dump 找对手
3. **兜底**：守护超时（`future.result(timeout=)`）让挂起可被发现——注意被放弃的线程还挂着，进程退出时会等它

### 最核心的一处代码：给故障现场留退路

```python
p = subprocess.Popen([sys.executable, __file__, "--deadlock-child"],
                     stdout=subprocess.DEVNULL, stderr=open(dump_path, "w"))
time.sleep(5)
p.kill(); p.wait()          # 死锁进程本来就救不活，直接击杀
dump = open(dump_path).read()
```

为什么这样写：第一版把死锁线程放在主进程，挂死的 worker 是**非 daemon 线程**（daemon 线程在进程退出时不被等待，非 daemon 则必须等它结束），`ThreadPoolExecutor` 退出时 `shutdown(wait=True)` 永远等它——整个脚本挂死 90 秒。

修复方式：死锁进程子进程化，父进程超时击杀后读 dump 验尸。**演示故障时要给"故障现场"留好退路。**

## Pitfalls & Q&A

这节收四个踩坑点和三个深入问答，踩坑按"现象 → 原因 → 解法"组织。

- **死锁线程放主进程**。现象：脚本永远退不出（实测挂死 90 秒）。原因：挂死 worker 是非 daemon 线程，`shutdown(wait=True)` 永远等它。解法：演示、测试都必须子进程隔离。
- **复现靠碰运气**。现象：死锁时有时无，测试红绿随机。原因：竞争窗口太小，调度器不一定命中。解法：在两次 acquire 之间 sleep 放大窗口，把概率变成必然。
- **断言字符串抄文档不抄实测**。现象：dump 明明正常，断言却一直失败。原因：faulthandler 实际输出是 `Timeout (0:00:03)!` 而不是想当然的 `Timeout (3 seconds)`。解法：断言以实测输出为准，本实验第一版就栽在这里。
- **修复只改一处却不回归**。现象："看起来修了"，上线后偶发复发。原因：改动没经过重复验证。解法：统一锁序后连跑 100 次守护超时循环——"看起来修了"和"100 次都过"是两回事。

**Q1: 锁排序怎么落地到大系统？**
给锁编号（按获取的资源层级），封装统一的"多锁获取函数"内部按编号排序（`sorted` 后依次 acquire）；代码评审检查任何反序 acquire。数据库行锁、两把 mutex 嵌套同理。

**Q2: `acquire(timeout=)` 能防死锁吗？**
不能防，只能检测：超时说明拿不到锁，可能是死锁也可能是慢——抛错/告警把"永久挂起"降级为"可发现的失败"。真正防死锁还是锁序。

**Q3: try/finally 释放锁和死锁什么关系？**
finally 保证"持有并等待"不会变成"永久持有"（异常路径也放锁），减少死锁诱因；但它防不了循环等待——两者是不同层面的卫生。
