# 13 · 并发设计模式集：优雅关闭、令牌桶、指数退避、fan-out / fan-in

> 零散知识到工程能力的最后一公里是**模式**。这一篇把并发的常用招式提炼成四个
> 可复用模式，每个都带确定性验收：优雅关闭（kill -TERM 后 128ms 体面退场）、
> 令牌桶（100 请求恰 1.00s）、指数退避（0.77s ≈ 理论 0.75s）、fan-out / fan-in
> （3 个失败被隔离，17 个成功照常收集）。

## Background

这节讲这四个模式出现之前，几类并发老问题是怎么被应付的，又在哪里撞墙。

没有专门方案时，工程师用最直白的写法：进程退出靠 `time.sleep(2)` 赌手头任务做得完；调用第三方 API 靠"每秒清零的计数器"压频率；上游失败就固定等 1 秒再试；批量任务往线程池里一丢，异常各自为政。

这些写法在演示里能跑，上生产各有撞墙的场景：

- `sleep(2)` 睡短了——进程被强杀时，正在写的数据文件直接撕烂；
- 每秒清零的计数器——挡不住开抢瞬间的脉冲流量，又把平稳期的速率压得过死；
- 固定间隔重试——成千上万个客户端在同一时刻齐发请求，上游刚缓过来又被压垮（重试风暴）；
- 批处理没有隔离——一个请求失败，整批结果跟着报废。

于是这些解法在工程实践中被反复打磨，固化成带行为契约的标准方案：网络库把重试间隔做成一轮比一轮长，网关用按速率补充的配额做速率控制，服务按"停止接活→排空→落盘"的顺序退出。本实验把四个最常用的方案收进一个脚本，各配一条可断言的验收线——断言（assert）是写进程序的自动检查，不满足就报错，让"写对了"能被证明。

## What

这节给出四个模式的定义、统一的心智模型，以及各自管什么。

模式（design pattern）是带着明确行为契约、能整体搬到新项目复用的问题解法——区别于零散的技巧。四个模式各管一件事：

- **优雅关闭**（graceful shutdown）：进程收到退出信号——SIGTERM，`kill` 命令默认发送的信号——后不立刻死，而是停止接新活、做完手头、保存成果再退出。
- **令牌桶**（token bucket）：一种限流（rate limiting，控制单位时间内放行的请求数）算法。以恒定速率往桶里放令牌，请求拿到令牌才放行，桶内积攒的令牌允许短时突发（burst，瞬间超过平均速率的流量）。
- **指数退避**（exponential backoff）：失败后等待 `base × 2^n` 再重试，等待时间一轮轮翻倍，给故障方恢复的时间。
- **fan-out / fan-in**（扇出 / 扇入）：把一批任务并行分发出去（fan-out），完成后把结果统一归拢（fan-in），失败单独收集。

一句话心智模型：**优雅关闭管生命周期（信号→停接活→善后→落盘），令牌桶管速率（长期平均+突发额度），指数退避管失败恢复（越挫越有耐心），fan-out / fan-in 管批量吞吐（并行扇出、失败隔离、结果归拢）**。四个模式对应生产并发系统的四大关切：活得好、跑得稳、摔得起、扛得住。

可以把四个模式想象成一支外包车队的运营手册：收车前先停止接单（关闭）、发单节奏受限（速率）、路线堵了就把再出发的间隔拉长一倍（重试）、一百单拆给多辆车再统一回收签收（批量）。但和真实车队不同的是，这里的每条手册都必须能写成断言——行为契约是否成立要靠测试证明，这正是模式区别于口口相传技巧的地方。

## When to Use

这节讲每个模式"在做什么事的时候"值得请出来，以及同一位子上的其他候选。

典型场景：

- 给常驻服务做滚动升级（rolling update，逐个替换实例、不中断服务的发布方式）、或容器编排（如 Kubernetes 这类自动调度、重启容器的集群管理系统）主动发 SIGTERM 时——需要优雅关闭，保证正在写的数据不烂尾。
- 调用方要压住自己对下游 API 的请求速率时——令牌桶适合"平时宽松、上限明确"的场合。
- 上游偶尔失败但整体健康（网络抖动、偶发超时），需要自动重试时——指数退避。
- 要并发处理几百个可独立重试的任务（抓页面、下载文件、群发通知）时——fan-out / fan-in。

何时不用：任务只有三五个且失败无所谓，直接写 for 循环串行跑更清楚；脚本跑完就退、没有共享状态要保存，不需要关闭协议；上游的失败是"重试也没用"的类型（参数错误、无权限），退避只是浪费时间。

同一关切往往有多个候选方案，取舍如下：

| 关切 | 方案 | 差异 | 什么时候选它 |
|---|---|---|---|
| 关闭 | 信号处理（本篇） | 进程级关闭入口，任何来源的退出都走它 | 要响应 `kill` / 编排系统的退出指令 |
| 关闭 | 毒丸（lab 04） | 任务流内部的关闭协议，靠特殊的"退出任务"通知 worker（干活的执行体） | 关闭时机由任务生产者控制 |
| 限流 | 令牌桶（本篇） | 控制"平均速率 + 突发上限"，容忍 bursts | API 调用方限流 |
| 限流 | 漏桶 | 强制恒定速率出口，削平一切突发 | 流量整形，要求出口绝对平滑 |
| 重试 | 指数退避（本篇） | 等待指数增长 + 封顶 + 随机偏移（jitter） | 上游需要恢复时间，重试要错峰 |
| 重试 | 固定间隔 | 每次等同样久 | 故障与时间无关、重试次数很少的场合 |
| 批量 | fan-out / fan-in（本篇） | 失败隔离，成功者照常交付 | 批处理，失败项可单独重试 |
| 批量 | TaskGroup（lab 09） | 结构化并发（子任务的存活被限定在一个代码块内，退出前自动等齐并回收），一败全停 | 事务型场景，必须全部成功 |


```
========================================================
[1. 优雅关闭：kill -TERM → 手头做完 → 落盘 → 退出]
========================================================

  关键：收到信号只'停止接活'，手头任务做完才走——强杀会撕烂正在写的数据

========================================================
[2. 令牌桶限流：50/s 满桶 50，连发 100 个请求]
========================================================
  100 个请求耗时 1.00s（前 50 突发 + 后 50 按 50/s）——速率钳制生效

========================================================
[3. 指数退避：100% 失败的上游，重试 5 次后放弃]
========================================================

========================================================
[4. fan-out / fan-in：20 个任务扇出，失败隔离收集]
========================================================
  20 个任务 5 个 worker：成功 17 个 + 失败 3 个分别收集
  总耗时 49ms（并行扇出）——单个失败不影响其余 19 个
```

诚实预期（本机 3 次实测）：

- **§1 落盘数 12 = 全部任务**：0.6s 内 5 个 worker 已消化完 12 个任务（每个 50ms），信号到来时"手头"只剩收尾——想看"做一半"的场景把任务 sleep 调大
- **§2 恰好 1.00s**：令牌桶的补币是精确的时间函数；±0.3s 断言带覆盖调度抖动
- **§4 的 3 个失败位置固定**（i % 7 == 3）——失败隔离的断言才能写死 17+3

脚本用到的标准库组件速览：

| 组件 | 在脚本里的角色 |
|---|---|
| `signal.signal()` | 注册 SIGTERM 处理函数，把信号转成回调 |
| `threading.Event` | 关闭标志位，worker 每轮循环检查 |
| `time.monotonic()` | 令牌桶补币用的单调时钟（只会前进、不受系统改时间影响的时钟） |
| `ThreadPoolExecutor` / `as_completed` | fan-out 的 worker 池与扇入归拢 |

## How It Works

这节按四个模式逐个拆机制，并解释输出里每个数字的来源。

### 优雅关闭：信号 → 事件 → 排水 → 落盘

`signal.signal(SIGTERM, handler)` 把信号转成 `threading.Event`（线程间共享的布尔标志位），worker 循环改成"拿不到新活且关闭已触发 → 下班"。

三要素缺一不可：**停止接活**（不再领新任务）、**做完手头**（处理中的任务完整跑完）、**落盘**（成果持久化后退出）。

你在输出 §1 看到的"SIGTERM 后 128ms 内退出，已完成任务 12 个落盘"，就是这三步走完的耗时与结果。它与任务流内部的毒丸协议（lab 04）互补，分工见 When to Use 的对比表——生产系统两者都要。

### 令牌桶：按时间差补币，不开定时器

桶以恒定速率积累令牌，桶满时允许**突发**——输出 §2 的"前 50 突发"用的就是满桶积攒的额度。实现核心只有三行：

```python
now = time.monotonic()
self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
self.updated = now
```

每次领取时按"距上次的秒数 × 速率"补币——懒计算（用到的那一刻才算账），无需后台线程、无定时误差、多个调用者天然共享同一个桶。用 `monotonic()` 而非 `time()`：系统改时间不会让桶凭空溢出。

### 指数退避：等待翻倍、双封顶、加抖动

失败后等待 `base × 2^n` 再试（0.05→0.1→0.2→0.4s），给上游指数级增长的恢复时间；上限封顶 + 次数封顶（不封顶的后果见文末踩坑清单）。间隔上再叠加 ±jitter，防止所有客户端在同一时刻同步重试（重试风暴）。

输出 §3 的"0.77s ≈ 理论 0.75s"说明等待完全按公式发生；断言时关闭 jitter——模式可以有随机性，验收必须确定。

### fan-out / fan-in：批处理的事务边界

扇出（`submit` 提交全部任务）→ 并行执行 → 扇入（`as_completed` 逐个归拢结果）。与 TaskGroup（lab 09）的本质区别是**失败隔离**：3 个失败被收集进 errors 列表，17 个成功照常交付。

你在输出 §4 看到的"成功 17 个 + 失败 3 个分别收集"与"总耗时 49ms"，就来自这条 submit → as_completed 流水线。失败隔离适合批处理（失败项单独重试）；必须全成的场景才用 TaskGroup 的一败全停。

## Pitfalls & Q&A

这节收录四个模式落地时真实踩过的坑，每条按现象、原因、解法展开。

- **优雅关闭里等待太狠**：现象是 worker 只看 `task_q.empty()` 就退，已入队未领取的任务留成孤儿；原因是"停止接活"和"排空队列"是两件事；解法是用毒丸或超时轮询保证两者兼顾。
- **信号处理里做重活**：现象是 handler 里做 IO 时程序偶发卡死不退（死锁）；原因是信号 handler 只该做最少的事；解法是 handler 只 set 一个 Event，排水逻辑放回主流程。
- **退避无上限**：现象是第 20 次重试要等 0.05×2¹⁹ = 26 小时；原因是指数曲线没有封顶；解法是同时封顶重试次数和单次等待上限。
- **jitter 写进断言**：现象是测试时好时坏；原因是模式带了随机性；解法是验收时关抖动或放大容差——别让随机性毁掉测试。
- **fan-in 时不区分结果与异常**：现象是成功和失败混在一个列表里，下游无法分别处理；解法是分池收集（本实验用 errors 列表），失败项交给单独的重试流程。
