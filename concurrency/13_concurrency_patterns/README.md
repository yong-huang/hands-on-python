# 13 · 并发设计模式集：优雅关闭、令牌桶、指数退避、fan-out / fan-in

> 零散知识到工程能力的最后一公里是**模式**。这一篇把前十二站用过的招式提炼成四个
> 可复用模式，每个都带确定性验收：优雅关闭（kill -TERM 后 128ms 体面退场）、
> 令牌桶（100 请求恰 1.00s）、指数退避（0.77s ≈ 理论 0.75s）、fan-out / fan-in
> （3 个失败被隔离，17 个成功照常收集）。

## 1. 为什么需要它

面过试都知道"要限流、要重试"，但写出来常常是错的：限流变成了精确等于、退避曲线随手拍、关闭逻辑靠 sleep、批处理一错全崩。模式的价值在于**每个都带明确的行为契约**——本实验的四个模式各配一条可断言的验收线，让"写对了"可以被证明。

## 4. 核心概念

### 4.1 优雅关闭：信号 → 事件 → 排水 → 落盘

`signal.signal(SIGTERM, handler)` 把信号转成 `threading.Event`，worker 循环改成"拿不到新活且关闭已触发 → 下班"。三要素：**停止接活**（不再领新任务）、**做完手头**（处理中的任务完整跑完）、**落盘**（成果持久化后退出）。对照项目 4 的毒丸：毒丸是"任务流内部的关闭协议"，信号处理是"进程级的关闭入口"——生产系统两者都要。

### 4.2 令牌桶 vs 漏桶：两种限流性格

令牌桶以恒定速率生成令牌，桶满允许**突发**（一次拿 50 个立刻通过）——适合"平时宽松、上限明确"的调用方限流。漏桶则强制恒定速率出口。实测：满桶 50 + 速率 50/s，前 50 请求瞬时通过、后 50 用时恰 1 秒。实现核心是"按时间差补币"而不是定时器——无需后台线程，纯懒计算。

### 4.3 指数退避：对上游最有耐心的姿势

失败后等待 `base × 2^n` 再试（0.05→0.1→0.2→0.4s），给上游指数级增长的恢复时间；上限封顶 + 次数封顶 + ±jitter 防止所有客户端同步重试（重试风暴）。实测 5 次尝试总耗时 0.77s ≈ 理论 0.75s。断言时关 jitter——**模式可以有随机性，验收必须确定**。

### 4.4 fan-out / fan-in：批处理的事务边界

扇出（submit 全部）→ 并行执行 → 扇入（as_completed 归拢）。与项目 9 TaskGroup 的本质区别：**失败隔离**——3 个失败被收集到 errors 列表，17 个成功照常交付。适合批处理（能重试的单独重试）；事务型场景（必须全成）才用 TaskGroup 的一败全停。

## 5. 关键代码解析

**为什么令牌桶用"时间差补币"而不用定时器线程？**

```python
now = time.monotonic()
self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
self.updated = now
```

每次 acquire 时按"距上次的秒数 × 速率"补币——懒计算，无需后台线程、无定时误差、多调用者天然共享。`monotonic()` 而非 `time()`：系统改时间不会让桶凭空溢出。

坑清单：

- **优雅关闭里等待太狠**：worker 只看 `task_q.empty()` 就退，会把已入队未领取的任务留成孤儿——"停止接活"和"排空队列"是两件事，本实现用毒丸或超时轮询保证两者兼顾
- **信号处理里做重活**：handler 只该 set 一个 Event，真正的排水逻辑在主流程里——handler 里做 IO 是死锁温床
- **退避无上限**：第 20 次重试要等 0.05×2¹⁹ = 26 小时；必须封顶次数和单次上限
- **jitter 写进断言**：模式带抖动，验收就关抖动或放大容差——别让随机性毁掉测试
- **fan-in 时不区分结果与异常**：成功和失败分池收集（本实验 errors 列表），混在一起下游无法处理

## 7. 深入要点

**Q1: 进程收到 SIGTERM 后如何优雅退出？**
handler 只 set 关闭 Event；worker 停止接活、完成手头任务；结果持久化后主线程 join 全部 worker 再退出。核心原则：信号处理函数不做重活，退出是流程不是事件。

**Q2: 令牌桶和漏桶的区别？**
令牌桶允许突发（桶内积攒的令牌可一次性用掉），控制"平均速率 + 突发上限"；漏桶强制恒速出口。API 限流常用令牌桶（容忍 bursts），流量整形常用漏桶。

**Q3: 重试为什么用指数退避加 jitter？**
固定间隔会让所有客户端在同一时刻重试（重试风暴打崩刚恢复的服务）；指数退避给上游递增的恢复时间，jitter 打散客户端的重试时刻。参数必须封顶（次数、单次间隔）。

**Q4: 批处理中一个任务失败，整批重跑还是隔离收集？**
看业务的事务性：能独立重试的批处理用失败隔离（fan-out/fan-in + 错误列表，成功的不陪葬）；全有全无的事务用结构化并发一败全停（项目 9 TaskGroup）。

**Q5: 优雅关闭如何保证"任务不丢"？**
三段式：停止接活（关入口）→ 排水（处理完已入队任务）→ 落盘（状态持久化后再退出）。任何一段缺失都会造成"做了一半"的数据——配合项目 4 的毒丸实现任务级的完整排水。

## 8. 总结

1. **优雅关闭三段式**：停止接活 → 做完手头 → 落盘退出；信号 handler 只当开关
2. **令牌桶懒补币**：时间差计算无需定时器；突发额度与恒定速率并存
3. **指数退避有封顶**：次数与单次上限必设；jitter 防风暴、验收时关掉
4. **fan-out / fan-in 失败隔离**：成功与失败分池收集，批处理与事务型各有模式
5. **模式 = 行为契约**：每个模式配确定性验收线，"写对了"可以被证明
