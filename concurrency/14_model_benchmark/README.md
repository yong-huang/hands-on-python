# 14 · 四种执行模型性能对决：用数据回答"该用什么跑"

> 同一个 IO 任务、同一个 CPU 任务，分别用串行 / threading / multiprocessing /

> 三条方向性结论全部成立——选型公式从此不是背的，是自己量出来的。

## Background

这节讲"靠口诀选执行模型"的旧状态，以及它在哪里失灵。

Python 并发选型流传已久的一句口诀是"IO 用协程（coroutine，用 async def 定义、能在 await 处暂停让出的函数）、CPU 用进程"。多数团队背下结论就开工：抓取一律协程，计算一律多进程，不再追问依据。

口诀回答不了追问：为什么线程跑 IO 也可以？差多少？什么时候线程反而比串行还慢？换一台机器、换一个 Python 版本，名次会不会颠倒？更常见的翻车是凭单次运行下结论——冷启动、任务规模不同，都足以把快慢排反。

工程上用微基准（microbenchmark，对同一个任务在受控条件下反复计时对比）回答这类问题：
正式计时前预热（先空跑几轮拉起状态）、交替多轮取中位数（多次测量排序后取中间值，抗单次噪声）、
各模型跑对称任务、只断"谁快"不断"快几倍"。

本实验把这套纪律用在串行 / 线程 / 多进程 / 协程四种跑法的同题对决上（计时纪律沿用 lab 11），
并用三条方向性断言（自动检查，不满足就报错）把结论钉死。

## What

这节定义四种执行模型，并给出对决的最终答案。

执行模型（execution model）指一段任务由谁、在哪、怎么调度执行。四种模型一句话说清：

- **串行**：一个任务做完再做下一个，无并发。
- **threading**（多线程）：同一进程内开多个线程共享内存，受 GIL 约束——GIL（全局解释器锁）是 CPython 里同一时刻只允许一个线程执行 Python 字节码的锁。
- **multiprocessing**（多进程）：每个 worker 一个独立进程，各有各的 GIL，可真并行。
- **asyncio**（协程）：单线程事件循环（event loop，循环调度协程的执行器），在 `await` 处主动让出。

任务也分两类：**IO 密集**（时间花在等网络、磁盘）与 **CPU 密集**（时间花在计算）。

对决结果按这两类归纳：**IO 密集看"等待重叠"——asyncio 16.8×、threading 8.0×；
CPU 密集看"绕开 GIL"——multiprocessing 2.78× 唯一真并行，
threading 1.18× 倒贴，asyncio ≈ 串行**。

（16.8× 表示耗时降到串行的 1/16.8。）

可以把四种模型想象成四种搬家方式：一个人慢慢搬（串行）、雇八个帮工一起抬箱子（线程）、租四辆货车各走各路（进程）、一个人怀里同时揣十件待送快递、谁不阻塞就先送谁（协程）。但和搬家不同的是，帮工再多，同一时刻也只有一人能干搬重物的活（GIL 所限）——人手优势只在"等电梯"（IO 等待）时才兑现。

## When to Use

这节把数据变成选型公式，并划出公式的边界。

选型公式：**IO 密集 → asyncio（等待重叠最大化）或 threading（生态兜底）；CPU 密集 → multiprocessing（真并行）**。落到"在做什么事的时候"：

- 并发抓取几百个网页、聚合多个慢 API——asyncio 首选；同步 SDK 改写不动就 threading 兜底。
- 批量压缩图片、算哈希、数素数这类纯计算——multiprocessing，且单块任务要够大。
- 定时脚本、并发量小——串行最简单，并发复杂度不值得。

三个边界：

- 混合负载用 "asyncio + run_in_executor"（把同步阻塞调用丢进线程/进程池，事件循环不被卡住的桥接法）分层处理；
- 任务太小时 spawn（启动全新子解释器进程）成本倒挂（见 lab 05）；
- free-threading（移除 GIL 的 CPython 官方构建）落地后，CPU 密集的线程版会重新变快（lab 16 实测）。

何时不用并发本身：任务毫秒级且量小，串行即可；团队不熟悉 asyncio 而并发只有几十，threading 的心智成本更低。

| 模型 | 实测（本机中位） | 差异 | 什么时候选它 |
|---|---|---|---|
| 串行 | 基准 1× | 零并发复杂度 | 任务小、量少 |
| threading | IO 8.0×；CPU 1.18×（倒贴） | 等待可重叠；CPU 被 GIL 串行化 | IO 任务 + 同步生态兜底 |
| multiprocessing | CPU 2.78×（唯一真并行） | 独立 GIL；有 spawn 与序列化（把对象转成字节流、到另一进程再还原）成本 | CPU 密集且任务够大 |
| asyncio | IO 16.8×；CPU ≈ 串行 | 单线程重叠等待，切换最便宜 | 海量并发 IO 且代码可协程化 |

诚实预期（本机 3 次实测）：

- **IO 数字极稳**（sleep 精确）：asyncio 8.5~16.8×、threading ≈ 8.0×；asyncio 略快于线程是因为没有线程切换开销
- **CPU 加速比 2.8~4× 波动**：4 个进程被操作系统分到性能核（快但费电的核）与能效核（省电但慢的核）的组合不同；断言线 ≥1.67×（s_cpu*0.6）
- **asyncio 跑 CPU 任务 ≈ 串行甚至更慢**（0.25 vs 0.16s）——事件循环自身有开销，await 帮不了计算
- `--quick` 档规模减半，用于快速回归；正式对比用全量档
- **跨版本提示**：不同 Python 小版本下倍数会漂移（3.14 实测线程版 CPU ≈1.0× 串行而非 1.18×——后跑的模型占机器渐热的便宜），三条方向性结论跨版本稳定；C 区断言与 B 区同样留 10% 容差，线程偶发的 0.95~0.99×（本机实测）不会误报失败

## How It Works

这节先立"数字可信"的方法论，再给结果与机制的对照，最后拆一处最容易被坑的代码。

### 基准方法论：四个纪律

四个纪律缺一不可：**预热**（首轮拉 CPU 频率、触发 spawn）、**交替多轮取中位**（消抖动，防"先跑方吃亏"——lab 11 的教训）、**对称任务**（各模型跑完全相同的 blocks）、**方向性断言**（断"谁快"不断"快几倍"——倍数随机器变，方向不变）。背离任何一条，数字就会说谎。

### 数字背后的机制对照

你在输出 A 区看到的"asyncio 16.8×"、B 区看到的"threading 0.186s 比串行 0.158s 还慢"，都能在下表里找到机制解释：

| 结果 | 机制解释（对应实验） |
|:---|:---|
| asyncio IO 16.8× | 等待重叠在一张调度表上（lab 08/10） |
| threading IO 8.0× | sleep 释放 GIL，8 线程等待重叠（lab 02/03） |
| threading CPU 1.18× | GIL 串行化 + 切换税倒贴（lab 02） |
| multiprocessing CPU 2.78× | 每进程独立 GIL 真并行（lab 05） |
| asyncio CPU ≈ 1× | await 不帮计算，循环开销倒贴（lab 08） |

### 进程池为什么要全局复用

**为什么进程池要全局复用（`_PROC_POOL`）而不是 with 块？**

```python
_PROC_POOL = None
def run_process_cpu(blocks):
    global _PROC_POOL
    if _PROC_POOL is None:
        _PROC_POOL = ProcessPoolExecutor(max_workers=4)
        _PROC_POOL.submit(cpu_task, 1000).result()   # 预热触发 spawn
    list(_PROC_POOL.map(cpu_task, [CPU_N] * blocks))
```

第一版把 Pool 创建放在 `with` 块里计时——spawn 4 个解释器的 0.4s 淹没了真并行收益，实测"加速比 0.98×"（虚假持平）。spawn 是一次性成本，必须挪出计时区（预热调用顺带触发）。这正是 lab 05 "任务规模要够大"的基准版表达。

## Pitfalls & Q&A

这节收录基准测量最容易犯的错，以及三个常见追问。

踩坑清单：

- **只跑一轮就下结论**：现象是名次与别人跑的对不上；原因是首轮冷启动 + 单次噪声足以翻转相邻模型的名次；解法是预热 + 3 轮中位做底线。
- **CPU 任务太小**：现象是得出"多进程没用"的错误结论；原因是 spawn 成本吞掉加速比；解法是加大单块任务规模再测。
- **线程池跑 CPU 任务还调大 max_workers**：现象是越调越慢；原因是 GIL 下纯添切换税；解法是线程数不必超过核数，CPU 任务改用进程池。
- **断言绝对倍数**：现象是换台机器测试就红；原因是倍数随机器漂移（2.8~3.7×）；解法是只断方向（谁最快），倍数写进文档但不进断言。

**Q1: IO 密集为什么 asyncio 比 threading 还快一点？**
两者都重叠等待，但 asyncio 的"切换"是函数调用级的让出，
threading 每次切换要经过内核调度。

16 个并发连接下差异 ~8%（实测 16.8× vs 8.0×，并发数不同倍数不同）；
千级并发时 asyncio 的内存与切换优势才真正拉开。

**Q2: 为什么你的基准里线程版 CPU 任务更慢，而有人说"差不多"？**
GIL 下线程版 = 串行 + 切换税，任务越大切换税越明显；任务极小或 C 扩展释放 GIL（numpy）时接近串行。"差不多"和"更慢"取决于任务形状——所以基准要交代任务规模。

**Q3: free-threading（PEP 703）落地后，这张表会怎么变？**
CPU 密集的 threading 从 1.18× 变成真并行（接近进程版且免序列化），
multiprocessing 的护城河收窄到"崩溃隔离"；IO 结论不变。

详见 [16_free_threading](../16_free_threading/README.md) 的实测。
