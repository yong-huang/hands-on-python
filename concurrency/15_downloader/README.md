# 🏁 15 · 可切换执行模型的并发下载器：终极串联

> 一个并发下载器把系列能力全部收进一个系统：**同一套下载协议代码，sync / thread /
> process / async 四种执行模型一键切换**（`--model`），限流（`--limit`，服务端实测
> 在飞峰值全部 ≤ limit）、指数退避重试、断点续传（删一半重跑只补 10 个）、SHA256
> 逐一校验——四模式结果完全一致。

## What

这是个毕业设计：流水线骨架（lab 04）、执行器与进程纪律（lab 05/07）、异步三件套（lab 11）、模式集（lab 13），全部收进一个 300 行的系统。一句话心智模型：**统一入口 `download_round(model, limit)` 把"怎么下载"封进后端，"下什么、下到哪、怎么验"留在协议层**。主链：入口按 `--model` 分发到四个执行模型闸门（限流/重试/续传挂在闸门上），访问本地 aiohttp 服务（20 个文件、30ms 延迟、首败恢复），最后 SHA256 逐文件断言；右下角是 SIGKILL 强杀对照——不挂进这套协议的下场。

## Why

它的验收标准也最苛刻：**四种执行模型跑同一个任务清单，结果必须完全一致**（SHA256 逐一比对）、**并发上限必须在服务端实测生效**（而不是客户端自己声称）、**中断后必须能续传**。能通过这三条，前面学的就都串起来了。

## How

```bash
cd concurrency/15_downloader
python3 downloader.py --verify-all --limit 5        # 四模式全跑 + 全部断言
python3 downloader.py --model async --limit 5 --twice   # 单模型 + 断点续传演示
```

真实输出（macOS, CPython 3.13.9）：

```
========================================================
[四模式全跑（--limit 5）]
========================================================
  sync     补下 20 → 成功 20，服务端在飞峰值  1，SHA256 校验 20/20
  thread   补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20
  process  补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20
  async    补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20

  断言：四模式全部成功 ✓ 并发上限全部生效 ✓ 校验全部通过 ✓
  同一套协议代码，四种执行模型结果完全一致 —— 统一接口的价值
```

`--twice` 断点续传演示：

```
========================================================
[断点续传：删掉一半文件再跑（只补缺失）]
========================================================
  第二轮补下 10 个（其余跳过），最终校验 20/20
  断点续传 ✓
```

诚实预期（本机 3 次实测）：

- **sync 峰值恒为 1**（顺序）、thread/process/async 峰值 = limit（5 或 3 都实测过）——并发上限由服务端计数观测，不是客户端自报
- **四模式文件内容完全一致**：本地服务用固定种子生成文件，每轮 SHA256 清单相同
- **async 轮不含网络不确定因素**：本地回环 + 首败必恢复，重试恢复率恒 100%

### 统一入口：协议与执行分离

`download_round(model, limit)` 是全系统唯一入口：协议层（读清单 → 逐文件下载 → SHA256 校验 → 断点续传判断）写一遍，四个后端各自实现"并发地执行抓取"。这是 lab 07 `Executor` 工厂思路的完整版——连 asyncio 也被包进同一签名。**切换模型不改一行协议代码**。

### 断点续传：文件系统就是状态库

续传不需要数据库：已存在的目标文件就是"已完成"的记录。每轮开始 `pending()` 过滤掉磁盘上已有的文件，只补缺失。配套纪律：**下载必须原子**（先写临时或整块写入，杜绝半截文件被当成"已完成"）；本实验文件整块 `f.write(data)` 天然满足。

### 服务端观测：并发上限要别人证明

客户端声称"我限流了"不算数——本实验的服务端维护 `in_flight` 计数器并记录峰值，四种模式的峰值全部 ≤ limit 才算通过。**资源上限的验收永远在被调用方做**，这是 lab 11 "服务端观测"思想的收口。

### process 后端的特殊性

sync/thread 共享父进程的本地服务；process 后端真开 N 个子进程，每个子进程走**真实网络**回连父进程的服务——这是唯一有跨进程序列化与网络栈参与的模型，也因此最有生产味（远端 worker 集群的微缩景观）。纪律沿用 lab 05：worker 顶层函数、参数可 pickle、`__main__` 保护。

## Deep Dive

**为什么 async 后端的 gather 必须放在 `async with session` 块内？**

第一版把 `asyncio.gather(...)` 写在了 session 上下文外面——session 进入即退出，20 个下载全部撞上 `RuntimeError: Session is closed`。asyncio 资源的生命周期由上下文管理器界定：**谁开谁关，用时必须在里面**。

踩坑清单：

- **服务器线程一启动就死**：`asyncio.run(_serve(...))` 在 `_serve` 返回后立刻关循环——服务必须以 `await Event().wait()` 常驻（daemon 线程随主进程退出，无需显式停止）
- **子进程模型用 stdin 方式测试**：spawn 子进程 re-import `__main__`，stdin 场景下 `__file__` 是 `<stdin>` 直接 FileNotFoundError——一切以真实文件入口为准
- **续传前 reset 目录**：第一版 `download_round` 开头无条件 `reset_dir()`，把"保留的另一半"也删了，续传变全量重传——断点续传的 reset 必须是可选参数
- **三模型全绿就收工**：第四个（async）才暴露 `Session is closed`——每条路径都要跑到断言，"其他三个都过了"不是证据

## Q&A

**Q1: 如何设计一个"执行模型可切换"的并发框架？**
定义协议层接口（输入：任务清单 + 并发参数；输出：统一统计），每个后端实现"如何并发地执行单个任务"。关键是把限流/重试/校验放在协议层而不是后端里——后端只回答"用多少个执行体、怎么排队"。

**Q2: 四种执行模型在你的系统里如何做最终选择？**
按负载类型（lab 14 的对决数据）+ 生态约束（已有同步库 → 线程；CPU 密集 → 进程；海量 IO → 协程）+ 运维成本。本实验证明三者可以被统一接口封装——**选型延迟到部署期**。

**Q3: 这个下载器要上生产，还缺什么？**
限流的动态调节（拥塞反馈）、磁盘空间预检、内存流式写入（大文件不全量 read）、失败任务的死信队列、指标上报。以及最重要：优雅关闭（lab 13）已就位——SIGTERM 后已下载清单不丢。
