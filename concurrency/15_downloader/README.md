# 🏁 15 · 可切换执行模型的并发下载器：终极串联

> 一个约 300 行的并发下载器，把协议与执行分离做到底：**同一套下载协议代码，
> sync / thread / process / async 四种执行模型一键切换**（`--model`），限流
> （`--limit`，服务端实测在飞峰值全部 ≤ limit）、指数退避重试、断点续传
> （删一半重跑只补 10 个）、SHA256 逐一校验——四模式结果完全一致。
>
> 读完本篇，你能看到限流、重试、续传、校验如何在一个真实系统里协同。

## Background

这节讲"手写下载脚本"的常见做法，以及它在哪里撑不住。

没有这套结构时，一个下载脚本通常长这样：`requests` 循环里逐个 GET，中间 `time.sleep(0.1)` 凭感觉限速；下到第 80 个文件断了网，重跑从第 1 个再来；文件下没下完整全凭运气；想把"顺序"改成"并发"，整个循环要推倒重写。

痛点集中在三处：

- **中断成本高**——大清单下载动辄几分钟，一断就全量重来；
- **并发一高就出事**——不控速率会被服务端限流甚至封禁，控了速率又不知道到底有没有生效（客户端自己说了不算）；
- **完整性没证据**——半截文件混在成品里，直到使用时才暴露。

工程实践把这些关注点拆开解决：协议（下什么、怎么校验、断在哪）与执行（用什么并发模型调度）分离；"磁盘上已有完整文件"当作断点记录——这就是断点续传（中断后重跑只补缺失部分）；完整性交给哈希校验；限流效果由服务端计数证明。本实验把这套拆分落成一个完整可跑的系统。

## What

这节给出下载器的定义、统一入口的心智模型和主链路。

它是一个执行模型可切换的并发下载器，也是系列的收口实验：流水线骨架（lab 04）、执行器与进程纪律（lab 05/07）、异步三件套（lab 11）、模式集（lab 13）收进约 300 行代码。四个执行模型分别是 sync（顺序执行）、thread（多线程）、process（多进程）、async（协程事件循环）。

一句话心智模型：**统一入口 `download_round(model, limit)` 把"怎么下载"封进后端，"下什么、下到哪、怎么验"留在协议层**。

主链路三步：

1. 入口按 `--model` 分发到四个执行模型闸门——限流（控制单位时间的请求数）/ 重试 / 续传都挂在闸门上；
2. 访问本地 aiohttp（一个支持异步的 HTTP 服务端/客户端库）测试服务：20 个文件、30ms 延迟、首败恢复（服务端故意先失败一次，验证重试能救回）；
3. 下载完成后用 SHA256（内容哈希——差一个字节摘要就完全不同）逐文件断言（assert，写进程序的自动检查，不满足就报错）。

可以把这套下载器想象成一家快递公司：协议层是运单规范（收什么、送到哪、怎么签收核验），四个执行模型是四种运力（步行、电动车、货车、无人机）。但和快递公司不同的是，这里换运力不需要改一张运单——四种模型跑完，SHA256 清单完全一致。

## When to Use

这节讲什么时候值得搭这样一套结构，以及四个后端各自的位置。

适合请出这套结构的场景：

- 批量拉取数据集、模型文件、公开资源——文件多、单文件不小，断点续传和校验都是刚需；
- 定时同步远端资源——每轮只补新增与缺失，天然增量；
- 对接有速率配额的第三方 API——限流必须由服务端观测证明生效，而不是客户端自报。

何时不用：三五个小文件的一次性下载，`curl` / `wget` 一行解决；现成工具的续传与校验已够用、又不打算嵌进自己的系统时，不必自研。

四个后端怎么选（依据见 lab 14 的对决数据）：

| 后端 | 并发特征 | 什么时候选它 |
|---|---|---|
| sync | 顺序执行，服务端观测的并发峰值恒为 1 | 调试基准；服务端明确要求串行 |
| thread | 线程池重叠等待，峰值 = limit | IO 下载的默认选择 |
| process | 子进程回连，走真实网络栈 | 下载后还要 CPU 后处理（解压、转码） |
| async | 单线程事件循环，最省资源 | 海量小文件、高并发 |

## Quick Start

这节跑一次四模式全验和一次断点续传。本地测试服务基于 aiohttp，首次运行前需 `pip install aiohttp`。下面输出里的每个 ✓ 都由断言产生。

```bash
cd concurrency/15_downloader
python3 downloader.py --verify-all --limit 5        # 四模式全跑 + 全部断言
python3 downloader.py --model async --limit 5 --twice   # 单模型 + 断点续传演示
```

真实输出（节选）：

```
========================================================
[四模式全跑（--limit 5）]
========================================================
  sync     补下 20 → 成功 20，服务端在飞峰值  1，SHA256 校验 20/20
  thread   补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20
  process  补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20
  async    补下 20 → 成功 20，服务端在飞峰值  5，SHA256 校验 20/20

  断言：四模式全部成功 ✓ 并发上限全部生效 ✓ 校验全部通过 ✓
  同一套协议代码，四种执行模型结果完全一致 —— 统一接口的价值
```

`--twice` 断点续传演示（节选：其前还有一轮普通下载的输出，此处省略）：

```
========================================================
[断点续传：删掉一半文件再跑（只补缺失）]
========================================================
  第二轮补下 10 个（其余跳过），最终校验 20/20
  断点续传 ✓
```

输出里的"在飞峰值"指服务端同一时刻正在处理的请求数的最大值——并发上限是否真的生效由它证明，而不是客户端自报。

诚实预期（本机 3 次实测）：

- **sync 峰值恒为 1**（顺序）、thread/process/async 峰值 = limit（5 或 3 都实测过）——并发上限由服务端计数观测，不是客户端自报
- **四模式文件内容完全一致**：本地服务用固定种子生成文件，每轮 SHA256 清单相同
- **async 轮不含网络不确定因素**：本地回环（loopback，请求不出本机、直接走 127.0.0.1 的网络路径，不经过物理网络）+ 首败必恢复，重试恢复率恒 100%

命令行参数速览：

| 参数 | 作用 |
|---|---|
| `--model` | 选择执行模型：sync / thread / process / async |
| `--limit` | 并发上限 |
| `--verify-all` | 跑全部四种模型并做全部断言 |
| `--twice` | 第二轮只补缺失文件，演示断点续传 |

## How It Works

这节按数据流拆机制：统一入口、续传、服务端观测，以及两个特殊后端。

### 统一入口：协议与执行分离

`download_round(model, limit)` 是全系统唯一入口：
协议层（读清单 → 逐文件下载 → SHA256 校验 → 断点续传判断）写一遍，
四个后端各自实现"并发地执行抓取"。

这是 lab 07 `Executor` 工厂思路的完整版——连 asyncio 也被包进同一签名。
**切换模型不改一行协议代码**。
你在输出里看到的"同一套协议代码，四种执行模型结果完全一致"，就是这条设计的断言。

### 断点续传：文件系统就是状态库

续传不需要数据库：已存在的目标文件就是"已完成"的记录。每轮开始 `pending()` 过滤掉磁盘上已有的文件，只补缺失——`--twice` 输出里"第二轮补下 10 个（其余跳过）"就是这次过滤的结果。

配套纪律：**下载必须原子**（先写临时文件或整块写入，杜绝半截文件被当成"已完成"）；本实验文件整块 `f.write(data)` 天然满足。

### 服务端观测：并发上限要别人证明

客户端声称"我限流了"不算数——本实验的服务端维护 `in_flight` 计数器并记录峰值，四种模式的峰值全部 ≤ limit 才算通过。输出表格里 sync 峰值 1、其余三模式峰值 5（= limit），都是这个计数器报出来的。**资源上限的验收永远在被调用方做**，这是 lab 11 "服务端观测"思想的收口。

### process 后端：唯一走真实网络的模型

sync/thread 共享父进程的本地服务；process 后端真开 N 个子进程，
每个子进程走**真实网络**回连父进程的服务——
这是唯一有跨进程序列化（参数经 pickle——Python 的对象序列化协议——搬运）
与网络栈参与的模型，也因此最有生产味（远端 worker 集群的微缩景观）。

纪律沿用 lab 05：worker 顶层函数、参数可 pickle、`__main__` 保护。

### asyncio 后端：session 的生命周期

**为什么 gather 必须放在 `async with session` 块内？** 第一版把 `asyncio.gather(...)` 写在了 session 上下文外面——session 进入即退出，20 个下载全部撞上 `RuntimeError: Session is closed`。

asyncio 资源的生命周期由上下文管理器界定：**谁开谁关，用时必须在里面**。

## Pitfalls & Q&A

这节收录四条真实踩坑与三个设计追问。

踩坑清单：

- **服务器线程一启动就死**：现象是本地服务起不来；原因是 `asyncio.run(_serve(...))` 在 `_serve` 返回后立刻关循环；解法是服务以 `await Event().wait()` 常驻（跑在 daemon 线程——随主进程退出而终止的后台线程——里，无需显式停止）。
- **子进程模型用 stdin 方式测试**：现象是 `FileNotFoundError`；原因是 spawn（multiprocessing 启动子进程的默认方式：启动全新解释器进程并重新 import 主模块）子进程 re-import `__main__` 时，stdin 场景下 `__file__` 是 `<stdin>`；解法是一切以真实文件入口为准。
- **续传前 reset 目录**：现象是续传变全量重传；原因是 `download_round` 开头无条件 `reset_dir()`，把"保留的另一半"也删了；解法是断点续传的 reset 必须是可选参数。
- **三模型全绿就收工**：现象是第四个模型（async）才暴露 `Session is closed`；原因是路径覆盖不全；解法是每条路径都要跑到断言——"其他三个都过了"不是证据。

**Q1: 如何设计一个"执行模型可切换"的并发框架？**
见上文"统一入口"一节——协议层接口（输入：任务清单 + 并发参数；输出：统一统计），限流/重试/校验放在协议层而不是后端里，后端只回答"用多少个执行体、怎么排队"。

**Q2: 四种执行模型在你的系统里如何做最终选择？**
按负载类型（lab 14 的对决数据）+ 生态约束（已有同步库 → 线程；CPU 密集 → 进程；海量 IO → 协程）+ 运维成本。本实验证明三者可以被统一接口封装——**选型延迟到部署期**。

**Q3: 这个下载器要上生产，还缺什么？**
限流的动态调节（拥塞反馈）、磁盘空间预检、内存流式写入（大文件不全量 read）、失败任务的死信队列（多次重试仍失败的任务的最终存放处，供人工处理）、指标上报。以及最重要：优雅关闭（lab 13）已就位——SIGTERM（`kill` 默认发送的退出信号）后已下载清单不丢。
