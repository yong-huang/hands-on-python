# 02 · 竞态复现与 GIL 边界实测：亲手把 counter 打丢

> 线程交错不可预测只是表象，两个致命追问才是本质：**竞态（多个线程交叠读写共享数据、结果依赖交错时序的缺陷）到底怎么发生的？**
> 和 **GIL（全局解释器锁——同一时刻只允许一个线程执行字节码）到底挡住了什么、放过了什么？** 本实验用可断言的实测给出答案——包括一个
> 反直觉的发现：在 CPython（Python 的官方参考解释器实现）3.13 上，裸 `counter += 1` 根本不会丢，真正咬人的竞态
> 长着另一副面孔。

## Background

这节讲竞态和 GIL 各自从哪里来：单线程时代的默认假设是什么，多线程一开它怎么失效。

没有多线程时，程序的执行结果只由输入决定：同一段代码跑一百遍，顺序、结果都一样。
写代码时默认"这一行执行完才轮到下一行"，`counter += 1` 就是放心地读、加、写三步连做。

引入共享内存的线程（见 [01_thread_lifecycle](../01_thread_lifecycle/README.md)）后，这个假设失效了：
多个执行流在同一份变量上交叠读写，最终结果取决于谁先谁后——
这种"结果依赖交错时序"的缺陷就是竞态（race condition）。

竞态的痛点在于不可稳定复现：开发机上一切正常，负载一高、机器一换就出错，日志里找不到确定的因果。
与此同时，CPython（Python 的官方参考解释器实现）解释器自己也要防止线程把内部状态改坏，它的答案是 GIL
（全局解释器锁——同一时刻只允许一个线程执行字节码的机制；字节码是解释器实际执行的中间指令）。

GIL 稳住了解释器，却带来"操作都安全了"的错觉——本实验实测这层保护的边界到底在哪。

## What

这节给出本实验的两个核心结论：竞态窗口的构成，以及 GIL 的保证范围。

"线程安全"（多线程同时操作数据也不出错的性质）的根基是两个事实：

- **竞态窗口 = 「读出旧值」与「写回新值」之间被插入了别人的完整读写**
- **GIL 只保证切换发生在它自己的检查点（循环回边——循环体执行完跳回开头的位置；调用边界——函数调用的进出位置），不保证你的业务动作原子（原子——不可分割，要么整个做完要么不做）**

沿箭头走一遍最小丢失现场：A 读到 100 → 调用边界被切换 → B 完整做完读 100、写 101 → A 回来接着写 101——B 的 +1 凭空蒸发。

可以把共享变量想象成一块白板：两个工人同时看了一眼 100，各自回工位算出 101，先后回去擦掉重写——后写的覆盖先写的，一次加法就此消失。但和白板不同的是，CPython 的切换只发生在 GIL 检查点，不发生在任意两条指令之间——所以有的写法丢、有的写法不丢，后文实测。

## When to Use

这节回答什么时候需要把竞态和 GIL 纳入考量，以及什么时候可以放心不管。

典型场景——在做什么事的时候要想起来它：

- **多线程共同修改同一份状态时**：计数器、缓存、余额、配置开关——只要有两个线程可能同时读-改-写，就要检查窗口
- **评审并发代码时**：认形状比背口诀可靠，"读旧值、隔一个调用、写回"和"先检查后行动（check-then-act，基于可能已过期的状态做决定）"是两个必须一眼认出的危险形状
- **给计算与 I/O 混合的任务选并发方案时**：先分清瓶颈是计算还是等待——GIL 挡计算不挡等待（实测数据见 Quick Start），两类任务的选型方向完全相反

何时不用：

- **单线程代码**：没有交错就没有竞态，不需要锁
- **状态无共享时**：数据都在局部变量里、或每个线程只碰自己那份，天然无窗口
- **任务量小到偶发偏差无所谓**：为一次性脚本引入锁与同步结构，复杂度得不偿失

同类方案对比（以"共享计数器怎么防丢"为例）：

| 方案 | 与裸读写相比 | 什么时候选它 |
|---|---|---|
| `threading.Lock` | 把读-改-写包成原子段 | 同进程多线程共享状态（见 [03_sync_primitives](../03_sync_primitives/README.md)） |
| `queue.Queue` | 用队列传递数据，消除共享变量 | 生产者消费者结构（见 [04_producer_consumer](../04_producer_consumer/README.md)） |
| `multiprocessing` | 每个进程有独立的 GIL 与内存 | CPU 密集型并行（见 [05_mp_accel](../05_mp_accel/README.md)） |
| `asyncio` | 单线程事件循环（一个线程内循环等待并派发任务的机制），切换只发生在 await 点——即协程（可暂停/恢复的函数）主动让出执行权的位置 | 高并发 I/O（见 [08_coroutine_loop](../08_coroutine_loop/README.md)） |

## Quick Start

这节把实验跑起来并读懂输出；全部结论都由脚本内置断言锁定，可复跑验证。

前置条件：CPython 3.13+（切换检查点位置与版本相关，旧版 CPython 上"裸 += 不丢"的结论不成立）；只需标准库，无第三方依赖。

```bash
cd concurrency/02_race_gil
python3 race_gil.py      # 五个实测小节 + 全部断言，约 10 秒
```

真实输出（§2 节选；§4/§5 省略末尾解释行，完整输出见脚本）：

```
========================================================

========================================================

    第 1 轮: 1,000,000  (丢失 0)
    第 2 轮: 1,000,000  (丢失 0)
    第 3 轮: 1,000,000  (丢失 0)

  实验组 读 20 线程 × 10,000 次，写前隔一次调用:
    第 1 轮:    34,400  (丢失 165,600 次, 82.8%)
    第 2 轮:    54,701  (丢失 145,299 次, 72.6%)
    第 3 轮:    43,072  (丢失 156,928 次, 78.5%)

    第 5 轮:    40,461  (丢失 159,539 次, 79.8%)

  → 丢失规模由调度时机随机决定，5 轮各不相同；加锁是唯一修法（项目 3）

========================================================
[4. CPU 密集：串行 vs 4 线程（数素数，预热后交替 3 轮取中位）]
========================================================

  4 线程: 0.183s   (1.53× 串行)

[5. IO 密集：4 个 0.25s 的模拟网络请求]
========================================================

  4 线程: 0.260s   (3.92× 加速，接近理论 4×)
```

诚实预期（本机 6 次实测）：

- **实验组丢失率在 72%~83% 之间波动，5 轮数值必然各不相同**——丢失多少由 GIL 切换落在哪个窗口随机决定，这正是"竞态不可复现"的本义；断言只锁"全部 < 预期 + 5 轮互异"两条底线
- **CPU 密集减速比 ≈ 1.5×**（10µs 切换间隔放大后；默认 5ms 间隔下 4 线程 ≈ 1.0× 串行，开销小到接近计时噪声，但方向永远不会是加速）
- **IO 加速比稳定 3.9~4.0×**（sleep 期间 GIL 释放，等待完全重叠）

实验用到的工具速览：

| 工具 | 在实验里的用途 |
|---|---|
| `sys.setswitchinterval(1e-6)` | 把 GIL 切换间隔（两次切换检查之间的时长）从默认 5ms 压到 1µs，逼出该发生的切换 |
| `dis` / `compile()` | 把 `counter += 1` 拆成字节码，看清读与写是两条独立指令 |
| `threading.Barrier` | 屏障——让多个线程在同一位置互相等待，把最坏交错钉成必然事件 |

## How It Works

这节逐个解释输出里的数字从哪来：字节码视角的竞态窗口、3.13 的反直觉真相、check-then-act 的确定性复现、两组基准的方法论，以及 GIL 的边界公式。

**竞态窗口在字节码里的样子。**

```python
code = compile("counter += 1", "<race>", "exec")
# LOAD_NAME counter   ← 读旧值
# LOAD_CONST 1
# BINARY_OP +=
# STORE_NAME counter  ← 写新值
```

读与写是两条独立指令。但**指令不原子 ≠ 一定被打断**——是否被打断取决于 GIL 把切换检查点放在哪里。What 节那条" A 读 100 → B 读 100 写 101 → A 写 101"的箭头要成立，前提是窗口恰好罩住了一个检查点。

**反直觉真相：3.13 上裸 `+=` 丢不了。** CPython 3.13 的切换检查点只落在**循环回边和调用边界**，
不落在一条语句的中部。实测：100 线程 × 10000 次裸 `+=`
（把 `sys.setswitchinterval` 压到 1µs 疯狂催促切换），3 轮全部分毫不差。

你在输出里看到的对照组"丢失 0"，就来自这里。

旧教程"两条指令之间随时可能被切开"的说法在当代 CPython 上已经不成立。那窗口在哪？**读-改-写之间隔着一个调用**：

```python
tmp = counter        # 读
audit_hook()         # ← 调用边界是切换检查点：GIL 可能在这里换人
counter = tmp + 1    # 用过期旧值写回 → 丢失
```

真实代码里 `audit_hook()` 就是写日志、查缓存、发 RPC（远程过程调用）——**没有人裸奔 `+=`，但人人都写过这种形状**。输出里实验组 72%~83% 的丢失率全部来自这个形状，这才是生产竞态的本来面目。

**check-then-act：比丢计数更危险的形状。** `if balance >= 100: balance -= 100` 的问题
不在"非原子"本身，而在**决定基于过期状态**。

实验用两道 `Barrier` 把最坏交错钉成确定性事件：6 个线程全员通过检查（都读到 100）、
然后才集体写回——余额 -500，一次不差。

无锁时这个交错不需要 Barrier 也会自然发生，只是时机随机——这正是"竞态不可复现"在生产里的样子：错不每次都犯，但一次就是事故。

**为什么对照实验要压 `sys.setswitchinterval(0.000001)`？** 默认 5ms 间隔下，
一次切换之间一个线程能执行上万条指令，竞态窗口被命中的概率趋近 0——
你会得出"没有竞态"的错误结论。压到 1µs 是把"该发生的切换"全部逼出来，
让窗口命中成为必然事件。

这是测量竞态的标准手法：不是消除随机性，而是提高采样率。

**为什么 CPU 基准要预热 + 交替 + 取中位？** 第一版实现"先串行后线程"单次计时，测出线程 0.91× 反超——假象：串行先跑时 CPU 还在低频，线程后跑时已经升频。预热一轮拉起频率、串行/线程交替各 3 轮取中位，才能把频率漂移和计时噪声从结论里挤出去。

**GIL 的边界：计算串行，等待并行。** CPU 密集任务 4 线程 **1.53× 慢于串行**：
GIL 让同一时刻只有一个线程在执行字节码，总功不变，多出的全是切换与缓存代价。

切换间隔越小心跳越贵（10µs 间隔放大出 1.5×，默认 5ms 下仅 ≈1.0×）。
输出里的 `4 线程: 0.183s` 对应前者。

IO 密集则相反，4 线程 **3.92× 快**：`sleep`/收发包时 CPython 显式释放 GIL，
等待可以重叠——`4 线程: 0.260s` 就来自这里。**记忆公式：GIL 挡计算，不挡等待。**

这决定了 [05_mp_accel](../05_mp_accel/README.md) 用进程绕 CPU 之墙、
[08_coroutine_loop](../08_coroutine_loop/README.md) 用协程（可暂停/恢复的函数）绕 IO 之墙。

而锁（[03_sync_primitives](../03_sync_primitives/README.md)）修的正是本节的竞态。

## Pitfalls & Q&A

这节收录实测过程中的坑（现象 + 原因 + 解法）与常见疑问。

踩坑清单：

- **在默认间隔下"复现不了竞态"就宣称代码线程安全**：现象是测试怎么跑都不丢。原因是默认 5ms 切换太温和，窗口命中概率趋近 0，不等于窗口不存在。解法：压低切换间隔或构造调用边界再测——换台负载重的机器结论可能反转
- **`time.sleep(0)` 当切换点不可靠**：现象是加了 `sleep(0)` 竞态仍复现不出来。原因是它把 CPU 还给调度器（决定哪个线程何时上 CPU 运行的操作系统组件），调度器可能立刻还给同一个线程。解法：用纯函数调用（CALL 边界）做稳定的检查点
- **对"更慢"的基准结果不假思索**：现象是看到线程版比串行慢就急着优化。原因是慢可能来自 GIL 切换税（本实验 §4），也可能来自锁争用（见 [03_sync_primitives](../03_sync_primitives/README.md)）。解法：先分辨原因再动手
- **拿 `dis` 有 LOAD/STORE 就断言"必丢"**：现象是按字节码推理出必丢、实测却分毫不差。原因是指令非原子只是必要条件，还要切换点落在窗口内。解法：两个条件同时满足才算数——实测 3.13 上只有"隔着调用"的形状满足

深入问答：

**Q1: 什么是竞态条件？举一个必然复现的方法。**
多个线程的执行结果依赖交错时序。复现不要赌调度运气：要么往读-改-写窗口里塞一个调用让窗口常开，要么用两道 Barrier 把最坏交错定格成必然（How It Works 里 check-then-act 一节的做法）——复现是修复的前提。

**Q2: CPython 的 GIL 是什么？它保证什么、不保证什么？**
定义见 What 节的两个事实，边界见 How It Works 的"计算串行，等待并行"。一句话版本：GIL 保证解释器内部同一时刻只有一个线程执行字节码，不保证你的业务动作原子。

**Q3: 既然有 GIL，为什么还需要 Lock？**
GIL 保护的是解释器，不是你的不变量（必须时刻为真的业务规则，例如"余额永不为负"）。6 个线程全部通过余额检查再集体扣款，
每个字节码都被 GIL 保护着，但"余额永不为负"这条业务规则照样被击穿。

GIL 管字节码原子性，Lock 管业务原子性——
见 [03_sync_primitives](../03_sync_primitives/README.md)。
