# 02 · 竞态复现与 GIL 边界实测：亲手把 counter 打丢

> 线程交错不可预测只是表象，两个致命追问才是本质：**竞态到底怎么发生的？**
> 和 **GIL 到底挡住了什么、放过了什么？** 本实验用可断言的实测给出答案——包括一个
> 反直觉的发现：在 CPython 3.13 上，裸 `counter += 1` 根本不会丢，真正咬人的竞态
> 长着另一副面孔。

## What

"线程安全"的根基是两个事实：**竞态窗口 = 「读出旧值」与「写回新值」之间被插入了别人的完整读写；GIL 只保证切换发生在它自己的检查点（循环回边、调用边界），不保证你的业务动作原子**。沿箭头走一遍：A 读到 100 → 调用边界被切换 → B 完整做完读 100、写 101 → A 回来接着写 101——B 的 +1 凭空蒸发。

## Why

"线程安全"三个字背起来容易，但只有亲手复现过丢失更新、亲眼在字节码层面看过竞态窗口、亲手量出 GIL 对 CPU 与 IO 密集任务**方向相反**的影响，你才能在代码评审时一眼认出危险形状，而不是背口诀。本实验全部结论来自本机实测，每条都可断言复跑——这也是后续所有实验的对比基准：锁（[03_sync_primitives](../03_sync_primitives/README.md)）修的就是这里的竞态，asyncio（[08_coroutine_loop](../08_coroutine_loop/README.md)）绕的就是这里的 IO 之墙，multiprocessing（[05_mp_accel](../05_mp_accel/README.md)）绕的就是这里的 CPU 之墙。

诚实预期（本机 6 次实测）：

- **实验组丢失率在 72%~83% 之间波动，5 轮数值必然各不相同**——丢失多少由 GIL 切换落在哪个窗口随机决定，这正是"竞态不可复现"的本义；断言只锁"全部 < 预期 + 5 轮互异"两条底线
- **CPU 密集减速比 ≈ 1.5×**（10µs 切换间隔放大后；默认 5ms 间隔下 4 线程 ≈ 1.0× 串行，开销小到接近计时噪声，但方向永远不会是加速）
- **IO 加速比稳定 3.9~4.0×**（sleep 期间 GIL 释放，等待完全重叠）

### 竞态窗口在字节码里的样子

```python
code = compile("counter += 1", "<race>", "exec")
# LOAD_NAME counter   ← 读旧值
# LOAD_CONST 1
# BINARY_OP +=
# STORE_NAME counter  ← 写新值
```

读与写是两条独立指令。但**指令不原子 ≠ 一定被打断**——是否被打断取决于 GIL 把切换检查点放在哪里。

### 反直觉真相：3.13 上裸 `+=` 丢不了

CPython 3.13 的切换检查点只落在**循环回边和调用边界**，不落在一条语句的中部。实测：100 线程 × 10000 次裸 `+=`（把 `sys.setswitchinterval` 压到 1µs 疯狂催促切换），3 轮全部分毫不差。旧教程"两条指令之间随时可能被切开"的说法在当代 CPython 上已经不成立。

那窗口在哪？**读-改-写之间隔着一个调用**：

```python
tmp = counter        # 读
audit_hook()         # ← 调用边界是切换检查点：GIL 可能在这里换人
counter = tmp + 1    # 用过期旧值写回 → 丢失
```

真实代码里 `audit_hook()` 就是写日志、查缓存、发 RPC——**没有人裸奔 `+=`，但人人都写过这种形状**。这才是生产竞态的本来面目。

### check-then-act：比丢计数更危险的形状

`if balance >= 100: balance -= 100` 的问题不在"非原子"本身，而在**决定基于过期状态**。实验用两道 `Barrier` 把最坏交错钉成确定性事件：6 个线程全员通过检查（都读到 100）、然后才集体写回——余额 -500，一次不差。无锁时这个交错不需要 Barrier 也会自然发生，只是时机随机。

## Deep Dive

**为什么对照实验要压 `sys.setswitchinterval(0.000001)`？**
默认 5ms 间隔下，一次切换之间一个线程能执行上万条指令，竞态窗口被命中的概率趋近 0——你会得出"没有竞态"的错误结论。压到 1µs 是把"该发生的切换"全部逼出来，让窗口命中成为必然事件。这是测量竞态的标准手法：不是消除随机性，而是提高采样率。

**为什么 CPU 基准要预热 + 交替 + 取中位？**
第一版实现"先串行后线程"单次计时，测出线程 0.91× 反超——假象：串行先跑时 CPU 还在低频，线程后跑时已经升频。预热一轮拉起频率、串行/线程交替各 3 轮取中位，才能把频率漂移和计时噪声从结论里挤出去。

**GIL 的边界：计算串行，等待并行。**
CPU 密集任务 4 线程 **1.53× 慢于串行**：GIL 让同一时刻只有一个线程在执行字节码，总功不变，多出的全是切换与缓存代价；切换间隔越小心跳越贵（10µs 间隔放大出 1.5×，默认 5ms 下仅 ≈1.0×）。而 IO 密集 4 线程 **3.92× 快**：`sleep`/收发包时 CPython 显式释放 GIL，等待可以重叠。**记忆公式：GIL 挡计算，不挡等待**——这决定了 [05_mp_accel](../05_mp_accel/README.md) 用进程绕 CPU 之墙、[08_coroutine_loop](../08_coroutine_loop/README.md) 用协程绕 IO 之墙。

踩坑清单：

- **在默认间隔下"复现不了竞态"就宣称代码线程安全**：切换太温和 ≠ 窗口不存在，换台负载重的机器就炸
- **`time.sleep(0)` 当切换点不可靠**：它把 CPU 还给调度器，调度器可能立刻还给同一个线程；纯函数调用（CALL 边界）才是稳定的检查点
- **对"更慢"的基准结果不假思索**：线程版更慢可能是 GIL 切换税（本实验），也可能是锁争用（项目 3）——先分辨再优化
- **拿 `dis` 有 LOAD/STORE 就断言"必丢"**：指令非原子只是必要条件，还要切换点落在窗口内——两个条件实测 3.13 只同时满足"隔着调用"的形状

## Q&A

**Q1: 什么是竞态条件？举一个必然复现的方法。**
多个线程的执行结果依赖交错时序。复现竞态不要赌调度运气：要么把读-改-写窗口里塞一个调用让窗口常开，要么像本实验用两道 Barrier 把最坏交错定格成必然——复现是修复的前提。

**Q2: CPython 的 GIL 是什么？它保证什么、不保证什么？**
它保证同一时刻只有一个线程执行 Python 字节码（解释器内部状态安全）；它**不**保证你的业务操作原子——`counter += 1` 的读改写之间隔着调用边界就可能被打断（实测丢失 72~83%）。

**Q3: 既然有 GIL，为什么还需要 Lock？**
GIL 保护的是解释器，不是你的不变量。6 个线程全部通过余额检查再集体扣款，每个字节码都被 GIL 保护着，但"余额永不为负"这条业务规则照样被击穿。GIL 管字节码原子性，Lock 管业务原子性——见 [03_sync_primitives](../03_sync_primitives/README.md)。
