# 11 · 异步 IO 实战——本地批量抓取器：aiohttp 三件套

> 队列、信号量、背压这套异步流水线骨架，接到真实 HTTP 协议上是什么样？实验内置一个
> 可控的本地 aiohttp 服务：50 个端点、30-80ms 延迟、15 个"首败必恢复"的不稳定端点
> ——离线可跑、确定性可断言。三种客户端模型同题对决：串行 3.6s / 线程池 0.4s / 异步 0.4s。

## Background

这节讲异步抓取器从哪来。抓一批 URL 的传统写法是 `requests` 加串行循环：一个抓完再抓下一个；嫌慢就换线程池，几十个工作线程分头抓。50 个延迟 30-80ms 的端点，串行要把每笔延迟全额累加，等好几秒。

线程池能重叠等待，但天花板明显：每个并发占一个真实线程，开到几百并发时线程本身的内存和切换开销成了新负担。更麻烦的是真实网络的抖动——偶发 5xx、慢端点、瞬时失败，裸客户端一遇抖动就整批报错，失败处理全靠散落的 if/else。

异步方案（aiohttp——基于 asyncio 的异步 HTTP 客户端/服务器库）把"等待"变成廉价资源：单线程挂起成百上千个请求。等待便宜了，剩下的乱象靠三件手段收编——限流、超时、重试；这三件套随后成为所有生产级异步客户端的标配。

## What

这节给出定义与心智模型。异步批量抓取器指在事件循环（event loop，单线程内调度并切换多个协程——协程即 coroutine，用 async def 定义、能在 await 点暂停和恢复的函数——的引擎）内并发发起大量 HTTP 请求的客户端。

抓取器对限流（Semaphore 控制同时在飞的请求数）、超时（给单个请求设 deadline）、重试（失败后按策略再试）做统一管理。

三件套各管一类失败：限流防打爆、超时防挂死、重试防抖动失败。

一句话心智模型：**同一组 50 个端点，三种模型各抓一遍——串行付全款（每个延迟都等）、线程池付 10 份、异步付 10 份但不占线程**；15 个不稳定端点第一次必失败，重试三件套让失败不再致命。

可以把三种并发模型想成排队买票：串行是排 50 次队，线程池是雇 10 个人分头排，异步是一个人攥着 50 张号同时等叫号；但和雇人不同的是，"拿号等叫"不占人手——异步的等待不占用线程，这正是它并发便宜的根源。

## When to Use

这节补判断力：什么活儿值得上异步客户端。主线看两件事——并发量是否大到线程嫌贵，以及对抖动的容忍度是否低到必须显式管理失败。

典型场景：

- **批量抓取/同步数据**：几百上千个 URL 或接口要拉，既要快（并发便宜），也要稳（超时+重试兜住抖动）。
- **调用不稳定上游**：依赖的第三方服务偶发 5xx 或超时，需要 deadline 和指数退避（exponential backoff，每次重试前把等待时间翻倍）避免整批失败。
- **给客户端写集成测试**：像本实验一样起一个本地可控服务，把抖动变成确定性，行为才能写成断言。

何时不用：只抓两三个页面的脚本，`requests` 串行最省事；页面要执行 JS 才能出内容，aiohttp 拿不到完整渲染结果，得用无头浏览器方案；CPU 密集的解析占大头时，瓶颈不在等待，异步无能为力。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `requests`（串行） | 简单直观，延迟全额累加 | 少量请求、脚本级工具 |
| 线程池 + `requests` | 几十并发，阻塞线程 | 已有 requests 代码、并发需求不高 |
| `aiohttp` + asyncio | 并发便宜，需异步生态 | 大批量、高并发 I/O |
| `httpx` | API 兼容 requests，同步/异步双模 | 一套代码要两种模式 |

## Quick Start

前置条件：安装 aiohttp（全系列唯一第三方依赖）；服务端内置，全程 127.0.0.1 本地服务，断网也能跑。阻塞、状态污染、策略不对等三类坑，脚本都真实踩一遍并写进断言：

```bash
cd concurrency/11_async_fetcher
pip install aiohttp           # 全系列唯一第三方依赖（实验 11 专属）
python3 async_fetcher.py      # 约 5 秒
```

脚本按串行 → 线程池 → 异步依次运行三种模型，结果集中在"三模型对决"一个小节。真实输出（首尾的版本行与断言横幅略）：

```
========================================================
[三模型对决：50 个端点（15 个不稳定）]
========================================================
  串行:     50/50 成功，65 次请求，3.60s
  线程池:   50/50 成功，0.43s
  异步:     50/50 成功，65 次请求，0.42s（首次失败 15 个，重试恢复 15 个）

  加速比: 异步 = 串行的 1/8.6；与线程池同并发下打平
  重试恢复率: 100%（不稳定端点全部救回）
  同并发 = 同等待重叠，打平是理论必然；异步的真正优势在'并发便宜'（见 README Q&A）
  三件套各司其职：Semaphore 限流防打爆、超时防挂死、退避重试救回失败
```

诚实预期（本机 5 次实测）：

- **异步与线程池打平（±20% 内）是理论必然**：同为 10 并发，等待重叠程度相同，断言只要求异步不明显慢于线程池。要在数字上看到异步赢，得并发到线程开不起的量级（数百并发）
- **不稳定端点的失败是确定性的**：服务端记录"首败必恢复"状态，每个模型用全新服务实例，重试恢复率恒 100%
- **串行 65 次请求**：50 正常 + 15 次首败重试；断言的是"全部成功"而非请求数

异步抓取的核心写法浓缩为三行，这段在做什么：`async with sem` 先取许可（限流），`session.get(..., timeout=...)` 给单请求 5 秒总超时（超时），失败则按 20/40/80/160ms 递增等待后再试（重试）——三件套的一次完整循环：

```python
async with sem:                          # 限流：同时在飞 ≤ 10
    async with session.get(url, timeout=aiohttp.ClientTimeout(total=5)) as resp:
        if resp.status == 200: return
await asyncio.sleep(0.02 * 2 ** (attempt - 1))   # 重试：指数退避 20/40/80/160ms
```

## How It Works

这节拆三件事：三件套为什么缺一不可、测试服务怎么把抖动变确定性、以及事件循环里阻塞调用的代价，并与上面的输出互相印证。

### 三件套各司其职：快 vs 稳

Semaphore 保证"打不死别人也撑不爆自己"：同时在飞（in-flight，已发出尚未完成）的请求数被钳在许可数内。超时保证慢端点不拖垮整体——挂死比失败更贵，失败能重试，挂死只能干等。

指数退避给抖动服务恢复时间，避免重试风暴。组合起来才是生产级客户端：只有裸 get 的异步代码只是"快"，不是"稳"。输出里"重试恢复率: 100%"就是三件套协同的战绩。

### 测试服务：把"抖动"变成确定性

测试服务对 15 个端点记录 `failed_once` 状态：第一次请求返回 500，之后恢复。这比"随机 30% 失败"好在一个决定性性质——**重试恢复率可以写成断言**（随机失败下重试 5 次仍全败的概率 ~11%，断言会 flake——时灵时不灵地随机挂）。测试基础设施的确定性 > 真实性。

### 事件循环的一等公民与二等公民

本实验开发中真实踩雷：把串行基准直接写在事件循环线程里，客户端一阻塞，同一循环里的服务端也停摆——互相等死直到超时。修复：`asyncio.to_thread()` 把阻塞基准丢进工作线程，让循环保持响应。

阻塞调用卡住整个循环的后果：所有协程停摆、同循环的服务端无法响应、超时机制失效。

### 对比实验的公平性：每组从相同初始状态出发

```python
runner, base = await start_server()      # 每个模型一个全新服务
ok_s, att_s, t_serial = await asyncio.to_thread(fetch_serial, base)
await runner.cleanup()
```

服务的"首败必恢复"状态存在服务进程内存里。若三个模型共用一个实例，串行模型先跑就会消费掉全部 15 次"首次失败"，后面模型的恢复率统计全部失真。**对比实验的每组样本必须从相同初始状态出发**——隔离失败状态，而不是假装它不存在。诚实预期第二条"每个模型用全新服务实例"就是这个意图。

## Pitfalls & Q&A

这节收五个踩坑点和三个选型问答，踩坑按"现象 → 原因 → 解法"组织。

- **在事件循环线程里调阻塞函数**。现象：客户端一开跑，同循环的本地服务端停摆，互相等死 5 秒超时。原因：阻塞调用冻结整个循环（机制见"一等公民"一节）。解法：阻塞代码一律 `asyncio.to_thread()`（见 lab 08 踩坑清单）。
- **重试策略不对等导致基准失真**。现象：异步模型在对比里莫名"输"了 0.03s。原因：第一版异步有指数退避、线程版立即重试，策略不对等。解法：对比实验的各变量必须同策略。
- **`runner.cleanup()` 忘记 await**。现象：结束时打 RuntimeWarning，服务没被清理，端口泄漏。原因：cleanup 是协程，不 await 就不执行。解法：`await runner.cleanup()`。
- **响应体不读就重试**。现象：失败的连接迟迟不释放。原因：500 的响应留着不读，连接不归还。解法：`async with resp` 的上下文退出会处理；手写裸连接时要显式 read。
- **拿 HTTPError 只捕 URLError**（urllib 的异常类型）。现象：超时异常穿透重试逻辑直接炸。原因：`socket.timeout`（TimeoutError）不是 URLError 子类。解法：捕 `OSError` 才是网罗全部网络错误的写法。

**Q1: 异步客户端为什么快？快在哪？**
不是"单线程更快"，而是**等待成本为零**：50 个请求的等待时间重叠在一张调度表上，
串行要累加每个延迟（实测 3.6s），异步只付总延迟/并发度（实测 0.4s）。
CPU 计算它一分钱省不了。

追问"比线程快吗"：同并发（10）下打平——等待重叠程度相同；
异步的优势在并发便宜（万级协程 vs 几十线程到顶）。

**Q2: 为什么需要 Semaphore？aiohttp 不是有连接池吗？**
连接池限制的是连接数，Semaphore 限制的是"在飞请求数"——包括连接、发送、等待响应全程。目标服务的并发承受力与你的连接数是两回事；限流是主动保护语义，连接池只是资源复用。

**Q3: 重试为什么用指数退避而不是立即重试？**
立即重试在服务端刚抖动时火上浇油（重试风暴）；指数退避 20→40→80ms 给服务恢复窗口，还能加抖动（jitter）防止客户端同步重试。本实验服务端"首败必恢复"设计下，一次重试就够——退避是为了真实世界的普适性。
