# 11 · 异步 IO 实战——本地批量抓取器：aiohttp 三件套

> 项目 10 的流水线骨架（队列/信号量/背压）这一篇接到真实 HTTP 协议上。内置一个
> 可控的本地 aiohttp 服务：50 个端点、30-80ms 延迟、15 个"首败必恢复"的不稳定端点
> ——离线可跑、确定性可断言。三种客户端模型同题对决：串行 3.6s / 线程池 0.4s / 异步 0.4s。

## 1. 为什么需要它

异步三件套——**限流**（Semaphore 防打爆）、**超时**（防挂死）、**重试**（防抖动失败）——是所有生产级异步 IO 客户端的标配，但纸上看和跑起来是两回事：阻塞函数会卡死整个事件循环、服务端状态会污染对比实验、重试策略不对等会让基准失真。本实验把这些坑全部真实踩一遍并写进断言。全程 127.0.0.1 本地服务，断网也能跑。

## 2. 总览：核心机制一图看懂

一句话心智模型：**同一组 50 个端点，三种模型各抓一遍——串行付全款（每个延迟都等）、线程池付 10 份、异步付 10 份但不占线程**。看图：三行客户端都汇入中央本地服务（15 个不稳定端点第一次必失败），右侧统计节点记录"50/50 成功、重试恢复率 100%"——重试三件套让失败不再致命。

诚实预期（本机 5 次实测）：

- **异步与线程池打平（±20% 内）是理论必然**：同为 10 并发，等待重叠程度相同，断言只要求异步不明显慢于线程池。要在数字上看到异步赢，得并发到线程开不起的量级（数百并发）
- **不稳定端点的失败是确定性的**：服务端记录"首败必恢复"状态，每个模型用全新服务实例，重试恢复率恒 100%
- **串行 65 次请求**：50 正常 + 15 次首败重试；断言的是"全部成功"而非请求数

## 4. 核心概念

### 4.1 异步三件套：限流、超时、重试

```python
async with sem:                          # 限流：同时在飞 ≤ 10
    async with session.get(url, timeout=aiohttp.ClientTimeout(total=5)) as resp:
        if resp.status == 200: return
await asyncio.sleep(0.02 * 2 ** (attempt - 1))   # 重试：指数退避 20/40/80/160ms
```

三件套各司其职：Semaphore 保证"打不死别人也撑不爆自己"；超时保证慢端点不拖垮整体（挂死比失败更贵）；指数退避给抖动服务恢复时间，避免重试风暴。组合起来才是生产级客户端——只有裸 get 的异步代码只是"快"，不是"稳"。

### 4.2 可控测试服务：把"抖动"变成确定性

测试服务对 15 个端点记录 `failed_once` 状态：第一次请求返回 500，之后恢复。这比"随机 30% 失败"好在一个决定性性质——**重试恢复率可以写成断言**（随机失败下重试 5 次仍全败的概率 ~11%，断言会 flake）。测试基础设施的确定性 > 真实性。

### 4.3 事件循环里的一等公民与二等公民

aiohttp 客户端是协程（一等公民），`urllib.urlopen` 是阻塞调用（二等公民）。本实验开发中真实踩雷：**把串行基准直接写在事件循环线程里，客户端一阻塞，同一循环里的服务端也停摆**——互相等死直到超时。修复：`asyncio.to_thread()` 把阻塞基准丢进工作线程，让循环保持响应。

## 5. 关键代码解析

**为什么每个模型都用全新服务实例？**

```python
runner, base = await start_server()      # 每个模型一个全新服务
ok_s, att_s, t_serial = await asyncio.to_thread(fetch_serial, base)
await runner.cleanup()
```

服务的"首败必恢复"状态存在服务进程内存里。若三个模型共用一个实例，串行模型先跑就会消费掉全部 15 次"首次失败"，后面模型的恢复率统计全部失真。**对比实验的每组样本必须从相同初始状态出发**——隔离失败状态，而不是假装它不存在。

坑清单：

- **在事件循环线程里调阻塞函数**：本实验最大教训——串行基准直接跑在循环里，服务端同循环运行，互相等死 5 秒超时。阻塞代码一律 `asyncio.to_thread()`（呼应项目 8 坑清单）
- **重试策略不对等导致基准失真**：第一版异步有指数退避、线程版立即重试，异步"输"了 0.03s——对比实验的各变量必须同策略
- **`runner.cleanup()` 忘记 await**：cleanup 是协程，不 await 服务不清理（RuntimeWarning 提示），端口泄漏
- **响应体不读就重试**：500 的响应留着不读，连接迟迟不释放；`async with resp` 的上下文退出会处理，但手写裸连接时要显式 read
- **拿 HTTPError 只捕 URLError**：`socket.timeout`（TimeoutError）不是 URLError 子类——超时会穿透重试直接炸；捕 `OSError` 才是网罗全部网络错误的姿势

## 7. 深入要点

**Q1: 异步客户端为什么快？快在哪？**
不是"单线程更快"，而是**等待成本为零**：50 个请求的等待时间重叠在一张调度表上，串行要累加每个延迟（实测 3.6s），异步只付总延迟/并发度（实测 0.4s）。CPU 计算它一分钱省不了。追问"比线程快吗"：同并发（10）下打平——等待重叠程度相同；异步的优势在并发便宜（万级协程 vs 几十线程到顶）。

**Q2: 为什么需要 Semaphore？aiohttp 不是有连接池吗？**
连接池限制的是连接数，Semaphore 限制的是"在飞请求数"——包括连接、发送、等待响应全程。目标服务的并发承受力与你的连接数是两回事；限流是主动保护语义，连接池只是资源复用。

**Q3: 重试为什么用指数退避而不是立即重试？**
立即重试在服务端刚抖动时火上浇油（重试风暴）；指数退避 20→40→80ms 给服务恢复窗口，还能加抖动（jitter）防止客户端同步重试。本实验服务端"首败必恢复"设计下，一次重试就够——退避是为了真实世界的普适性。

**Q4: 怎么测试"会随机失败的"异步客户端？**
把随机性变成确定性状态机：服务端记录"该端点已失败过一次"（首败必恢复），恢复率就从概率变成断言。随机性适合压测吞吐，确定性适合验证逻辑。

**Q5: 事件循环里混用阻塞库会怎样？**
阻塞调用卡住整个循环：所有协程停摆、服务端（若同循环）无法响应、超时机制失效——本实验的串行基准第一版就因此死锁。方案：换异步库，或 `loop.run_in_executor` / `asyncio.to_thread` 丢进线程。

## 8. 总结

1. **异步三件套**：Semaphore 限流 + 超时兜底 + 指数退避重试，缺一不稳
2. **可控测试服务**：首败必恢复的确定性设计，让恢复率成为断言而不是运气
3. **阻塞代码必须离开事件循环线程**：to_thread 是桥，留在原地就是互等死锁
4. **对比实验要同策略同起点**：重试策略对等、服务状态隔离，数字才有意义
5. **异步优势 = 等待重叠**：50 端点 1/8.7 耗时，规模越大差距越大（万级并发才是主场）
