# 05 · multiprocessing 多核加速实测：绕开 GIL 的真并行

> Python 多线程受 GIL（全局解释器锁——同一时刻只允许一个线程执行字节码）限制，CPU 密集任务开再多线程也不加速。
> 本实验用标准库 `multiprocessing` 为每个任务开一个独立解释器进程、配一把独立 GIL，实测 CPU 密集任务 2.5× 加速，同题 threading 对照只有 0.75×；
> 并复现 macOS 默认 spawn 启动方式（子进程会重新 import 主模块）下漏写 `__main__` 保护的静默失败。
> 读完本篇，你能判断什么任务值得上多进程，并拿到 Pool（进程池）保序、启动成本、pickle 限制（worker 函数与参数必须能被 pickle——Python 的对象序列化机制——打包运输）三个工程要点。

## Background

这节回答三个问题：多进程方案出现之前 Python 程序怎么做并发、那条路在计算密集场景为什么走不通、多进程方案如何应运而生。

在 `multiprocessing` 之前，Python 做并发的默认工具是线程（`threading`）：多个执行流共享同一个解释器的内存，创建成本低，由操作系统负责调度。想让任务"同时跑"，常规写法就是把任务函数丢给几个 `Thread`，期待四个任务落在四个核上。

撞墙点在 CPython（Python 官方的参考解释器实现，python3 命令运行的就是它）的 GIL 上：这把锁规定同一时刻只有一个线程执行字节码。4 个素数计数任务串行跑完要 0.49 秒，换成 4 个线程"同时"跑，实测反而要 0.66 秒——锁争用不但没加速，还要倒贴一笔。

受害的是 CPU 密集任务（瓶颈在算力、不在等待外部 IO 的任务）：它们被 GIL 彻底串行化。IO 密集任务（大部分时间在等网络或磁盘）不受此限，等待时会释放 GIL，所以线程在 IO 场景仍然够用。

出路在操作系统层面：进程（操作系统分配资源的基本单位，拥有独立内存空间）各自带一个完整解释器，而 GIL 是每解释器一把——各进程的锁互不相干，字节码就能真正同时执行。标准库 `multiprocessing` 把"开进程、分发任务、回收结果"这套样板封装成几个类，让多进程并行像开线程一样好写，这就是本实验的主角。

## What

这节给出 `multiprocessing` 的定义、一次任务分发的流程概览，以及一个承载后续机制的心智模型。

`multiprocessing` 是 Python 标准库提供的多进程并行方案：它把任务交给多个独立的 Python 解释器进程执行，每个进程持有一把独立 GIL，因此 CPU 密集任务能真正同时跑在多个核上，绕开线程模型的串行化。

一次 `pool.map`（向进程池批量提交任务的调用）从提交到收工只有三步：

1. **提交**——主进程把任务列表切块，分发给池（`Pool`，预先启动固定数量 worker、让它们循环领任务的结构）里的 worker（池中领任务干活的工作进程）；
2. **并行执行**——spawn 出的各个子进程同时计算自己领到的那一块；
3. **汇合**——结果按输入顺序（而非完成顺序）返回主进程。

可以把这套机制想象成连锁餐厅的中央派单：总部（主进程）把订单分给四家分店（四个子进程），每家分店有全套独立厨房（各自的解释器、GIL 与内存），同时开工，出餐按下单顺序摆上同一张桌（结果按输入顺序汇合）。

但和连锁店不同的是：分店之间不能直接伸手拿对方冰箱里的食材——任何传参与返回值都要经过 pickle（Python 的对象序列化机制，把对象转成字节流以便跨进程传输）打包运送，这份物流成本正是多进程方案的核心代价。

## When to Use

这节讲什么场景值得上多进程、什么场景应该换方案，以及同类工具怎么选。

- **批量纯计算**：对一批互相独立的数据项各做一次重计算——批量生成缩略图、数值模拟扫参数、对几万个字符串各算一次哈希。每一项都计算量大、不等待外部 IO 时，切块交给进程池，总耗时近似除以核数。
- **长时离线作业**：特征工程、日志聚合、批量渲染这类一跑几分钟以上的作业——spawn 的零点几秒启动成本可以忽略，把单核跑满改成多核并行就是纯收益。

何时不用：

- **IO 密集任务**：瓶颈在等网络、等磁盘，进程等待时整个解释器闲置——进程等 IO 是浪费一张解释器票，线程或协程更省。
- **单任务只有毫秒级**：spawn 一次约 0.3~0.5 秒（见 Quick Start 的诚实预期），启动成本吞掉全部收益甚至倒挂。
- **任务间需要高频共享状态**：进程隔离让每次共享都过一遍序列化；确需共享内存，走 `SharedMemory`（跨进程共享的内存块），见 [06_ipc_shared](../06_ipc_shared/README.md)。

同类方案对比：

| 方案 | 与 multiprocessing 的差异 | 什么时候选它 |
|---|---|---|
| `threading` 线程 | 共享内存，受 GIL 串行化 | IO 密集任务的默认选择 |
| `concurrent.futures` 线程池 | 线程版任务池，接口与进程池同名（`map`/`submit`） | IO 密集且想统一池接口 |
| `concurrent.futures` 进程池 | 同为多进程，接口更现代，支持按完成顺序收结果 | 需要流式收结果，见 [07_futures](../07_futures/README.md) |
| `asyncio` 协程 | 单线程事件循环，不靠多核 | 万级并发连接的 IO 场景，见 [08_coroutine_loop](../08_coroutine_loop/README.md) |

## Quick Start

实验只依赖标准库，无需安装第三方包，完整脚本在实验目录的 `mp_accel.py`。

```bash
cd concurrency/05_mp_accel
python3 mp_accel.py      # 四个实测小节 + 全部断言，约 15 秒
```

这段命令在做什么：脚本依次量出 CPU 密集任务的加速比、复现漏写 `__main__` 保护的静默失败、验证 `pool.map` 的保序承诺，最后运行全部断言。

真实输出（节选）：

```

========================================================
  串行 4 连跑:  0.492s
  Pool(4):      0.197s   (2.50× 加速)
  对照（同一任务 threading 4 线程）——GIL 下白忙:
  threading(4): 0.660s   (0.75×，不加速)
  多进程 = 每个进程一把独立 GIL，字节码真并行

========================================================

========================================================
  父进程退出码 0，stdout = 'OK 1'  ← 看起来一切正常！
  真相在 stderr：子进程 re-import 主模块时再次执行 p.start()，
  抛 RuntimeError '...before the current process has finished its bootstrapping phase...'，
  子进程 exitcode=1 尸退，worker 结果悄悄丢失——静默失败，比当场崩溃更危险
  规矩：入口代码必须 if __name__ == '__main__' 保护

[4. pool.map 保序：慢任务在前，结果仍按输入顺序]

```

诚实预期（本机 4 次实测）：

- **加速比 2.4~3.2× 波动**：M 系列芯片性能核/能效核混排，4 个子进程落在哪几颗核由调度器决定；断言只锁 ≥2.0× 底线
- **threading 对照 0.75~0.78×**：不是加速 1.0 倍，是**负加速**——GIL 争用还有倒贴
- **spawn 启动成本约 0.3~0.5s**：所以任务规模要够大（本实验 15 万素数）摊薄它，任务太小会得出"多进程更慢"的误判

写自己的多进程脚本时，常用到这几个 API：

| API | 作用 | 备注 |
|---|---|---|
| `multiprocessing.Pool(n)` | 预启动 n 个 worker 进程组成池 | 池的创建是一次性成本，建好应复用 |
| `pool.map(func, iterable)` | 任务分块分发，结果按输入顺序整批返回 | 会等全部任务完成 |
| `pool.imap` / `pool.imap_unordered` | 流式逐个产出结果 | 后者完成即产出，不保输入顺序 |
| `multiprocessing.Process(target=f)` | 手动启动单个子进程 | 本实验用它复现 `__main__` 陷阱 |
| spawn / fork | 子进程的两种启动方式 | macOS 与 Windows 默认 spawn |

## How It Works

这节把 Quick Start 输出里的三段现象逐一对应到底层机制，并补上计时方法与任务规模的算账方式。

### 独立解释器：2.50× 从哪来

`Process` 启动的是一个完整的新解释器——自己的 GIL、自己的堆、自己的模块状态。CPU 密集任务在 4 个进程里就是 4 份真并行计算，输出里的 `2.50× 加速` 与那行"多进程 = 每个进程一把独立 GIL，字节码真并行"就来自这里。

代价随之而来：

- spawn 启动一个子进程要 50-100ms（重新 import 一切）；
- 所有传参和返回值都要过 pickle 序列化；
- 跨进程改一个全局变量是不可能的——各改各的副本，真正的共享与通信见 [06_ipc_shared](../06_ipc_shared/README.md)。

### spawn 与 `__main__` 保护：静默失败如何发生

macOS 默认 spawn：子进程启动时会重新 import 主模块。入口代码若不躲在 `if __name__ == '__main__'` 后面，子进程 import 时又会执行 `p.start()`，在子进程里抛 `RuntimeError: ...bootstrapping phase...` 后带伤退场。

父进程毫不知情：照常打印 OK、照常 exit 0，worker 的结果悄悄丢了。输出第 [3] 小节里"父进程退出码 0，stdout = 'OK 1'"正是这个现场——真相只在 stderr 的 traceback 里，子进程 exitcode=1 被当成了"正常数据"。

崩溃会喊，静默失败只能靠检查 exitcode 发现。

### `Pool` 与 `map` 的保序承诺

`Pool(n)` 预启动 n 个 worker，`pool.map(func, iterable)` 把任务分块分发，承诺结果严格按输入顺序返回，哪怕各任务完成时间乱序。

输出第 [4] 小节用"最慢任务先提交"验证：输入 [0.3, 0.1, 0.2, 0.05]，返回仍是同样顺序；总耗时 0.35s ≈ 最慢任务 0.3s，证明 4 个任务确实并行了。代价是全批等齐。

需要"完成一个收一个"时，改用 `imap_unordered`，或 concurrent.futures 的 `as_completed`（按完成顺序逐个取结果的接口，见 [07_futures](../07_futures/README.md)）。

### 计时方法：Pool 创建为什么放在计时外

```python
def bench_once(n_procs):
    with multiprocessing.Pool(n_procs) as pool:   # spawn 成本在计时外
        t0 = time.perf_counter()
        pool.map(cpu_task, [CPU_N] * n_procs)
        return time.perf_counter() - t0
```

池创建是一次性成本（spawn 4 个解释器），生产中池会复用成百上千次任务，把它算进单次任务会低估加速比。但也要诚实——首次使用的用户确实要付这笔钱，所以诚实预期把"spawn 启动成本约 0.3~0.5s"单列。

### 任务规模的隐藏门槛

多进程的收益公式：`加速 ≈ 总功 / (总功/n + 启动成本)`。任务太小，spawn 成本吞掉全部收益甚至倒挂——本实验用 15 万规模的素数计数把单任务拉到 ~0.15s，4 任务总功 0.6s，启动 0.4s 摊薄后仍剩 2.5×。先算这笔账，再决定要不要多进程。

## Pitfalls & Q&A

这节收集五个常见坑（现象 + 原因 + 解法）和两个延伸问答。

### 踩坑清单

- **嵌套函数/lambda 传给 Pool**：现象是 pickle 抛 `Can't get local object`，当场报错。原因：spawn 按限定名 pickle 目标函数，lambda、闭包内函数、实例方法绑定的匿名对象没有稳定限定名。解法：worker 必须是模块顶层函数，或用 `functools.partial` 包顶层函数。
- **漏写 `__main__` 保护**：现象是父进程照常打印 OK、退出码 0，worker 结果却悄悄丢失。原因：spawn 子进程 re-import 主模块时重放入口代码，子进程抛错退场而父进程不读 exitcode（机制见 How It Works 节）。解法：入口代码一律 `if __name__ == '__main__'` 保护，Jupyter 和脚本两种环境都要养成习惯。
- **任务太小就上多进程**：现象是加速比低于 1，比串行还慢。原因：spawn 启动成本吞掉全部收益。解法：先做"启动成本 vs 单任务收益"的除法（公式见 How It Works 节）。
- **在子进程里 print 大量内容**：现象是各进程输出交错、单行被撕裂。原因：spawn 子进程继承 stdout，多进程同时写。解法：结果用返回值带回来，在主进程统一输出。
- **以为 `pool.map` 会流式返回**：现象是整批卡到最后一个任务完成才返回。原因：map 的语义就是等全批。解法：要流式用 `imap`/`imap_unordered`，或 [07_futures](../07_futures/README.md) 的 `as_completed`。

### 深入问答

**Q1: fork 和 spawn 两种启动方式有什么区别？**

fork（复制父进程内存的启动方式）快，Unix-only，与线程混用有安全隐患；spawn 重新启动解释器并 import 主模块，慢但跨平台，macOS/Windows 默认。

spawn 下必须写 `__main__` 保护，否则子进程 re-import 时重放入口代码——本实验实测是"子进程尸退 + 父进程静默继续"。

**Q2: pool.map 和 imap 的区别？**

map 等全批完成、按输入顺序返回整批；imap 流式按输入顺序逐个产出；imap_unordered 完成顺序即产出顺序。吞吐敏感 + 任务耗时差异大时，后两者能把"最慢任务"从关键路径上摘掉。
