# 10 · 异步生产者-消费者与限流：asyncio.Queue、Semaphore、背压

> 流水线可以搬进单线程世界：`asyncio.Queue` + `Semaphore` +
> `maxsize` 背压。实测数据先看一眼——5000 条任务 0 秒级跑完（204 万条/秒）、
> 在飞峰值被 Semaphore 钳在 10、无界队列峰值 4749 vs 有界 64。

## Background

这节讲单线程世界里的流水线从哪来。经典做法是多线程生产者-消费者：`threading` 开若干生产者与消费者线程，中间用 `queue.Queue`（线程安全队列）传递数据。想并发抓 1 万个 URL，就开一批工作线程围着队列转。

痛点在线程本身：每一次 put/get 都有锁竞争和线程切换，线程一多，内存与切换开销随之上涨；多个消费者共同更新一个计数字典，还得再配一把锁防竞态（race condition，结果取决于线程执行时序的缺陷）。并发目标到了千级、万级，线程版先被自己的调度成本拖垮。

asyncio 换了一条路：并发不再来自"更多线程"，而来自单线程内的协作式调度——协程（coroutine，用 async def 定义、能在 await 点暂停和恢复的函数）在 await 点主动让出，由事件循环（event loop，在单线程里调度并切换多个协程的引擎）切换执行。

队列、信号量这些流水线零件被重写成协程感知的版本，同样的结构搬进单线程世界，调度成本降到函数调用级。

## What

这节给出定义与心智模型。异步流水线指在事件循环内用队列把生产者与消费者协程串起来的数据处理结构。

一句话心智模型：**asyncio.Queue 是单线程世界的传送带（满了 await put 挂起），Semaphore 是并发闸门（许可外排队），无界队列是反面教材（生产狂奔、内存堆积）**。

可以把 asyncio.Queue 想象成食堂出餐口的传送带：灶台（生产者）不停往上放，窗口（消费者）不停取；但和真实传送带不同的是，这条带子有容量上限，放满后灶台会被"按住"暂停出菜，而不是把菜摞到半空——这个把压力顶回上游的动作就是背压（backpressure）。

结构之外，组织纪律一样不能少：

- **总量守恒**：毒丸收尾——给每个消费者发一枚 `None` 哨兵，5000 条恰好处理一遍
- **并发上限**：Semaphore 许可数钳制同时在飞（in-flight，已开始尚未完成）的任务数
- **内存上限**：`maxsize` 背压，队列长度有界

## When to Use

这节补判断力：什么活儿值得搭这条流水线。主线看数据要过几道"快慢不一的关卡"——关卡多、两端速率不齐，才需要队列解耦。

典型场景：

- **高并发抓取**：解析协程不断把新 URL 入队，请求协程带着 Semaphore 限速消费——lab 11 的异步抓取器（[11_async_fetcher](../11_async_fetcher/README.md)）正是这套骨架。
- **日志/事件入库**：业务侧产生事件快，写库侧慢，用有界队列让上游自动减速，而不是让内存爆掉。
- **守速率约束的第三方调用**：对方限流，用 Semaphore 钳住在飞请求数，既是自我保护也是礼貌。

何时不用：数据量小、生产消费都快，直接顺序循环即可；CPU 密集型计算 asyncio 帮不上忙——单线程只有一个核，要多核并行得换进程方案（见下表）。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 线程 + `queue.Queue` | 抢占式多线程，put/get 有锁竞争与线程切换 | 已有线程代码，或要与阻塞库混用 |
| `asyncio.Queue` | 单线程协作式，await 让出，无数据竞争 | 事件循环内的高并发 I/O 流水线 |
| `multiprocessing.Queue` | 跨进程，数据要序列化（把对象转成字节流、到另一进程再还原） | CPU 密集、需要多核并行 |

## How It Works

这节按"传送带 → 闸门 → 背压"的顺序拆机制，并与上面的输出互相印证。

### asyncio.Queue：等待是让出，不是阻塞

与线程版 `queue.Queue` API 几乎一致，但 put/get 是 **await** 的：队列满时 `await q.put()` 挂起生产者，空时 `await q.get()` 挂起消费者——等待是让出控制权，不是阻塞线程。

毒丸收尾协议原样适用（None 哨兵 + task_done + join：消费者每处理完一条就调 task_done 计数，主流程 join 等计数归零，确认全部处理完才退出）。

你在输出 §1 看到的"没有锁、没有 GIL 争用，只有 await 让出"（GIL——全局解释器锁，CPython 中同一时刻只允许一个线程执行字节码）就是这条差异的直接结果。

单线程内没有数据竞争，计数字典不需要锁；单条消息只被一个消费者取走，由 Queue 的 get 语义天然保证。

### Semaphore：异步世界的并发闸门

`async with sem:` 包住"访问受限资源"的协程段，超过许可数的协程在 await 处排队。单线程能挂起上万协程，没有 Semaphore 的话，一万次并发请求会同时砸向目标——限流既是自我保护也是礼貌，也是高吞吐能持续的前提。

输出 §2 的"在飞峰值 = 10（≤ 许可数 10）"就是闸门在计数：拿到许可才放行，退出一段才归还。

### 背压：让过载反馈到源头

无界队列 + 慢消费者 = 内存里的定时炸弹（输出 §3 实测峰值 4749 条堆积）。`maxsize=64` 让 `await q.put()` 在队满时挂起——生产速率被自动钳制到消费速率，内存占用恒定（§3 第二行峰值恰为 64）。背压的定义由此而来：不丢弃、不报错，让压力沿流水线传回源头。

### 最核心的一处代码：为什么消费者敢不用锁

```python
results[item] = results.get(item, 0) + 1   # 多个消费者并发执行这段
```

线程版这里必须上锁：读-改-写的间隙会被切换打断。异步版是单线程协作式调度——只有 await 点才会切换，而这几行之间没有 await，是原子执行的。

这是 asyncio 的重要红利：**同步段天然原子**。但边界同样清晰：一旦中间插了 await，原子性即告破裂——"await 之前是安全的，之后不一定"要时刻记住。

## Pitfalls & Q&A

这节收四个常见踩坑点和两个迁移问题，踩坑按"现象 → 原因 → 解法"组织。

- **在协程里调阻塞函数**（`time.sleep`、同步 requests）。现象：整个程序卡住，别的协程全部停摆。原因：阻塞调用冻结了事件循环，Semaphore 也救不了。解法：一律用异步库（`asyncio.sleep`、aiohttp）。
- **无界队列 + 生产快于消费**。现象：压测 QPS 正常，内存却持续上涨。原因：队列无限堆积。解法：给 `maxsize` 开背压，并监控队列长度——只看 QPS 不看 qsize 会漏掉。
- **忘了给消费者发毒丸**。现象：程序退不出去，`await q.get()` 永远挂起。原因：消费者不知道生产已结束。解法：每个消费者发一枚 `None` 哨兵（线程版的教训在异步世界原样成立）。
- **Semaphore 包错范围**。现象：限流加了，吞吐反而低了一个数量级。原因：包住整个循环体 vs 只包资源访问段，粒度过大。解法：只包受限资源段；锁的粒度原则同样适用于许可。

**Q1: asyncio.Queue 和 queue.Queue 的区别？**
API 几乎一致，等待机制完全不同：前者 await 让出（单线程协作），后者阻塞线程（多线程抢占）。前者只能在事件循环内用，跨线程要用 `queue.Queue` 或 `loop.call_soon_threadsafe` 桥接。

**Q2: 毒丸关闭在异步版有什么不同？**
协议相同（None 哨兵 + task_done + join），但发给每个消费者一枚毒丸后用 `asyncio.gather(*consumers)` 等待即可；另外 asyncio 队列的 task_done/join 语义与线程版完全一致，可以无缝迁移经验。
