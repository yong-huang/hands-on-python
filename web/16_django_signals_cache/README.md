# 16 · 信号、缓存与测试：Django 段收官的三根支柱

> 功能写完只是半成品——本实验补上工程化的三根支柱：**信号**把审计日志从业务代码里
> 解耦出去（post_save 一行 receiver）、**缓存**用 `CaptureQueriesContext` 把"省了一次
> 查询"变成可断言的数字（第二次调用 0 条 SQL）、**pytest-django + coverage** 用 4 条
> 用例和 97% 覆盖率守住全部回归。三件事都有断言，没有一件靠"应该没问题"。

## Background

这节回答一个前置问题：为什么"功能能跑"之后还有一大截工程化要补。把博客系统缩到最小，就能看到没有这三样东西时的日常。

**保存文章要记审计日志。** 最初的写法是在每个视图函数里，
`save()` 之后手动补一行 `AuditLog.objects.create(...)`。

文章只在一处创建时还好；一旦后台、API、管理命令都能创建文章，
每处都要记得补、补法还可能不一样——
这种"散弹式修改"（shotgun surgery：一处变更被迫改动多个调用点）是维护事故的高发区。

**重复查询拖慢读路径。** 首页每刷新一次就查一次热门文章，数据没变，SQL 却一次不少地打向数据库。手动加缓存又引入新问题：存哪、何时失效、怎么证明缓存真的生效了。

**改完代码靠手感。** 没有自动化测试时，回归验证靠手动把页面点一遍；"这段代码有没有被任何断言盯着"无从回答。Django 对这三类问题各给出了框架级答案——解耦副作用的信号、统一读写的缓存框架、配合 pytest 的测试工具——它们就是本实验的三根支柱。

## What

这节给出三样东西的定义，并配一个共同的心智模型。

- **信号（signal）**：Django 的对象级发布-订阅机制——某个事件发生时框架发出通知，预先注册的处理函数自动执行。最常用的是 `post_save`（模型 `save()` 完成后发出的内置信号），处理函数用 `@receiver`（订阅信号的装饰器）声明。
- **缓存框架（cache framework）**：Django 统一封装的"算过一次、存起来复用"机制，核心入口形如 `cache.get_or_set(key, fn, timeout)`——取不到就算、算完就存。
- **pytest-django + coverage**：前者让 pytest 能操作 Django 的数据库与配置，后者统计测试执行到了哪些代码行，回答覆盖率问题。

一句话心智模型：**保存触发信号、信号落审计；缓存把重复查询压成 0 条 SQL；pytest 把以上全部行为钉进回归**。

可以把三根支柱想象成餐厅运营：信号是"每上一道菜，后台自动记一笔台账"（前厅业务不用管）；
缓存是"常客点的菜提前备好，不必每次现做"；
测试是"打烊前的巡检清单"。

但和餐厅不同的是：代码里的台账与备菜必须能被程序验证——
这正是 `CaptureQueriesContext`（统计一段代码执行了多少条 SQL 的测试工具）存在的意义。

## When to Use

这节补判断力：什么场景值得用，什么场景是负资产。

**信号**——在"保存或删除之后，还要做一件与主流程无关的事"的时候：写审计日志、失效关联缓存、发通知。不用：逻辑属于主流程（下单必须扣库存）、需要返回值或严格控制执行顺序。

**缓存**——在"同一份数据被反复读取，而计算或查询有成本"的时候：首页热门列表、全站配置项。不用：写多读少，或业务要求强一致——读到旧值会出错的地方宁可不缓存。

**覆盖率**——在"给已有行为补回归防线"的时候当底线指标用。不用：为新功能先凑覆盖行数。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 信号 | 事件发生自动触发，调用链隐身 | 多个入口共用的旁路副作用 |
| 调用点直接写 | 链路可见，但要改每个调用点 | 只有一两个入口、逻辑即主流程 |
| Celery 等任务队列 | 异步执行，可承载重活 | 副作用耗时长，不能拖住请求 |
| `cache.get_or_set`（低级 API） | 粒度最细 | 缓存函数结果与查询结果 |
| 视图装饰器 / 模板片段缓存 | 整页或片段级粗粒度 | 整页复用、内容改动少 |

## Quick Start

这节跑通整个实验：一条命令依次演示信号审计、缓存断言与覆盖率验收。前置条件：仓库自带的虚拟环境（含 Django 与 pytest-django）。

```bash
cd web/16_django_signals_cache
source ../.venv/bin/activate
python3 signals_cache_demo.py    # 3 节断言 + subprocess 跑 pytest --cov（收尾清理）
```

真实输出节选：

```

  首次 get_or_set → 1 条 SQL，拿到 1 个标题
  第二次 get      → 0 条 SQL（LocMemCache 命中）
  CaptureQueriesContext 让'缓存省了一次查询'从感觉变成可断言的数字

  coverage: blog app 覆盖率 97% ≥ 80% ✓
```

诚实预期：

- **LocMemCache 是进程内缓存**：单进程教学够用；多 worker 部署各缓存各的，生产换 Redis/Memcached 后端（settings 换一行）
- **覆盖率 97% 的含金量说明**：blog app 代码量小（models/handlers/apps），行覆盖高不等于分支全覆盖——指标守底线，不追虚荣
- **信号让调用链"隐身"**：排查"AuditLog 谁写的"需要 grep receiver——本实验 docs 与测试都显式记录了这条链路

实验涉及的工具速览：

| 工具 | 作用 |
|---|---|
| `post_save` + `@receiver` | 模型保存后自动执行审计写入 |
| `cache.get_or_set` | 一行完成"取缓存，未命中就算并回填" |
| `CaptureQueriesContext` | 统计代码块内的 SQL 条数，把优化变成断言 |
| `@cached_property` | 把方法的计算结果缓存到实例上 |
| `pytest --cov` | 跑用例并输出覆盖率报告 |

## How It Works

这节把三个现象拆到机制层：你在输出里看到的每个数字，都对应下面的一处设计。

### 信号：连在哪、为什么

`post_save` 在模型 `save()` 后发出，`@receiver(post_save, sender=Article)` 的处理函数自动落审计。信号必须连接在 `AppConfig.ready()` 里（AppConfig 是每个 Django 应用的配置类）——保证只连一次且 import 即生效：

```python
class BlogConfig(AppConfig):
    name = "blog"
    def ready(self):
        from . import handlers  # noqa: F401  # 应用就绪时加载 handlers，完成信号连接
```

models.py 在应用注册早期被加载，此时连信号可能在测试（import 两次）或迁移（migration——Django 生成并执行数据库表结构变更脚本的过程，此时不加载完整 app）场景下重复连接或丢失连接。

`ready()` 是 Django 官方指定的"应用就绪"钩子——文档里那句"signals 放这"不是风格建议，是正确性要求。

这套设计的收益是业务零侵入、多订阅者互不影响；代价是调用链隐身、顺序不可控——所以信号只放"旁路副作用"（审计/缓存失效/通知），绝不放主流程逻辑。

### 缓存：0 条 SQL 是怎么断言出来的

`cache.get_or_set(key, fn, timeout)` 把"取不到就算、算完就存"压成一行。
有效性的证据来自 `CaptureQueriesContext`：首次调用 SQL ≥1、第二次 0——
输出里"1 条 SQL → 0 条 SQL"那两行就来自这里，数字断言而非感觉。

生产换 Redis 只是换 settings（Django 的项目配置模块）的 BACKEND，
代码不动，这正是缓存框架抽象的价值。

`@cached_property` 是另一层实例级缓存：首次访问计算并写进实例 `__dict__`，之后直接命中。本实验断言"改了 content，word_count 不变"——这正是它的语义：**缓存绑定实例当时的状态**。输入会变的派生值不能用（要用带失效的 cache 框架）。

### 测试：隔离与覆盖率

`pytest.ini` 声明 `DJANGO_SETTINGS_MODULE`（一个环境变量，指向 Django 的配置模块，让 pytest 知道要加载哪个项目的配置），
`@pytest.mark.django_db` 给用例开数据库：每个测试包在事务里，结束回滚——用例之间零残留。

需要迁移之外的表结构，或事务内无法测的行为（如 `transaction.atomic` 嵌套）时，
用 `pytest.mark.django_db(transaction=True)`。

`--cov=blog` 的覆盖率回答"有没有断言盯着这段代码"——本实验设 80% 为底线，实测 97%。

## Pitfalls & Q&A

这节先列四个真实踩坑点，再答两个选型问题。

**信号 receiver 连接两次**：现象是审计日志成对出现；原因是 `post_save` 被连了两遍（模块被 import 两次等）；解法是 `ready()` + `dispatch_uid`（给连接指定唯一 ID，Django 据此去重）双保险。

**在信号里做重活**：现象是批量更新时请求明显变慢；原因是每次 save 都触发（含全表更新的循环 save），信号里的慢查询被放大成事故；解法是审计类轻写入留在信号，重计算进任务队列，并防住循环触发（save 里又 save）。

**缓存永不失效**：现象是数据已更新、页面仍显示旧值；原因是 `timeout` 没显式给、失效策略缺失；解法是显式设 `timeout=60` 这类期限，并按业务容忍度设计"缓存与 DB 不一致"的窗口期，不是越久越好。

**覆盖率当 KPI 追 100%**：现象是为凑行数给 getter 写无意义断言；原因是把行覆盖当成了质量本身；解法是覆盖率守底线（防"零断言代码"），分支质量看断言内容。

**Q1: post_save 的 created 参数怎么用？**
`created=True` 表示本次是新建（INSERT），False 是更新（UPDATE）——审计日志区分动作、缓存失效策略差异（新建预热、更新失效）都靠它。

**Q2: Django 缓存层有哪些后端与粒度？**
后端：LocMem（开发）、Redis/Memcached（生产）、Database（低频）。粒度：低级 API（cache.get/set，本实验）、视图装饰器（整页）、模板片段（{% cache %}）。选型按"失效粒度与共享需求"。
