# ⛓️ 17 · 三框架同题对比：Flask / FastAPI / Django+DRF

> 集成点：把 Flask / FastAPI / Django+DRF 三个框架拉到同一道题前——**同一个 TODO
> API（CRUD + 受保护路由）各写一遍**，共享同一套 HMAC token 认证、跑同一组 14 条
> HTTP 断言、上同一个压测（1000 请求 × 并发 50），最后给出 wc -l 实测的代码量与
> QPS/p95 对比表。选型从此有数据：不看布道文，看控制变量下的实测。

## Background

这节讲清一件事：框架选型为什么难，以及"同题对比"从哪来。没有对比方法时，人们选 Web 框架主要靠三类信息源：布道文、star 数、身边同事的口碑。

这些信息各有立场。两篇文章各夸各的框架，读者分不清差异来自"框架能力"还是"作者偏好"；想动手验证，最常见的做法又是给每个框架各挑一道题——题不同，写出来的差异照样分不清是框架的还是题的。

控制变量实验由此而来：把题、认证、压测规格全部锁死，让残留差异只能来自框架本身。本实验就是这个思路的一次落地。

## What

这节定义实验对象与判读结论。本实验是一次**控制变量的同题对比**：用三个 Python Web 框架各实现同一个 TODO API（CRUD——增删改查——外加需要认证的受保护路由），跑同一组断言与同规格压测。

三位选手的一句话画像：

- **Flask**：微框架——只提供路由与请求/响应对象，其余能力自己拼装
- **FastAPI**：基于类型注解的框架——校验、序列化（把 Python 对象转成 JSON 文本响应）、文档从注解自动生成（校验由 Pydantic——依据类型注解做数据校验的库——完成），原生异步
- **Django + DRF**：全家桶框架加其 REST 库（DRF，即 Django REST framework）——ORM（对象关系映射：把数据库表映射成 Python 对象来读写的持久层）、admin（自带的后台管理站点）、认证开箱即用

一句话心智模型：**同一道题 → 三种方言的实现 → 同一组断言 → 同一规格压测 → 一张对比表**。

实测结论有三条：14 条断言三框架全绿——**同题同解，没有框架做不到**；代码量 62/83/119 行——微框架最短、全家桶最长，长出来的部分是"免费送的基础设施"；QPS（每秒请求数）131/131/121——**本地 dev server（框架自带的开发服务器）的量级同档**，压测绝对值不该进选型论证。

## When to Use

这节把实测数据转成选型判断：在做什么事的时候，选哪个框架。

- **在做微服务、IO 密集的 API**（多服务互调、高并发等待外部资源）的时候，选 FastAPI——异步模型与自动校验直接命中诉求
- **在做小工具、原型、内部小接口**的时候，选 Flask——需要什么加什么，代码量最小
- **在做内容密集型站点、需要 admin 后台与 ORM 迁移（把数据库表结构变更写成版本化脚本并应用到数据库）**的时候，选 Django——全家桶省掉自建成本

何时不用纠结选型：团队已在一个框架上深耕多年、又没有明确痛点时，熟悉度的价值高于框架间差异——本实验的性能数据也说明差异主要不在速度。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| Flask | 微框架，代码量最小，能力自己拼 | 小而美、快速原型、已有同步栈 |
| FastAPI | 类型注解驱动，异步原生 | 微服务、异步密集、要自动文档 |
| Django+DRF | 全家桶，代码量最长，基础设施最全 | 内容密集、需要 admin/ORM/auth |

## Quick Start

这节跑通整个对比实验：一条命令起三个服务器、跑断言与压测、输出对比表。前置条件：仓库自带的虚拟环境（含三个框架与压测依赖）。

```bash
cd web/17_framework_showdown
source ../.venv/bin/activate
python3 showdown.py    # 起三个服务器跑断言 + 压测，输出对比表（约 30s）
```

真实输出节选：

```
========================================================
[Flask：同一组断言 + 压测]
========================================================
  14 条断言全绿（注册/受保护路由/CRUD/404/重复删除）
  压测: 131 req/s · p95 5767.1ms

========================================================
[对比总表]
========================================================
  框架              代码行数       QPS   p95(ms)
  Flask             62       131    5767.1
  FastAPI           83       131    5773.6
  Django+DRF       119       121    6211.5

  判读：QPS 绝对值不重要（本地 dev server），量级同档即说明——
  选型该看生态与团队：微服务/异步密集选 FastAPI，小而美选 Flask，内容密集选 Django
```

诚实预期：

- **QPS ~130 是 dev server 的数字**（werkzeug——Flask 底层自带的服务器库；uvicorn——FastAPI 用的异步服务器；生产用 gunicorn——带多进程 worker 的生产服务器——后是另一个量级；WSGI/ASGI 两种服务器接口的差异见 Q2）；本实验只比较三者的相对方向
- **Flask 与 FastAPI 的 14 条断言状态码完全一致**；唯一的"方言差"是 Django 路由带尾斜杠（适配在 paths 表里）
- **DRF 版没有用 ModelSerializer（DRF 里从模型自动生成序列化代码的组件）**：standalone 单文件用 ViewSet（DRF 里把一组增删改查视图打包的组件）+ 手写校验，所以 Django 版 119 行的代码量对比在这项上有失真，参考意义有限——完整 DRF 形态见 lab 15

实验构成速览：

| 部件 | 作用 |
|---|---|
| `tokenbox.py` | 三框架共享的 HMAC token 认证（HMAC：用共享密钥对内容做签名的消息认证码） |
| `showdown.py` | 编排：起服务 → 跑断言 → 压测 → 汇总对比表 |
| 14 条断言 | 状态码序列，充当 API 契约 |
| 压测参数 | 1000 请求 × 并发 50，三框架同规格 |
| `p95` | 第 95 百分位响应延迟，压测的延迟指标 |

## How It Works

这节解释对比为什么公平、输出怎么读：三组机制分别对应公平性、契约与方言差异。

### 控制变量为什么公平

认证逻辑若各写各的，断言差异就分不清是"框架差异"还是"实现差异"——所以 tokenbox.py 三框架共享，HMAC 逻辑零差异。压测同理：三个 app 同机同端口规格同跑，且明确"dev server 数字看方向不看绝对值"。你在对比总表里看到的 131/131/121，只在"相对方向"这个语义下有效。

### 同题同解：14 条断言的契约

断言序列覆盖注册（401/200）、受保护路由（401/200）、CRUD（201/200/404/204）与重复删除（404）——**状态码序列就是 API 契约**。三个框架跑出完全一致的状态码序列，证明"框架决定的是写法，不是能力"。输出里"14 条断言全绿"一行，就是这份契约在三框架上的验证结果。

### 三种方言的同一道题

同一道题在不同框架里的表达差异集中在四处：

| 维度 | Flask | FastAPI | Django+DRF |
|:---|:---|:---|:---|
| 路由 | 装饰器 + `<int:id>` | 装饰器 + 类型注解 | urls.py + Router |
| 校验 | 手写 if → 400 | Pydantic 模型 → 422/400 | Serializer/手写 → 400 |
| JSON | jsonify | 返回 dict 自动序列化 | Response/JsonResponse |
| 存储 | 进程内 dict | 进程内 dict + asyncio.Lock | sqlite + ORM（standalone） |

## Pitfalls & Q&A

这节先列五个踩坑点，再答三个深入问题。

**压测客户端用了相对 URL**：现象是压测函数报 `UnsupportedProtocol`；原因是 `client.get("/todos")` 在带 `base_url` 的 AsyncClient 下缺少协议与主机；解法是压测函数拿完整 URL。

**空标题校验三个框架写法不一**：现象是 FastAPI 版放过了空串标题；原因是 `title: str` 只拦缺失/类型，不拦空串；解法是 handler 里补 `strip()` 后返回 400——统一契约要自己保证，类型注解只管类型。

**Django 401/400 日志刷屏**：现象是预期内的失败每次都打告警日志；
原因是 `django.request` 对 4xx 默认告警；

解法是在 settings.configure 里用声明式 `LOGGING` 静音——
命令式 `setLevel` 会被 `get_wsgi_application()` 内部的二次 `django.setup()`
重放默认配置覆盖（实测踩中）。

**standalone Django 的模型 app_label**：现象是单文件版模型无处挂靠；原因是单文件没有 app 包；解法是挂靠已有 app（`app_label="auth"`）——这是教学取巧，真实项目要建 app + migrations。

**Django 为什么用文件库而不是 `:memory:`**：现象是其他线程请求报 `500: no such table`；
原因是 werkzeug 多线程服务下每个请求各开一条连接，

而 SQLite 的 `:memory:` 是**每连接独立**的数据库，
主线程 `ensure_db()` 建的表在其他线程"消失"；

解法是换成文件库：

```python
DATABASES={"default": {..., "NAME": DB_PATH}}   # 第一版是 ":memory:"，踩坑
```

这类"连接私有状态"的坑在连接池语境下同样存在。

**Q1: 为什么三者压测 QPS 同档？瓶颈在哪？**
瓶颈在 dev server 与本地回环（werkzeug 每请求线程、日志 IO），不在框架路由开销——框架本身的分派成本是微秒级。生产对比要用 gunicorn/uvicorn 多 worker + 真实依赖（DB/网络）。

**Q2: WSGI 与 ASGI 的服务模型差异？**
WSGI（Python 传统同步 Web 服务器接口）：一个可调用对象同步处理单请求，并发靠线程/进程池；ASGI（异步版本）：单线程事件循环 + 协程，等待不占线程，原生支持 WebSocket/长连接。线程模型与容量的实证见 lab 10。

**Q3: 迁移成本角度，三者互迁的方向性结论？**
Flask→FastAPI：视图函数签名变注解，成本低收益高（自动文档/校验）；Flask/Django→Django：引入 ORM 与迁移成本高；Django→Flask：丢掉 admin/auth 需自建——"往全家桶迁"比"往微框架迁"贵。
