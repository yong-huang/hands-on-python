# 11 · 中间件、异常与后台任务：请求管道的三个扩展点

> 业务代码只该写业务——耗时打点、异常兜底、响应后发信这些"横切关注点"该挂在管道上。
> 本实验给 FastAPI 管道装上三个扩展点并实测边界：**函数式中间件**给响应盖耗时戳
> （并实测它够不到未处理异常的 500）、**exception_handler** 把业务异常兜底成约定 JSON、
> **BackgroundTasks** 用时间戳证明"响应先于任务"。

## Background

这节讲问题域：在框架提供统一挂载位之前，Web 服务里那些"每个接口都需要"的杂务是怎么做的，以及那种做法在哪里撞墙。

假设不用任何管道机制，给一个多接口服务加耗时统计，最直接的做法是把计时代码复制进每个路由函数（路由函数——处理某个 URL 请求的函数）；想统一错误格式，就在每个函数里写一遍一样的 try/except；下单后要发确认邮件，就把发信代码直接写进接口，让用户等它发完。

接口一多，三处开始撞墙：

- 计时、加头这类代码复制 N 份，漏改一处，数据就不可信；
- 错误处理散在各函数里，同一种业务失败在不同接口返回不同形状的错误；
- 慢操作（发邮件、写审计）堵在接口里，用户等待时间被无关工作拖长。

这类"处处需要、又与具体业务无关"的需求有个名字：横切关注点。Python Web 框架圈的标准答案是：在请求管道上预留统一挂载位，让这类逻辑写一次、对所有接口生效。FastAPI（基于 Starlette 的异步 Web 框架）把挂载位整理成三个扩展点，即本实验的对象。

## What

这节定义三个扩展点分别是什么，并给出贯穿全文的心智模型。

- **中间件（middleware）**：包在请求与响应外层的一段框架代码，所有请求进出都必须经过它。本实验用函数式写法 `@app.middleware("http")`——FastAPI 底层库 Starlette 提供的 BaseHTTPMiddleware 语法糖——给每个响应盖 `X-Process-Time` 耗时头。
- **异常处理器（exception handler）**：向框架注册"某类异常发生时返回什么错误响应"的函数。本实验把业务异常 `BusinessError` 兜底成 HTTP 418（状态码——服务器给每个请求标的三位数结果）加约定 JSON。
- **后台任务（BackgroundTasks）**：FastAPI 提供的"响应发送完之后再执行"的进程内任务机制。本实验用它安排一封模拟确认邮件，并实测响应与任务的先后顺序。

三个扩展点作用在管道的不同位置：

| 扩展点 | 挂载位置 | 本实验的实测对象 |
|---|---|---|
| 函数式中间件 | 包住整个请求/响应周期 | `X-Process-Time` 的覆盖范围 |
| `exception_handler` | 路由之外、中间件之内 | 业务异常兜成 418 + 约定 JSON |
| BackgroundTasks | 响应发送之后 | 响应与任务的时间戳顺序 |

可以把请求管道想象成一条单向流水线：请求从最外层流入，
经中间件、路由 handler、异常处理器，变成响应后流出；
后台任务挂在流水线末端，产品下线之后才开动。

但和流水线不同的是：最外层还有一道框架自带的兜底工位
（`ServerErrorMiddleware`），未被处理的异常会越过用户中间件直接到它那里。

一句话心智模型：**请求沿"中间件 → handler → 异常处理器 → 响应"单向流动；
后台任务挂在响应之后，500 兜底悬在用户中间件之外**。

## When to Use

这节讲三个扩展点各自值得用的时机、不该用的边界，以及同类方案怎么选。

典型场景：

- 在做"每个接口都要、又不想逐个改业务函数"的全局修饰时——统一耗时头、请求 ID、安全响应头——用中间件。
- 在做错误响应协议统一时——"库存不足返回 418 + 约定 JSON，客户端按协议处理"——用 exception handler。
- 在做"失败不致命、不该让用户等"的收尾动作时——发确认邮件、写审计、清临时文件——用 BackgroundTasks，选型前评估任务丢失的业务代价。

何时不用：

- 准入校验（"当前用户能否访问这个路由"）：中间件看不到路由参数，该用依赖注入（lab 09 的 `Depends` 机制——路由执行前按声明自动准备参数）。
- 可靠异步（任务丢了会造成业务损失）：BackgroundTasks 与 Web 服务同进程、无持久化，进程重启任务即丢，该上 Celery/ARQ 这类独立任务队列。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 函数式中间件 | 包住整个周期，覆盖不到最外层 500 | 横切的响应整形 |
| 纯 ASGI 中间件 | 更底层，直接处理 ASGI 事件流（Python 异步 Web 服务的标准接口），能盖住含 500 在内的所有响应 | 全响应统一加头且须含 500 |
| 依赖注入 `Depends` | 在路由解析阶段执行，可复用依赖树 | 准入校验、资源准备（lab 09） |
| exception handler | 只在异常发生时接管响应 | 业务失败的统一错误协议 |
| BackgroundTasks | 同进程、响应后执行、无持久化 | 轻量、丢了不致命的收尾 |
| Celery/ARQ | 独立进程与队列，支持重试 | 必须成功、耗时的异步任务 |
| nginx 等反向代理 | 在框架之外统一处理 | 全局统一（如全站响应头） |

```
  GET /business-error    → 418 · X-Process-Time=0.2ms

========================================================

========================================================
  POST /orders → 200 · {'message': '订单已受理，确认邮件稍后发送'}

  语义提醒：TestClient 的 post 会等整次 ASGI 调用（含后台任务）才返回；
  真实服务器上响应字节先发给客户端、任务随后跑——时间戳证据两种环境都成立

========================================================
全部断言通过 ✓ 耗时头全覆盖、418 约定 JSON、后台任务时间戳晚于响应
```

诚实预期：

- **500 响应没有耗时头是实测结论**：如果想让未处理异常也带耗时头，需要把计时逻辑写成纯 ASGI 中间件挂到 ServerErrorMiddleware 之内（或用 nginx 等外层设施兜底打点）
- **TestClient 下后台任务在 post 返回前完成**：一次 ASGI 调用含后台任务；"客户端先拿到响应"只在真实服务器上发生，进程内时间戳证据两种环境通用
- **中间件里 `call_next` 之后的代码不保证对流式响应生效**：本实验的响应都是小 JSON，`BaseHTTPMiddleware` 语义足够；流式场景的时序差异不在此展开

本实验用到的三个注册入口：

| API | 作用 |
|---|---|
| `@app.middleware("http")` | 注册函数式中间件 |
| `@app.exception_handler(ExcType)` | 注册某类异常的处理器 |
| `background.add_task(fn, *args)` | 把函数排到响应之后执行 |

## How It Works

这节按请求流经的顺序拆开三层机制，并与 Quick Start 输出里的现象互相印证。

### 中间件：必经之路与它的盲区

函数式中间件内部以 `call_next(request)` 分界：之前是请求阶段、之后是响应阶段。你在输出里看到的 `X-Process-Time=0.3ms`，就来自"请求阶段起表、响应阶段停表"的两次打点。

覆盖范围取决于中间件栈的层序：`ServerErrorMiddleware` 在最外层（兜底未处理异常），
用户中间件在其内，`ExceptionMiddleware`（处理已注册异常与 HTTPException）更内。

输出里 200、兜底 418、路由 404 都带耗时头，唯独 `GET /boom → 500` 没有——
未处理异常一路向外冒泡、越过用户中间件，
由最外层兜底后直接返回，响应不再流回用户中间件。

覆盖范围有终点，这就是实测边界。

### 异常分层：业务失败与程序缺陷走不同的路

可预期的业务失败（`BusinessError`：库存不足、余额不够）
由 exception handler 兜成 418 + 约定 JSON，客户端按协议处理；
程序缺陷（`RuntimeError`）不注册 handler、让它 500，交给监控告警接住。

输出里 `GET /business-error → 418 · X-Process-Time=0.2ms` 同时印证两件事：
handler 生效了；异常在内层就被接住，响应仍流经外层中间件，所以带耗时头。

handler 里只剩 `raise`，错误响应的形状由 handler 统一决定——这是"用异常表达业务失败"的收益。两条铁律：两种失败一条 handler 都不能吞，吞掉业务失败会破坏协议、吞掉程序缺陷会把 bug 藏进 200。

### 后台任务：为什么用时间戳证明"响应先于任务"

`background.add_task(fn, *args)` 把任务排到响应发送之后执行。输出里 `响应创建 1789066687.939 < 任务完成 1789066688.244（差 0.31s）` 说明模拟发信的 0.31 秒没有计入用户等待。

为什么不用"客户端何时拿到响应"来证明——第一版断言是"post 返回时任务未完成"，实测翻车：TestClient 的 post 会等整次 ASGI 调用（含后台任务）结束才返回，客户端时钟在测试环境里测不到"先响应后任务"。时间戳是进程内证据，测试环境与真实服务器都成立。

```python
EVIDENCE["response_created_at"] = time.time()   # handler 里打点
background.add_task(send_confirmation_email, ...)  # 任务里再打点
assert EVIDENCE["response_created_at"] < EVIDENCE["task_done_at"]
```

这段在做什么：在 handler（响应创建时刻）与后台任务（任务完成时刻）各留一个进程内时间戳，断言前者早于后者。测试什么该用客户端时钟、什么该用服务端留痕，这道分界线本身就是一课。

## Pitfalls & Q&A

这节收四个实测与工程中的坑，再答三个取舍问题；每条坑按现象、原因、解法展开。

踩坑清单：

- **中间件里吞异常**。现象：try/except 捕获后不 re-raise，接口"永远不报错"。原因：误把中间件当兜底层。解法：中间件只加东西（耗时头、请求 ID），不做异常兜底；捕获后必须 re-raise，否则 ServerErrorMiddleware 的 500 兜底被绕过，缺陷被伪装成 200。
- **业务失败用 500 表达**。现象：监控满屏 500，点开全是"库存不足"。原因：错误分级失真。解法：418/422/409 这类 4xx 管业务失败，500 只留给程序缺陷。
- **后台任务静默失败**。现象：任务抛异常但接口"一切正常"。原因：响应早已返回，异常只进日志。解法：关键任务要有落盘或重试机制，不能只依赖进程内执行。
- **把重活塞 BackgroundTasks 当队列用**。现象：任务量一大，服务变慢甚至堵死。原因：与 Web 服务同进程、无持久化，并发受 worker 数限制。解法：按任务丢失的业务代价选型，重的、必须成功的任务迁到 Celery/ARQ。

深入问答：

**Q1: FastAPI 中间件和依赖注入的区别？怎么选？**
中间件包住整个请求/响应周期，能改响应头、做耗时打点，但看不到路由参数；依赖注入在路由解析阶段执行，能复用依赖树、能按路由声明。横切的"响应整形"用中间件，"准入校验/资源准备"用依赖（lab 09）。

**Q2: 自定义异常的兜底链是什么顺序？**
异常先找 `exception_handler(具体类型)`，
再找 `RequestValidationError`/HTTPException 的内建处理，
最后落到最外层 ServerErrorMiddleware 的 500。

越具体的 handler 越先命中；未被兜底的异常继续向外层冒泡。

**Q3: 如何给所有响应（含 500）加统一响应头？**
把逻辑写成纯 ASGI 中间件并注册在 `app.add_middleware` 时置于合适层级，或交给反向代理（nginx `add_header`）——边界在框架内时用 ASGI 原生写法，全局统一时交给网关。
