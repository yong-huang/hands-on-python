# 12 · JWT + OAuth2 认证：签名 cookie 思想的工业级放大

> JWT（JSON Web Token，带签名的自证凭据）把手工签名 cookie 的防伪思想
> 升级成工业标准的三段式 `header.payload.signature`——**签名防篡改、不保密、
> 不防过期**的结论原样成立。本实验用 FastAPI 的 OAuth2PasswordBearer + PyJWT +
> bcrypt 搭出完整认证链：登录签发 → 依赖解码验签 → 四路 401（缺失/篡改/错密钥/过期）全部实测。

## Background

这节讲认证的来路：在"服务端不存会话"的思路流行之前，登录态是怎么管理的，瓶颈在哪里。

没有它之前：Web 应用普遍用服务端 session（会话——服务端为每个登录用户维护的状态）管理登录态。用户登录后，服务端在内存或数据库里记一张会话表，并给浏览器发一个 session ID cookie（随机标识串），此后每个请求靠它查表找到用户。

两处开始撞墙：其一，服务扩到多个实例后，会话表必须集中共享（所有实例查同一张表）或做粘性转发（由负载均衡器把同一用户的请求固定发到处理过他上一次请求的那台实例），任何一侧重启都可能把在线用户踢下线；

其二，到了前后端分离、移动端与微服务互调的场景，基于浏览器 cookie 的会话体系接不过去，服务间要么重复登录、要么共享一套会话存储。

工程界的倒转方案：服务端不再保存会话，改为在登录时签发一个自带身份与过期时间、且无法伪造的自证凭据；此后每个请求带上它，服务端只需验签。这一思路的工业标准化产物就是 JSON Web Token（JWT）。

## What

这节定义 JWT 的结构与三条边界，并给出贯穿全文的心智模型。

JWT（RFC 7519 定义）是一种带签名的自证凭据格式：
三段 `header.payload.signature`，
各段做 base64url 编码（URL 安全的 base64——编码不等于加密）。

本实验让它跑在 OAuth2（开放授权协议标准）的 password flow 上：
登录接口验证用户名密码后签发 token，后续请求凭 token 证明身份。

| 段 | 内容 | 谁能读 | 作用 |
|---|---|---|---|
| header | 声明签名算法（本实验用 HS256） | 任何人 | 告诉验签方怎么验 |
| payload | claims——身份与元数据的键值对（`sub` 用户、`exp` 过期时间） | 任何人 | 携带身份 |
| signature | 对前两段的 HMAC（把密钥混入哈希的消息认证码，只有持密钥者能生成）签名 | 无密钥者不可伪造 | 防篡改 |

三条铁律贯穿本实验：**签名防篡改、不保密、不防过期**。
可以把 JWT 想象成塑封的景区门票：检票口只验证面防伪图案（签名）与有效期（`exp`），
不需要打电话回总部查购票登记（服务端不存会话）；

但和门票不同的是——票面是透明塑封，任何人都能读上面的信息（不保密），
而且票一旦印出来，有效期内单方面收不回（难吊销，补丁见 How It Works）。

一句话心智模型：**登录用 bcrypt 换信任，签发把信任装进 token；此后每个请求靠"验签 + 过期"两关重放信任——服务端不再存会话状态**。

## When to Use

这节讲 JWT 值得用的场景、不该用的边界，以及与 session 等方案的分工。

典型场景：

- 在做前后端分离或移动端 API 时——客户端不走浏览器 cookie，JWT 放请求头即可自证身份。
- 在做多个微服务认同一个登录态时——服务之间只需共享验签密钥，不必共享会话存储。
- 在做第三方开放接口的短期访问凭据时——签短命 token，泄露窗口可控。

何时不用：

- 单体应用且登录态必须能"强制下线、即时吊销"：服务端 session 一删即生效，JWT 做不到（补丁的代价见 How It Works）。
- 只在服务端渲染的简单网站：session + cookie 更直接，引入 JWT 是多一层复杂度。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| JWT | 无状态自证，吊销难 | 跨服务、多端 API 认证 |
| 服务端 session | 状态在服务端，可即时吊销 | 单体应用、需强杀登录态 |
| 不透明 token（本体无信息、每次查库校验的随机串） | 可随时作废，代价是每请求查库 | 需要即时吊销的 API 凭据 |
| 手工签名 cookie（lab 03） | 同一签名思想，非标准格式 | 自研小型 Web 应用 |
| API key | 长期静态凭据，粒度粗 | 服务器对服务器的简单调用 |

诚实预期：

- **/token 的参数用 query string 简化**：标准 OAuth2 password flow 用表单编码（`OAuth2PasswordRequestForm`），且必须走 HTTPS——演示环境从简，README 明确标注差异
- **用户表是进程内 dict**：教学聚焦认证链路本身；落库版本（bcrypt 哈希列 + 失败计数）见 lab 07 的书签应用，两者结构一致
- **HS256 密钥 ≥32 字节**：第一版用 15 字节密钥被 PyJWT 的 `InsecureKeyLengthWarning` 当场教育（RFC 7518 建议）——警告即规范，已如实改成长密钥

| 库 | 角色 | 关键 API |
|---|---|---|
| PyJWT | token 签发与验签 | `jwt.encode` / `jwt.decode` / `ExpiredSignatureError` |

## How It Works

这节按"拦截 → 验签 → 过期 → 密码校验"的链路拆机制，并与输出里的四路 401 互相印证。

### 四路 401：验签与过期是两道独立的关

输出里的四路 401 各对应一道防线：

- ① 无 token——`OAuth2PasswordBearer` 从 `Authorization: Bearer` 头提取凭据，缺失直接 401，请求到不了业务代码；
- ② 篡改签名段——HS256（HMAC-SHA256，共享密钥的哈希认证算法）验签不过；
- ③ 错误密钥签发的 token——格式完美，但签名必然不匹配。"密钥即主权"：验签方只信自己的密钥；
- ④ 过期 token——签名完全合法，但 `jwt.decode` 检查 `exp` 抛 `ExpiredSignatureError`。

②③ 拦"伪造"，④ 拦"超时"，两道关缺一不可——
lab 03 的结论（签名防篡改，不防过期）在标准库上原样成立。

同一个 `OAuth2PasswordBearer(tokenUrl="/token")` 声明还兼任文档开关：
`/docs` 的 Swagger 页面（FastAPI 自带的交互式 API 文档）右上角出现 Authorize 按钮，
登录后交互测试自动带 token——认证逻辑与文档按钮是同一个声明。

### 三段式的边界：payload 只是 base64

header（算法）.payload（claims）.signature（对前两段的 HMAC）各段 base64url 编码。
payload **只是 base64，不是加密**：`sub`/`exp` 任何人可读可解，
所以密码、隐私绝不能进 claims；签名只保证不可篡改——改一个字符验签就挂。

它与 lab 03 手写签名 cookie 是同一思想，JWT 多了标准化 claims 与生态互操作。

### 无状态的天花板：发出收不回

`exp` 让服务端拒绝过期 token，但已签发的未过期 token 无法单方面作废。工业界的补丁：短过期（15 分钟）+ refresh token 换新、黑名单表、token 版本号随密码修改递增。无状态的省，要用吊销的难来还。

### get_current_user：把三类解码失败分开捕获

```python
try:
    claims = jwt.decode(token, SECRET, algorithms=[ALGO])
except jwt.ExpiredSignatureError:
    raise HTTPException(401, "token 已过期")       # 特指过期：客户端该去刷新
except jwt.PyJWTError:
    raise HTTPException(401, "token 无效")         # 签名/格式/claims 问题
```

这段在做什么：解码失败按类型分流——过期特指（客户端该去刷新），
其余（签名、格式、claims 问题）归为无效；对外统一 401，对内文案有别。
你在输出里看到的 ② 与 ④ 两种 401 情形，就来自这两个 except 分支。

另外 `algorithms=[ALGO]` 白名单必不可少：不锁算法会让攻击者用 `alg: none`
（把算法字段改成"无签名"）或 RS256 混淆攻击绕过验签——经典 JWT 漏洞。

### bcrypt 与统一 401 的枚举防护

用户表只存 bcrypt（慢哈希密码算法：刻意耗 CPU，且自动混入随机盐——盐是每次哈希时拼进密码的随机值，同一密码每次哈希结果都不同，可防预计算表破解）哈希，脚本直接打印断言无明文。
校验用 `checkpw` 恒时比较（比较耗时与内容无关，防时序攻击——通过耗时差异推断秘密；
lab 03 的结论直接复用）。

响应面上，错误密码与用户不存在统一返回 401 同文案——
任何差异都是枚举用户名的侧信道（通过非预期通道泄露信息的漏洞）。

lab 07 的失败计数限流在这里同样适用（本实验聚焦 token 链路未重复实现）。

## Pitfalls & Q&A

这节收四个实测踩过的坑，再答三个方案取舍问题；每条坑按现象、原因、解法展开。

踩坑清单：

- **HS256 密钥太短**。现象：PyJWT 2.13 对 <32 字节密钥发 `InsecureKeyLengthWarning`（RFC 7518 建议），本实验第一版实测中招。原因：密钥长度是规范要求。解法：密钥从环境变量注入且长度达标。
- **payload 里放敏感信息**。现象：token"看着像加密"就往里塞隐私。原因：base64 一解就见，signed ≠ encrypted（lab 03 的坑原样重演）。解法：claims 只放身份与过期时间。
- **不锁 `algorithms` 白名单**。现象：验签代码"能跑"。原因：解码未显式 `algorithms=["HS256"]` 时，`alg: none` 攻击可让验签形同虚设。解法：解码时必须显式锁定算法。
- **把 JWT 当会话存储**。现象：claims 越塞越多、token 越来越长。原因：误把无状态凭据当数据库。解法：claims 只放身份（sub/权限），业务状态查库——token 越大每次请求越贵，且无法中途修改。

深入问答：

**Q1: JWT 与服务端 session 的取舍？**
JWT 无状态、跨服务信任友好，代价是吊销困难（短过期 + refresh 补偿）；session 状态在服务端、可即时吊销，代价是共享存储。登录态必须可强杀选 session，微服务间信任选 JWT（分工表见 When to Use）。

**Q2: refresh token 为什么要配套 access token？**
access token（短命访问凭据）控制在 15 分钟级别，压缩泄露窗口；refresh token（长命换新凭据）只用于换新 access，且服务端可对它单独吊销（存库）。两者分离在"无状态便利"与"可吊销安全"之间取平衡。

**Q3: 密码哈希用 bcrypt 还是 SHA256 加盐？**
SHA256 太快，GPU 每秒数十亿次暴力尝试；bcrypt/scrypt/argon2 是慢哈希（刻意耗 CPU/内存），且盐内嵌格式串。慢是特性不是缺点——把离线爆破的成本抬到不可行。
