## Background

这节回答两个问题：单文件 Flask 脚本怎么长成真实项目，以及账号系统为什么不能自己随手拼。

跟着 Flask 官方入门教程写过第一版的人，通常把所有路由写进一个 `app.py`：`app = Flask(__name__)` 在模块顶层，配置直接写死，几十个视图函数从上往下排。

这堵墙在项目变大时撞上来：路由前缀靠手写、命名容易冲突；想在测试里换一个内存数据库，发现配置与代码耦合在模块顶层，不改代码就换不掉；用户系统更是各自为战——密码明文落库、登录接口不设防，一次拖库（攻击者把整张用户表偷走）或脚本化爆破就足以出事故。

Flask 官方教程给出的组织方式后来成为社区标准起手式：用"可插拔的分区模块"拆视图，用"创建应用的函数"隔离配置与实例，把密码存储与登录防爆破当成不可妥协的安全底线。本实验把这套做法完整跑通，并逐点用断言钉死。

## What

这节定义两个组织机制（蓝图、应用工厂）与登录认证的三段链路，并给出贯穿全文的心智模型。

**蓝图（Blueprint）**——Flask 的分区注册机制：把一组视图、模板和统一的 URL 前缀打包成一个可插拔模块，主应用只负责挂载。

**应用工厂（application factory）**——把"创建 Flask 应用"封装成 `create_app(config)` 函数：每次调用产出一份独立实例，配置、数据库、蓝图各自独立。

登录认证在本应用里走三段：注册、登录、守卫。一句话心智模型：**注册把密码变成哈希，登录把身份变成 session，守卫把 session 变成 g.user——三层各管一段，谁也不越界**。

其中 session 是 Flask 的签名 Cookie 会话对象，内容存浏览器、签名防篡改；g 是 Flask 的请求级命名空间，一个请求内共享。

可以把应用工厂想象成奶茶店的加盟配方：同一份配方（代码）在不同城市（测试/开发/生产）开出各自独立的门店（实例），各用各的原料库（数据库）。但和连锁店不同的是，这些门店之间没有任何共享仓库——输出 [1] 里"app A 注册了 alice，app B 用户数 = 0"展示的正是这种完全隔离。

| 机制 | 在本应用中的形态 | 验收方式 |
|---|---|---|
| 应用工厂 | `create_app(test_config)`，多实例隔离 | 两个实例数据互不可见 |
| 双蓝图 | `/auth/*` 管账号，`/links/*` 管书签 | url_map（Flask 应用对象上的路由注册表）分区 + 全流程状态码 |
| 密码哈希 | werkzeug scrypt，只存哈希不存明文 | 直接查库验证 |
| 登录限流 | 失败计数锁定，先于密码校验 | 锁定后正确密码也 429 |

## When to Use

这节给判断力：什么规模的项目值得引入蓝图与工厂，哪些场合不必。

典型场景：

- 在做视图数量持续增长的 Flask 项目时——按功能拆成 auth/links/admin 等蓝图，URL 前缀统一管理，路由不再互相踩脚
- 在做需要测试与多环境的项目时——`create_app(test_config)` 让测试挂内存库、开发挂本地库、生产挂远端库，代码只有一份
- 在做任何有用户账号系统的服务时——哈希存储、统一 401 防枚举、失败计数锁定是底线配置，与业务无关

何时不用：

- 几个视图的原型或 demo：`app = Flask(__name__)` 单文件更直接，拆蓝图是过早抽象
- 纯内部工具、无用户体系：auth 链路可以整个省掉（但只要存了任何凭证，哈希这条仍不可省）
- 已经深度使用 Django 的项目：自带用户系统与分区机制，不必混用两套

同类方案对比：

| 方案 | 与本实验做法的差异 | 什么时候选它 |
|---|---|---|
| 单文件 `app = Flask(__name__)` | 无工厂、无分区，配置写死在模块顶层 | 原型、小工具 |
| Flask-Login 扩展 | 第三方托管登录态（加载用户、记住我） | 不想手写 g.user 装载与守卫时 |
| Django auth | 框架内置的用户/权限/会话体系 | 项目本身就基于 Django |
| FastAPI 依赖注入守卫 | 用 `Depends` 声明式做认证（见 lab 09） | 项目本身是 FastAPI |

## Quick Start

这节把演示跑起来：一条命令、一段真实输出、四条诚实预期。

再加两道安全底线：密码绝不能明文落库（werkzeug scrypt），登录接口必须扛暴力破解（失败计数锁定）。这四件事没有一个能靠"背概念"回答，本实验全部用断言钉死。

```bash
cd web/07_flask_auth_app
source ../.venv/bin/activate
python3 flask_auth_app.py    # 完整演示（4 个小节，内置验收断言）
```

真实输出节选（Flask 3.1.3）：

```
========================================================
[1. 应用工厂与蓝图注册：create_app 的隔离性（验收点）]
========================================================
  蓝图注册: ['auth', 'links']；url_map 含 /auth/* 与 /links/*（url_prefix 分区）
  app A 注册了 alice；app B 用户数 = 0——同一份代码，两个独立世界

========================================================
[2. 全流程：注册 / 登录 / 加书签 / 登出 / 未登录守卫（验收点）]
========================================================
  未登录 GET /links/ → 302 → /auth/login（蓝图 before_request 守卫）
  注册成功 → 302；错误密码登录 → 401（错误文案与剩余次数回显）
  正确密码登录 → 302 → /links/（session 存 user_id）
  添加书签 → 列表页显示「Flask 官方文档」· 我的书签（1）
  登出 → session 清空 → 再访问 /links/ 又是 302 守卫

========================================================
[3. 密码只存哈希：直接查库验证（验收点）]
========================================================

  明文 'wonderland' 不在库里（scrypt 单向哈希，盐值内嵌格式串）

========================================================
[4. 限流：5 次错误后锁定，正确密码也进不来（验收点）]
========================================================
  连续 5 次错误密码 → 5 × 401（每次提示剩余次数）
  第 6 次（仍错误）→ 429 Too Many Requests
  锁定后用【正确】密码 → 仍是 429：锁定检查先于密码校验，爆破没有第二次机会
  生产补强：计数带时间窗（如 15 分钟）+ 按 IP 双重限流 + 解锁需过期或管理员介入
```

诚实预期：

- **本应用表单未挂 CSRFProtect**：教学聚焦蓝图/工厂/认证；真实上线必须补上（lab 05 的 `CSRFProtect(app)` 一行即可，本应用表单结构完全兼容）
- **用户不存在与密码错误返回同一响应**（都是 401）：防用户名枚举；但失败计数器只存在于已注册用户身上，探测者可借此推断用户名是否存在——生产应把计数也记在 IP 维度
- **限流是纯计数器**：无时间窗（15 分钟自动解锁需自己加）、不按 IP、重启即清零——生产补强清单见 §4 输出末行
- **运行后不落任何文件**：全部 sqlite 库建在 `tempfile.TemporaryDirectory`，进程退出自动清理

## How It Works

这节按请求的顺序拆开四个机制，并解释输出里每个验收现象的来源；最后给出最核心的一处安全代码与完整请求链路。

### 应用工厂：create_app(test_config)

工厂把"创建应用"变成函数调用：每次产出独立实例——各自的 `SECRET_KEY`、各自的 engine、各自注册蓝图。输出 [1] 里"app A 注册了 alice，app B 用户数 = 0"就来自这份隔离。

这正是测试环境（内存库）、开发（本地库）、生产（远端库）共用一份代码的方式，也是 Flask 官方教程与大型项目的标准起手式。`app.teardown_appcontext(close_db)` 则保证每个请求结束时 session 被关闭——lab 06 的"一请求一 session"在这里落地。

### 双蓝图与登录态流转

auth 蓝图（`url_prefix="/auth"`）管注册/登录/登出；links 蓝图（`/links`）管书签。

登录态三级流转：**登录成功 → `session["user_id"]`**（签名 Cookie 承载，思想见 lab 03）；**每个请求开始 → `before_app_request` 查库装 `g.user`**（app 级钩子，g 的用法见 lab 04）。

**links 蓝图 `before_request` 检查 g.user**——蓝图级守卫一处声明，全蓝图视图生效，未登录一律 302 去登录页。输出 [2] 第一行的 302 就是这条守卫发出的。

### 密码哈希：scrypt 与单向性

`generate_password_hash`（werkzeug——Flask 底层的工具库，哈希函数由它提供；默认 scrypt——一种刻意消耗内存的慢哈希算法）产出 `scrypt:32768:8:1$盐$哈希` 格式串。

参数、盐、哈希自包含（盐是一段随机数据，与密码拼在一起再哈希，让相同密码得到不同哈希、预计算对照表失效），校验时 `check_password_hash` 原样解析。直接开 sqlite 文件查表：明文不在库里。

哈希的意义：拖库也拿不到密码（只能离线暴力试）；scrypt 的内存难度大幅抬高 GPU 暴力破解的成本。

### 登录限流：先于密码校验的闸门

`failed_attempts` 计数器挂在用户行上：错误一次 +1，成功登录清零；达到 5 次后，login 视图**第一件事**就是返回 429——密码对错根本不看。关键断言是"锁定后用正确密码仍 429"（输出 [4] 最后一行）：如果闸门放在密码校验之后，攻击者猜中密码的那一次就登进来了，限流形同虚设。

### 登录时为什么要 session.clear()

```python
user.failed_attempts = 0
db.commit()
session.clear()                  # 防会话固定（session fixation）
session["user_id"] = user.id
```

如果登录前后 session 是同一个，攻击者预先种下的 session 值（同站 XSS 或共享电脑场景）在登录后依然有效——先清空再写入等于换了新身份载体。lab 03 讲过签名 cookie 防篡改；clear + 重写是"换票不补票"。

### 一次带登录态请求的完整链路

WSGI（Python Web 应用与服务器之间的标准接口）收到请求压上下文栈（见 lab 04）→ `before_app_request` 从 session 读 user_id 装载 g.user → 蓝图守卫检查 g.user。

视图通过 g.db 拿 session 查库（见 lab 06）→ after_request/teardown 收尾关 session → 弹栈。登录态的载体是签名 session Cookie（见 lab 03）。

## Pitfalls & Q&A

这节先列五个真实踩过的坑（现象、原因、解法），再补三个有增量的深入问题。

踩坑清单：

- **密码哈希校验写成 `if user.password_hash == password`**：等于明文比较；永远 `check_password_hash`，它做恒时比较（比较耗时与内容无关，攻击者无法靠响应快慢一位位猜出哈希）且解析盐
- **"用户不存在"与"密码错误"返回不同提示**：帮攻击者枚举有效用户名；两者统一 401 同文案
- **锁定闸门放在密码校验之后**：本实验专门断言正确密码也被 429——顺序错了，限流就拦不住爆破
- **把业务逻辑写进 `__init__.py`**：工厂只负责装配（配置/扩展/蓝图），视图全在蓝图模块里；`__init__.py` 超过 40 行就该反思
- **忘了 teardown 关 session**：连接积压、SQLite 锁库；`teardown_appcontext` 一行根治（本项目 db.py 现成）

**Q1: 什么是应用工厂模式？解决什么问题？**
多实例与配置隔离已在 How It Works 讲过；这里补两点增量：工厂把扩展绑定延迟到 `create_app` 内部，避免循环导入；代价是视图里不能直接 import app 变量，要用 `current_app`（指向当前请求所辖应用对象的代理）。

**Q2: 密码为什么必须哈希存储？scrypt/bcrypt/argon2 的共同点？**
拖库防护：单向哈希+盐使明文不可逆。三者都是**慢哈希**（刻意耗 CPU/内存，暴力破解成本高），且盐内嵌格式串。与之对比 SHA256 是快哈希，GPU 每秒数十亿次，不适合存密码。

**Q3: 登录接口的防爆破清单？**
失败计数锁定（本实验，注意先于密码校验）、计数带时间窗自动解锁、按 IP+账号双维度、验证码/递增延迟、统一"用户不存在/密码错误"响应防枚举、全站 HTTPS。
