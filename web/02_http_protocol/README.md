# 02 · HTTP 协议观察器：手搓报文，看清 wsgiref 藏了什么

> HTTP 的细节——请求报文怎么拼、响应怎么解析、body 读到哪算完、连接能不能复用——
> 平时都被 requests 一类库代劳。本实验下到 socket 层：**自己拼请求报文、自己解析响应、
> 自己实现 chunked 解码和 keep-alive 复用**——做完再看 `requests.get()` 那一行代码，
> 你知道它背后发生了什么。全程只依赖标准库，服务端也是本实验自带的一个 60 行极简 HTTP/1.1 服务。

## Background

这节讲 HTTP 报文与连接模型的来龙去脉：1.0 时代的默认做法、它在哪里撞墙、1.1 如何作答。

HTTP（HyperText Transfer Protocol，超文本传输协议——浏览器与服务器之间的应用层文本协议）在 1.0 时代的默认模式是每个请求新建一条 TCP（Transmission Control Protocol，传输控制协议——操作系统层面负责在两台机器间可靠收发字节流的连接）连接，用完即断。

建立与拆除 TCP 连接有真实成本：每次建连都要来回三次握手（双方各发确认包才能开始传数据），页面引用几十个资源时，延迟随请求数叠加。

更隐蔽的问题在 body 的结尾：没有定界机制时，客户端只能靠"服务器关闭连接"来判断响应读完了。想在一条连接上先后发多个请求，就必须回答两个新问题——body 读到哪里算完？连接还能不能复用？

HTTP/1.1 把答案写进了协议本身：`Connection` 头管理连接复用（即 keep-alive），`Content-Length` 与 `Transfer-Encoding: chunked` 互斥地负责体定界。这三件事平时被库代劳，本实验把它们全部做成可断言的实测。

## What

这节给 HTTP 报文下定义，并建立一个能装下定界与复用的心智模型。

一条 HTTP 报文是四段式文本：起始行 + 头部 + 空行 + 体。所谓解析，就是按 CRLF（回车换行符 `\r\n`）切字符串：

```
GET /text HTTP/1.1\r\n        ← 起始行（请求行；响应侧是状态行）
Host: 127.0.0.1\r\n           ← 头部，一行一个 k: v
Accept: text/plain\r\n
\r\n                          ← 空行，头结束的标记
<151 字节的体>                 ← 体，定界方式看头部
```

三个必须下到字节层才看得见的事实：

- 报文是纯文本四段式，解析就是按 CRLF 切字符串
- body 的结束由两种互斥机制定界：`Content-Length` 先知长度，或 `Transfer-Encoding: chunked` 分块流式
- 连接可以复用（keep-alive），复用与否看服务端 accept（服务器接收一条新连接的调用，每条新连接只执行一次）计数器一测便知

心智模型：可以把一条报文想象成贴着快递面单的包裹——起始行和头部是面单（去向与物品声明），空行是面单与货物的分界线，体是货物本身。但和真实包裹不同的是，"货物到哪算完"不由包裹的物理边界决定，而由面单上的声明说了算——所以解析器必须先读完头部才知道体怎么读。

## When to Use

这节讲什么场景值得下到 socket（操作系统提供的 TCP 编程接口，应用通过它收发原始字节流）层手写 HTTP，什么时候用现成库就好。

典型场景：

- 排查"库外"问题的时候：请求超时、keep-alive 连接被提前断开、响应体截断——这类问题要看到原始字节才能定位
- 自己写服务端或内部工具的时候：哪怕几十行的极简服务，也要答对体定界与连接复用这两道题
- 校验自己对协议的理解的时候：手搓解析与 `http.client` 逐项一致，就是本实验的验收标准

何时不用：日常调用 HTTP API 直接用 `requests`——它自动补头、自动解码、管理连接池；手写 socket 的价值在理解协议与排查底层，不在开发效率。

同类方案对比：

| 方式 | 差异 | 什么时候选它 |
|---|---|---|
| `requests` | 自动补头、自动解码、连接池 | 业务代码发请求 |
| `http.client` | 标准库，可控但不裸 | 不想装第三方包的脚本 |
| 裸 socket（本实验） | 报文逐字节自己拼、自己切 | 学习协议、排查底层问题 |

```
  解码还原 151 字节，与原文逐字节相等 ✓

========================================================
[4. keep-alive 复用：3 个请求 1 条连接 vs 一请求一连接]
========================================================
  复用组: 3 个请求（含 1 个 POST）共用 1 条连接，服务端 accept 次数 = 1
  对照组: 2 个请求 2 条连接（Connection: close），服务端 accept 次数 = 2
  keep-alive 省 TCP 握手/慢启动——浏览器同域 6 连接、连接池，全是它的后裔

========================================================
全部断言通过 ✓ 手搓解析与 http.client 逐项一致、chunked 逐字节还原、
keep-alive 3 请求 1 连接（服务端计数器为证）
```

诚实预期：

- **复用组的"3 请求 1 连接"由进程内计数器断言**（服务端与客户端同进程，`STATS` dict 共享）——跨进程时把计数器换成响应头回显即可，结论不变
- **手搓客户端按 Content-Length 提前收工**：keep-alive 连接不会主动关闭，若不按头定界而傻等对端断开，就会白等一个 idle timeout——这本身就是定界机制存在的理由

| 工具 | 作用 |
|---|---|
| `socket` | 收发原始 TCP 字节流，报文从这里逐字节进出 |
| `http.client` | 标准库 HTTP 客户端，§2 中作为手搓解析的对照基准 |

## How It Works

这节按一次请求的服务端处理顺序拆机制：报文怎么切开、体怎么定界、连接怎么复用、POST 的体怎么读。

### 头读够与体读够：两个循环、两种边界

解析器没有任何魔法：`raw.partition(b"\r\n\r\n")` 一刀分开头和体，头部再按行切。服务端用两个循环分别等"头读够"和"体读够"：

```python
while CRLF.encode() * 2 not in buf:   # 头：边界是"空行"这个标记
    buf += conn.recv(4096)
head, _, buf = buf.partition(CRLF.encode() * 2)
need = int(headers.get("content-length", 0))
while len(buf) < need:                # 体：边界是头里声明的数字
    buf += conn.recv(4096)
payload, buf = buf[:need], buf[need:] # 多读的部分是下一条请求，留在 buf 里
```

头和体的定界机制不同：头靠标记（空行），体靠声明（数字）。输出 §1 那行"状态行 → 96 字节头部 → 空行 CRLF → 151 字节 body"的拆解，就是这两个循环先后完成的活。

最后 `buf[need:]` 保留粘包余量——keep-alive 下一条请求的头可能已经躺在缓冲区里，这一行处理的就是"TCP 粘包"的本质：**TCP 只有字节流，报文边界是应用层自己切的**。

手写解析器与 `http.client` 对同一响应给出逐项相同的状态/头/体（§2 验收点），说明标准库做的也是同一件事，只是把边界情况（多行头、大小写、HTTP/0.9 兼容……）处理得更完备。

### body 定界：Content-Length vs chunked

有 `Content-Length: N` 时，读到恰好 N 字节为止，多一节都是下一条报文的（keep-alive 下按长度切分是正确性要求，不是优化）。没有长度声明（流式场景）时用 `Transfer-Encoding: chunked`：每块前置一行十六进制块长，`0\r\n\r\n` 终止：

```
14\r\n<20 字节>\r\n83\r\n<131 字节>\r\n0\r\n\r\n
```

解码器 7 行写完：读块长行 → 读对应字节 → 循环到 0 号块。输出 §3 的块长序列 `[20, 131, 0]`（HEX: `14/83/0`）就是这套格式的实测——`14` 是十六进制，等于十进制 20；末块 0 是终止块；解码结果与原文逐字节相等。

### keep-alive：accept 计数器说话

复用组同一个 socket 对象连发 GET/POST/GET 三个请求，服务端 `accept()` 只执行 1 次；对照组每请求声明 `Connection: close`，2 个请求 2 条连接——输出 §4 的两组数字正是这份对照。

服务端循环里顺手实现了 keep-alive 的标配策略——**空闲超时**（`recv` 超时就关闭连接），生产服务器的 keep-alive timeout 是同一件事。

### POST 与 Content-Length 请求头

请求体同样要定界：手搓 POST 必须自带 `Content-Length: 4` 头，服务端按它把 `ping` 从流里切出来再回显。`http.client`/`requests` 帮你自动加这个头——输出 §4 复用组里"含 1 个 POST"，省掉的正是这一步。

## Pitfalls & Q&A

这节收录开发过程真实踩中的四个坑（现象 + 原因 + 解法）与两个深入问题。

- **`Content-Length` 与实际 body 不一致**：现象是客户端按头等 4 字节永远"没读够"，干等超时，服务端同时在 keep-alive 循环里等下一条请求也超时，线程崩溃、连接被 RST（Reset，TCP 层的强制重置信号，对端立即作废这条连接）。原因是 /echo 路由第一版把头写成了请求体长度（4），响应体却是 9 字节。解法是让头的数字与真实发送的字节数严格一致——一个头的错误同时打挂两端，这是全实验最深的一坑
- **keep-alive 连接没有 idle timeout**：现象是对端不发下一条请求时 `recv` 永远阻塞，线程悄悄泄漏。原因是连接不会主动关闭。解法是给 `recv` 设超时、超时即关闭（即 How It Works 说的空闲超时），真实服务器全部带 keep-alive timeout
- **往"空行之后"追加头**：现象是后拼的"头"出现在 body 位置。原因是 `craft_request(...)` 的返回值已经以空行结尾，再 `+ b"Connection: close"` 会把头拼进体里。解法是头必须拼在空行之前
- **用字符串拼接响应头**：现象是 `f"{k}: {v}"` 解包直接 ValueError。原因是头列表约定为 `(k, v)` 元组，`"Connection: keep-alive"` 字符串混进去无法解包。解法是统一用元组形式存头

**Q2：WSGI 里的 `wsgi.input` 和本实验什么关系？**

server（如 wsgiref/gunicorn）做完了本实验服务端的活：按定界机制把 body 从 TCP 流里切出来，包成 `wsgi.input` 文件对象交给应用——所以 Flask 的 `request.data` 直接可读，不用关心 chunked。
