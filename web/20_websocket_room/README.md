# 20 · ⚠️ 选做——WebSocket 实时聊天室：长连接与广播

> HTTP 的"请求-响应"配对在实时场景失灵——聊天室需要**服务端主动推**。
> WebSocket 一次握手升级为长连接，广播就是遍历房间连接列表逐个 send。本实验用
> TestClient 双客户端实测：A 发 → B 收、断开减员、HTTP 端点查在线人数——
> 全程只依赖 FastAPI 自带的 WebSocket 支持。

## Background

这节从 HTTP 的一个天生限制说起。HTTP 是"请求-响应"模型：客户端不发问，服务端就不开口。想让网页及时看到新消息，最早的通用做法是轮询——客户端定时发 GET 问"有新消息吗"，而多数时候得到的回答是"没有"。

轮询的两难在于间隔：设得短，大量空请求白白打满服务器；设得长，消息延迟肉眼可见。长轮询（服务端把请求 hold 到有数据才回答）缓解了空转，但每条消息仍要重新走一轮完整 HTTP 请求，服务端依旧无法主动开口。

WebSocket 协议由此出现：客户端发一次带 `Upgrade: websocket` 头的 HTTP 握手，成功后这条连接升级为持久的双向通道——服务端随时能推，客户端随时能发。聊天室是它最经典的应用场景，本实验就在 FastAPI 里实现一个可断言的最小聊天室。

## What

这节定义 WebSocket 是什么，以及本实验聊天室的组成。

WebSocket（一种在单条 TCP 连接上提供全双工——双向同时收发——通信的协议）由一次 HTTP 握手升级而来，之后不再有请求-响应的配对。一句话心智模型：**握手一次，连接归会话——此后服务端可随时主动推，客户端也可随时发，没有配对关系**。

可以把 WebSocket 想象成接通的电话线：拨号一次（握手），之后双方随时开口，不必每句话都先"喂？"再等对方回"喂？"（那是 HTTP 的请求-响应）。但和电话不同的是：服务端要在内存里记着每一通还通着的电话，对方挂断要自己发现并清线。

本实验聊天室的组成：

| 部件 | 职责 |
|---|---|
| WebSocket 端点 | 接入房间，收发聊天消息 |
| `ConnectionManager` | `rooms: dict[str, list[WebSocket]]`，连接增删与广播的持有者 |
| `/rooms/{room}/count` | HTTP 端点，核对服务端记录的在线人数 |
| `/` 极简聊天页 | 浏览器手测入口，多开标签页体验广播 |

## When to Use

这节补判断力：什么场景值得上 WebSocket，什么场景轮询反而更划算。

- **在做聊天、协同编辑、行情推送**这类服务端要主动、高频推送的场景的时候——消息必须由服务端发起，连接值得长期维持
- **在做在线状态、多人房间人数这类实时展示**的时候——广播加状态字段即可，无需客户端反复询问
- 何时不用：低频状态更新（几分钟一条）用轮询或 SSE 足矣；纯请求-响应的增删改查，普通 HTTP 更简单

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| HTTP 轮询 | 客户端定时 GET，实现最简单、实时性最差 | 低频更新、对延迟不敏感 |
| 长轮询 | 服务端 hold 请求到有数据 | 兼容旧环境、推送频率很低 |
| SSE（Server-Sent Events——服务端单向推流的 HTTP 协议） | 单向推、基于纯 HTTP | 只需服务端到客户端的单向流 |
| WebSocket | 全双工长连接，代价是连接状态管理 | 聊天、协同、行情等双向实时场景 |

诚实预期：

- **广播包含发送者自己**：A 也会收到 "Alice: hi"（回声），断言里先消费自己的回声再等对方消息——前端通常按昵称把回声渲染成右侧气泡
- **广播是逐个 `await send`**：一个慢客户端会拖慢整个广播循环——这就是背压（backpressure：下游消费速度跟不上上游发送速度，压力沿链路反向传导）——生产要按客户端写队列异步刷
- **未实现 Litestar（另一个 Python Web 框架）对照路径**：清单标注二选一，本站选了 WebSocket 主线；Litestar 的 DI（依赖注入——由框架构造并传入依赖对象的机制）对照可按 lab 09 的方法自行扩展
- **TestClient 之外建议浏览器手测**：应用内置 `/` 极简聊天页，真实浏览器多开两个标签页即可体验广播

## How It Works

这节按"握手 → 入房 → 收发 → 断开"的生命周期拆机制，并解释广播循环里的一处防御写法。

### WebSocket 握手与生命周期

WebSocket 以 HTTP GET（带 `Upgrade: websocket` 头）开始握手，
成功后这条 TCP 连接升级为全双工通道。

服务端 `await websocket.accept()` 接纳连接；
此后 `receive_text`/`send_json` 双向自由——**没有请求-响应配对**，
消息的语义由应用层自己定义（本实验用 JSON 的 text 字段）。

### 连接管理器：房间就是列表

`ConnectionManager` 的 `rooms: dict[str, list[WebSocket]]` 是全部状态——
connect 追加、disconnect 移除、broadcast 遍历。

在线人数、房间隔离、私聊（定向 send）、踢人（close 指定连接）都是对这份列表的操作。
你在输出里看到的"房间 1 人""房间剩 1 人"，就是对这份列表做计数的结果。

### 断线感知与清理

对端断开后，服务端挂起的 `receive_text()` 抛 `WebSocketDisconnect`——
except 分支里移除连接并广播离开。
输出里"Bob 断开 → A 收到系统消息 · 房间剩 1 人"就来自这条清理路径；
人数准确性完全依赖它。

广播的 `count` 字段随每条消息携带，客户端可实时渲染在线人数（本实验用它断言减员）。

### 广播为什么要拷贝列表

```python
async def broadcast(self, room: str, text: str) -> None:
    for ws in list(self.rooms.get(room, [])):  # 拷贝遍历
        await ws.send_json({"text": text, "count": ...})
```

`await send` 期间事件循环（asyncio 调度协程运行的机制）可能调度其他协程——某客户端断开会让 `disconnect` 修改原列表。直接遍历原列表会 `RuntimeError`（列表在迭代中被修改）或跳过/重复，拷贝一份遍历是并发容器的标准防御。

## Pitfalls & Q&A

这节先列四个踩坑点，再答四个深入问题。

**用 `send_json` 发聊天内容、两端协议不一致**：现象是广播变成 `Alice: {"text":"hi"}`；原因是服务端 `receive_text` 收到的是 JSON 字符串原样文本，两端没有约定同一套消息协议（本实验真实踩中）；解法是统一消息协议——本实验统一用 JSON 的 text 字段。

**忘记处理 `WebSocketDisconnect`**：现象是人数只增不减；原因是断开的连接留在列表里，广播持续向死连接发送；解法是 except 分支移除连接并广播离开。

**广播不含发送者时漏掉回声断言**：现象是从某条起断言全部错位失败；原因是客户端消息队列顺序（加入广播 → 回声 → 对方消息）必须逐条对齐，跳一条后面全错位；解法是逐条消费对齐，跳过回声时同步调整队列预期。

**房间人数只信客户端**：现象是前端人数与真实连接数不符；原因是客户端本地状态可能过期；解法是以服务端列表为准并暴露 HTTP 端点核对——本实验 count 断言走的就是服务端状态。

**Q1: WebSocket 连接在多 worker/多实例部署下的问题？**
连接是有状态资源且分散在各进程内存里——
A 在 worker1、B 在 worker2 时广播够不着。

解法：消息走 Redis Pub/Sub（发布-订阅频道）等共享通道，
各 worker 订阅后推给自己的连接；或会话粘性（同一用户固定路由到同一实例）+ 房间路由。

**Q2: 服务端怎么感知客户端断线？心跳的意义？**
TCP 断开时 `receive` 抛 WebSocketDisconnect；但半开连接（如拔网线）感知不到——需要应用层心跳（定时 ping/pong + 超时踢除），否则"在线人数"虚高、死连接堆积。

**Q3: 广播的背压怎么解？**
每连接独立发送队列 + 异步刷写，慢消费者限流或踢除；消息体尽量小、房间分组广播缩小扇出（一次广播要触达的连接数）。

**Q4: FastAPI 里 WebSocket 端点和 HTTP 端点能共存吗？认证怎么做？**
同一 app 天然共存（同一 ASGI 栈——异步服务器网关接口，FastAPI 的运行层）。

WS 认证通常在握手阶段做：cookie/token 作为查询参数或首帧凭证，依赖 `websocket.headers` 读取——拒绝就在 accept 之前 close。
