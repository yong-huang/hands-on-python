# 05 · 模板与表单：Jinja2 渲染与两道输入防线

> 视图直接返回 dict 还不够——真实服务要返回 HTML。本实验把服务端渲染三件套一次配齐：
> **Jinja2 模板**（base.html 继承 + 宏渲染字段 + 自定义过滤器 + 自动转义）、
> **WTForms 校验**（必填/长度，错误文案随表单回显）、**CSRF 防线**（CSRFProtect 全局
> 拦截无 token 的 POST）。XSS 输入存得进库、渲染出来是安全文本——用 test_client
> 把"防线分层"四个字做成可断言的事实。

## Background

这节讲动态网页三要素——模板、表单校验、CSRF 防护——各自在解决什么历史问题。

没有模板引擎之前，服务端用字符串拼接生成 HTML：`"<h1>" + name + "</h1>"`。痛点一：布局重复，每个页面都从头拼一遍导航与页脚。

痛点二：拼接不转义，用户名里带 `<script>` 就成了存储型 XSS（Cross-Site Scripting，跨站脚本攻击——注入页面、被其他访客浏览器执行的恶意脚本）的入口。

表单处理同样全手工：每个字段手写 if 判空、判长度，错误文案各写各的。更被动的是"别的网站替用户提交表单"这件事——CSRF（Cross-Site Request Forgery，跨站请求伪造——借用户浏览器里的登录态发恶意请求）在早期 Web 几乎无解，直到"服务器签发、表单携带的随机 token"成为通行做法。

Flask 把三件事配成套装：Jinja2（Flask 内置的模板引擎）负责渲染——继承、转义都内建；WTForms（把字段与校验规则声明成 Python 类的表单库）负责输入校验；Flask-WTF 的 CSRFProtect 负责 CSRF 拦截。本实验把这条装配线跑通，并逐道断言。

## What

这节给出服务端渲染三件套的定义，以及围绕表单输入的三个安全事实。

服务端渲染（server-side rendering——服务器把数据填进模板、直接吐出完整 HTML 的方式）在本实验由三件套完成：

- Jinja2 模板：base.html 继承 + 宏渲染字段 + 自定义过滤器 + 自动转义
- WTForms 校验：必填/长度声明，错误文案随表单回显
- CSRF 防线：CSRFProtect 全局拦截无 token 的 POST

三个必须亲手验证的安全事实：

- **CSRF 攻击为什么被 token 一招破解**——恶意站点诱导浏览器发跨站 POST，但拿不到埋在你表单页里的随机 token
- **CSRFProtect 与 FlaskForm 校验是两道不同的闸**——前者在视图之前拦截（400），后者在视图里管格式（200 回显错误）
- **转义发生在渲染出口而不是入库口**——`<script>` 能合法存进存储，Jinja2 渲染时把它变成无害文本，`|safe` 是唯一豁免口

一句话心智模型：**GET 渲染表单时埋 token，POST 回来先过 CSRF 闸（400 拒绝）再过格式闸（200 回显），全过才落库 + flash + 302**。

可以把这条流水线想象成机场安检：第一道闸核对"票是不是本人发的"，第二道检查"行李是否合规"，全过才放行。但和机场不同的是，第一道闸设在业务代码之前——被拦下的请求根本到不了视图函数。

## When to Use

这节讲服务端渲染与表单防线适合什么场景，什么时候不这么搭。

典型场景：

- 做内容站、管理后台、多页表单流程的时候：服务端渲染直接出完整 HTML，模板继承让布局只维护一处
- 接收用户输入并落库的时候：WTForms 声明式校验 + 渲染出口自动转义，两道默认防线开箱即得
- 页面需要"提交成功提示一次"的时候：flash 消息 + PRG 模式是现成方案

何时不用：纯 API 后端只返回 JSON，用不上模板渲染；前后端分离的页面由浏览器端框架渲染 HTML，服务端不再出页面——但输入校验与转义的责任仍在，只是换了执行位置。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| Jinja2 服务端渲染 | 服务器出完整 HTML，继承复用布局 | 内容站、后台、表单流程 |
| 字符串拼接 HTML | 转义与复用都要自己扛 | 几乎不选 |
| 前端框架渲染（React/Vue 等） | HTML 在浏览器端生成 | 重交互的前后端分离应用 |
| 手写校验 if | 每字段重复劳动，无统一错误回显 | 字段极少的一次性脚本 |

## Quick Start

这节实测四条验收点：CSRF 拦截、合法提交落库、自动转义，外加格式校验的回显行为。

前置条件：依赖 Flask 与 Flask-WTF，使用框架阶段的公共虚拟环境。

```bash
cd web/05_flask_templates_forms
source ../.venv/bin/activate
python3 flask_templates_forms.py    # 完整演示（5 个小节，内置验收断言）
```

真实输出节选：

```
========================================================
[2. CSRF 防线：无 token 的 POST 走不到视图（验收点）]
========================================================
  不带 csrf_token 的 POST → 400（CSRFProtect 在视图之前拦截）
  原理：token 由服务器签发并埋进表单，恶意站点诱导的跨站 POST 拿不到它
  伪造 token 的 POST      → 400（签名校验不过）

========================================================
[4. 合法提交：302 落库 + flash 消息（验收点）]
========================================================
  带 token 合法提交 → 302 重定向，存储落库 1 条
  重定向后页面：flash「留言成功！」+ 留言渲染 + 共 1 条留言（dtime 过滤器显示时间）

========================================================
[5. 自动转义：`<script>` 出门就变 `&lt;script&gt;`（验收点）]
========================================================
  提交内容: '<script>alert(1)</script>你好' → 落库成功（存储层不过滤）
  渲染结果: &lt;script&gt;alert(1)&lt;/script&gt;你好（Jinja2 自动转义）
  防线分层：入库不拦、出口转义；想原样输出必须显式 |safe——一线之隔就是 XSS

========================================================
全部断言通过 ✓ 无 token 400 / 缺字段超长 200 回显 / 合法 302 落库 + flash / XSS 转义
```

诚实预期：

- **csrf_token 长度 91 字符**：每次签发值都不同（含随机数与时间戳），长度与格式随 flask-wtf 版本浮动
- **转义断言依赖默认配置**：`app.jinja_env.autoescape` 默认按文件后缀开启（.html 开）；显式关掉 autoescape 本实验立刻红——这本身就是个好实验
- **存储层不过滤**：`MESSAGES` 里存的是原始 `<script>` 文本。这不是漏洞，是分层——过滤错位置（入库）会让你失去原始数据，出口转义才是安全边界

本实验用到的组件速览：

| 组件 | 作用 |
|---|---|
| Jinja2 | Flask 内置模板引擎：继承、宏、过滤器、自动转义都在这里 |
| WTForms | 表单字段与 validators（校验规则）的声明库 |
| Flask-WTF / CSRFProtect | 表单集成与 CSRF 全局拦截 |
| `app.test_client()` | 模拟 POST：无 token / 伪造 token / 合法提交的实测工具 |

## How It Works

这节按一次提交的旅程拆机制：token 怎么埋与验、两道闸怎么分工、flash 怎么只闪一次、转义发生在哪一步。

### 模板继承与宏：一处定义，处处生效

`base.html` 定骨架（header/flash 区/content 块），`messages.html` 用 `{% extends %}` 只填内容块——改导航只动一处。

字段渲染抽成 `_macros.html` 的 `render_field(field)` 宏（macro——模板里可复用的"函数"）：label、控件、错误文案位三件套统一产出，新增表单复用成本极低。

过滤器是模板里的"管道"：内置 `|length` 数条数，自定义 `@app.template_filter("dtime")`（filter——模板里用 `|` 管道调用的格式化函数）把 datetime 格式化成 `HH:MM:SS`。输出 §4 里留言行首的时间，就是这个自定义过滤器的产物。

### flash 消息：一次性便签

`flash("留言成功！")` 把消息塞进 session，**只在下一次响应渲染时出现、渲染完即焚**。模板里 `get_flashed_messages(with_categories=true)` 取出，可按 `ok/error` 分类染色。

它天然配 PRG（Post-Redirect-Get，POST 成功后 302 重定向到 GET 的模式）：POST 成功 302 回列表页，刷新不会重复提交，flash 也只闪这一次——输出 §4 的「留言成功！」正是重定向后那次 GET 渲染出来的。

### CSRF：token 为什么有效

攻击场景：你登录着 bank.com，又逛了 evil.com，后者藏一个 `<form action="bank.com/transfer" method="post">` 自动提交——浏览器带着你的 Cookie 发请求。

防线：**POST 必须携带服务器签发在表单页里的随机 token**，evil.com 跨站拿不到这个值——同源策略（浏览器限制不同源站点互相读取数据的规则）挡着，服务器直接 400。

`hidden_tag()` 在表单里埋 `csrf_token` 隐藏域，`CSRFProtect` 则把校验提到视图之前——输出 §2 实测"无 token 的 POST 连视图一行代码都没执行"，伪造 token 同样 400。

### 校验的两道闸，两种状态码

| 闸 | 位置 | 失败表现 | 实测 |
|:---|:---|:---|:---|
| CSRFProtect | 视图之前 | 400，错误页 | 无/伪造 token 均 400 |
| WTForms validators | 视图内 `validate_on_submit()` | 200，重新渲染表单 + 错误文案 | 「昵称必填」「昵称最长 10 字」 |

记住这个区别：**400 = 请求本身不可信；200 = 请求可信但数据不合格**。前者是安全边界，后者是用户体验。

### 转义断言为什么查两样

```python
assert "&lt;script&gt;alert(1)&lt;/script&gt;" in html, "script 应被转义后渲染"
assert "<script>alert(1)" not in html, "绝不能出现可执行的原样 script"
```

只查第一个，恶意内容若被 `|safe` 原样输出、转义串恰好又出现在别处（比如错误提示里），断言会假绿；第二条"负面断言"确保可执行形态真的不存在。输出 §5 的渲染结果同时满足这两条——安全测试永远要正反两把尺。

## Pitfalls & Q&A

这节收录四个真实踩过的坑（现象 + 原因 + 解法）与两个深入问题。

- **忘设 `SECRET_KEY`**：现象是启动即 RuntimeError。原因是 CSRF token 与 flash（走 session 签名）都依赖它。解法是设置 `SECRET_KEY`，生产从环境变量注入，别硬编码进仓库
- **在宏里漏了错误文案位**：现象是校验失败时用户只看到"提交没反应"。原因是 `field.errors` 没有被渲染。解法是把错误回显当表单的一部分，在宏里补上
- **图省事 `|safe`**：现象是本实验的 XSS 输入若套上 `|safe` 渲染就是真漏洞。原因是 `|safe` 关掉自动转义。解法是想加粗/换行就用受控的 Markdown 渲染器，不要裸 safe
- **POST 成功后直接 `render_template`**：现象是用户刷新就重复提交。原因是响应没有 302。解法是按 PRG 三步收尾（Redirect → Get）

**Q1：Jinja2 的自动转义防什么？什么时候会失效？**

防 XSS：变量输出前把 `< > & " '` 转成 HTML 实体，注入的脚本变纯文本。

失效途径：显式 `|safe`、`Markup()` 包装、对非 HTML 模板（如 JS 模板）默认不开启——每条都是主动豁免，用前想清楚。

**Q2：为什么校验失败返回 200 而不是 400？**

业界两种都有：服务端渲染传统派用 200 + 表单回显（用户停在表单页看错误）；前后端分离 API 派用 400 + JSON errors。

关键是语义一致：本实验的 400 专留给 CSRF（请求不可信），数据不合格用 200 回显——状态码分工明确。
