# 14 · Django 视图与表单：FBV vs CBV、泛型视图与 auth 组件

> Django 的视图层有两种写法：FBV（函数视图——一个函数处理一种请求）与
> CBV（类视图——用类封装请求处理，其中预置好的模式化基类叫泛型视图）。
> 本实验搭出 ListView/DetailView/CreateView 三条泛型链路 + 一个 FBV 对照组，
> 外加 auth 组件自带的 LoginView；分页零重叠、未登录 302 带 next、非法表单回显
> 不落库——三条链路全部 test client 实测。

## Background

这节讲视图层的样板代码问题：在泛型视图出现之前，一个"列表页"要手写哪些步骤，烦在哪里。

没有它之前：Django 早期只有函数视图，每个列表页都要手写"查全表 → 切页 → 组装分页对象 → 渲染"四步，每个创建页都要手写"GET 显示表单、POST 校验保存"的分支，登录页也得从会话校验开始自己搭。

样板代码的代价不止是长：分页越界要不要 404、校验失败要不要回显错误、登录后跳回原地址——这些细节每个项目都可能漏掉一处，而且同样的四步在项目之间复制来复制去。

Django 的应对是把高频模式沉淀成框架件：泛型视图包掉列表/详情/创建的标准动作，auth 组件（内置的认证功能包）包掉登录与访问控制。于是视图层的第一道选择题变成：手写（FBV）还是用泛型（CBV）——按模式化程度分流。

## What

这节定义 FBV、CBV 与泛型视图的分工，并给出贯穿全文的心智模型。

Django 视图是"接收 HTTP 请求、返回响应"的可调用对象——MTV 结构里的 V。两种写法：

| 写法 | 形态 | 适合 |
|---|---|---|
| FBV | 一个普通函数，逻辑全裸写 | 非模式化逻辑（聚合统计、特殊流程） |
| CBV 泛型视图 | 类属性声明，样板全包办 | 列表/详情/创建等模式化页面 |
| auth 组件视图 | 框架自带的 LoginView 等 | 登录、访问控制 |

可以把泛型视图想象成餐厅的"套餐"：列表、详情、创建这类高频组合，点套餐（声明 `model`、`paginate_by`）比单点每道工序快；但和套餐不同的是，你可以进后厨重做任何一步——重写 `form_valid` 等钩子（hook——框架在固定时机留给你覆写的方法），不合适还能退回单点（FBV）。

一句话心智模型：**读链路交给泛型视图，写链路交给"Mixin 守卫 + CreateView + ModelForm 双闸"**。Mixin（混入类）是被多继承复用的小功能类，这里的 `LoginRequiredMixin` 负责拦未登录请求。

## When to Use

这节讲两种写法各自值得用的时机，以及判断标准。

典型场景：

- 在做标准的"列表-详情-创建"页面时——取数、分页、渲染、表单校验都是模式化动作——用泛型视图。
- 在做聚合统计、自定义 JSON 输出这类没有固定形状的接口时——FBV 直写更省绕弯。判断标准：需求与某个泛型视图"形状"的匹配度超过七成用 CBV，否则 FBV。
- 在做"页面要登录才能看/写"的访问控制时——auth 组件的 `LoginView` + `LoginRequiredMixin` 现成可用。

何时不用：

- 页面流程特殊、与任何泛型形状都对不上：用 FBV，不为"显得高级"硬套泛型。
- 已经要覆写多个泛型钩子才能满足需求：退回 FBV（阈值讨论见踩坑清单）。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CBV 泛型视图 | 声明式，模式化动作全包 | 标准 CRUD 页面 |
| FBV | 一个函数一个请求，直白 | 聚合统计、特殊流程 |
| auth 组件视图 | 框架自带登录/守卫 | 站点访问控制 |
| DRF 泛型视图 | 同一思想的 API 版 | 前后端分离接口（lab 15） |

## Quick Start

这节跑通演示脚本，看三条链路的实测结果。

前置条件：仓库自带 venv，依赖 Django 6.1.1。

```bash
cd web/14_django_views_forms
source ../.venv/bin/activate
python3 views_forms_demo.py    # migrate + 灌 6 篇文章 + 三节断言（收尾清理）
```

脚本用 Django 自带的 test client（进程内模拟请求的测试客户端）逐节断言：分页零重叠、未登录重定向带 next、非法表单回显不落库。

真实输出节选：

```
========================================================
[1. ListView 分页：每页 4 条，第二页拿走剩下的（验收点）]
========================================================
  第 1 页 → 200 · 「1 / 2」· 含 06/05/04/03（ordering=-created 生效）
  第 2 页 → 200 · 「2 / 2」· 恰好是剩下的 02/01，与第一页零重叠

========================================================
[3. CreateView：未登录 302 带 next、非法表单回显、合法发布（验收点）]
========================================================
  未登录 GET /blog/new/ → 302 → /accounts/login/?next=/blog/new/（next 指回原页）
  提交 1 字标题 → 200 · 页面含「标题至少 4 个字符」且不落库
  合法提交 → 302 · 落库 7 篇（ModelForm 字段校验 + clean_title 双闸全过）
```

诚实预期：

- **种子时间戳是固定值**（2026-01-01 至 06）：分页断言要求顺序确定，`auto_now_add` 会用"运行时刻"破坏确定性——改用 `default=timezone.now` 配合显式传值
- **`client.login()` 与 POST LoginView 都测了**：前者建立会话用于后续断言，后者验证 auth 组件视图本身可达
- **Django 5+ 的 LogoutView 只接受 POST**：本实验聚焦登录与创建，登出未纳入断言（lab 07 书签应用有完整登出流程）

本实验用到的泛型视图与组件：

| 组件 | 用途 | 关键声明 |
|---|---|---|
| `ListView` | 列表 + 分页 | `model` / `paginate_by = 4` / `ordering` |
| `CreateView` | 创建表单 | `form_class` / `success_url` |
| ModelForm | 从模型长出的表单 | `clean_title()` 业务规则 |
| `LoginView` / `LoginRequiredMixin` | 登录与守卫 | settings 的 `LOGIN_URL` |

## How It Works

这节拆开四条链路的机制，并与输出里的三个验收现象互相印证。

### CBV 泛型视图：模式化的代价被框架付掉

`ListView` 用 `model + paginate_by` 两个声明换走"查全表、切页、组装 page_obj、渲染"全套；
`DetailView` 按 pk（主键）取单对象；
`CreateView` 把"GET 显示表单、POST 校验保存"的分支也包了。

你在输出里看到的「1 / 2」与第一页含 06/05/04/03，
就来自 `paginate_by = 4` 与 `ordering = ["-created"]` 两个声明。

可定制点按层级渐进：改模板名、改 queryset、重写 `form_valid`——
从声明到覆写，不必一步到位。

### FBV 的正当性：非模式化需求更直白

`article_stats` 一个函数 + `JsonResponse` 完成聚合统计——没有要套的泛型模式时，FBV 少一层抽象。两者可以在同一个 urls.py 里混用（本项目就是这么写的）：泛型管标准页面，FBV 管特殊接口，互不冲突。

### ModelForm 与 clean_<field>：双层校验

ModelForm（从模型长出字段与校验的表单类）第一层从模型继承 `max_length`、外键有效性；
第二层 `clean_title()` 补业务规则（标题至少 4 字符）。

失败的表单重新渲染并携带错误文案（200 + errors）、不落库；
成功的走 `form_valid` 保存后 302（重定向——告诉浏览器改去另一个 URL）。

输出里「标题至少 4 个字符」且不落库、合法提交落库 7 篇，
就是双闸各司其职的证据。

### auth 组件：登录也是泛型视图

`LoginView` 处理 GET 渲染、POST 验证、写 session（服务端会话）、按 `next` 跳转全套；
`LoginRequiredMixin` 拦下未登录请求，302 到 `settings.LOGIN_URL` 并拼上 `?next=` 原地址——
登录成功自动跳回。

你在输出里看到的 `302 → /accounts/login/?next=/blog/new/`，就是这条守卫链路。

两条 settings 约定（LOGIN_URL/LOGIN_REDIRECT_URL）+ 一行 Mixin = 完整的访问控制。

### 确定性测试：为什么种子时间戳要显式固定

```python
Article.objects.create(title=f"文章 {k:02d}", created=datetime(2026, 1, k, tzinfo=timezone.utc))
```

这段在做什么：给每篇种子文章显式指定递增的 `created` 时间戳。
模型的 `ordering = ["-created"]` 决定列表顺序——
`auto_now_add` 会让 6 篇文章挤在同一秒内，分页断言（第一页含 06 不含 02）变成抛硬币。

确定性测试的前提是确定性输入：与排序相关的断言必须先固定排序键。
第一版用 `auto_now_add` 时分页内容断言随机红，就是这一课。

## Pitfalls & Q&A

这节收四个实测与工程中的坑，再答两个机制问题；每条坑按现象、原因、解法展开。

踩坑清单：

- **CBV 属性名写错静默失效**。现象：`paginate_by` 拼错只是"没有分页"，不报错。原因：泛型视图的行为靠约定属性名驱动，写错等于没写。解法：改完类属性要跑断言验证行为。
- **`success_url` 用了普通 `reverse`**。现象：启动时抛导入/路由错误。原因：CreateView 的 `success_url` 在类定义时求值，此时 urls.py 还没加载完。解法：必须用 `reverse_lazy`（延迟到真正需要时再求值）。
- **clean 方法里忘记 return**。现象：校验通过但字段值丢了。原因：`clean_title` 校验后不 `return title`，字段值被清空。解法：校验逻辑末尾必须返回（可能是修正过的）字段值。
- **把业务逻辑塞进泛型视图的钩子迷宫**。现象：一个 CBV 里覆写了四五个钩子，读不回去。原因：超出了泛型视图的模式边界。解法：覆写超过三个钩子就退回 FBV——CBV 的可读性红利有阈值。

深入问答：

**Q1: ListView 的分页是怎么工作的？**
`paginate_by` 声明每页条数后，ListView 自动切 QuerySet 并向模板注入 `page_obj/paginator`；
URL 参数 `?page=N` 驱动切页，越界抛 404。

切页发生在 SQL 层（LIMIT/OFFSET），不是取全量再切片。

**Q2: ModelForm 的校验顺序？**
字段级：`Field.clean()`（内置校验器）→ `clean_<field>()`（自定义单字段）；然后 `form.clean()`（跨字段）。错误收集在 `form.errors` 按字段归位——模板里逐字段回显就是读它。
