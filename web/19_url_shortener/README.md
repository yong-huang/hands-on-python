## Background

这节从分享长链接的麻烦说起。没有短链服务时，人们直接把原始 URL 复制给对方——邮件、文档、幻灯片里又长又易断，聊天窗口一换行就点不开。

再往前一步就撞墙：部分发布渠道对 URL 长度有硬性限制；发出去的链接无法统计有多少人点过；发现内容不合适时，也无法让已经散出去的链接失效。链接一旦出手，就完全脱离控制。

短链接服务因此而生：用自己的短域名加一个短码代替长 URL，用户访问短码时服务端跳转（302）到真实地址，顺便完成计数、过期与吊销。

本实验把这个服务当作综合组装题：FastAPI、SQLAlchemy（Python 生态常用的 ORM——把数据库表映射成 Python 对象的库）、JWT、pytest、Docker 各自都会造，交付物考验的是组装。

## What

这节定义短链接服务是什么，以及本实现钉住的四个设计要点。

短链接服务是一种"长 URL 到短码"的映射服务：缩短接口把长地址记进库并领一个唯一码，跳转接口凭码查库、验期、计数，再返回 302 重定向。一句话心智模型：**缩短是把"长 URL + 过期时间"记进账本并领一个唯一码；跳转是凭码查账、验期、计数、302**。

可以把短码想成衣帽间的寄存牌——凭牌取物、牌号全局唯一。但和寄存牌不同的是：短码还要统计被取用了多少次、能到点自动作废，作废与不存在还要向客户端报不同的错。

本实现钉住的四个设计要点：

- **唯一性约束放哪一层**：数据库层 `unique=True` + 应用层冲突重试——"理论上不会撞"的随机码必须由约束兜底
- **点击计数的事务性**：302 返回前 `clicks += 1` 并 commit，连点 3 次计数=3 有断言盯着
- **过期语义**：410 Gone 区别于 404 Not Found——"曾经存在"与"从未存在"是两种错误
- **管理端隔离**：删除走 JWT（JSON Web Token——自带签名的认证令牌）保护的管理端点，与公开端点权限分离

| 能力 | 行为 | 关键语义 |
|---|---|---|
| 缩短 | 长 URL → 唯一短码，可带过期时间 | 随机码撞了换码，自定义码被占报 409 |
| 跳转 | 短码 → 302 到目标地址 | 先验过期，再计数，再跳转 |
| 统计 | 查询某短码的点击数 | 计数在响应前已 commit |
| 管理 | `DELETE /admin/links/{code}` | JWT 保护，与公开端点隔离 |

## When to Use

这节补判断力：什么场景值得自建短链服务，什么场景不必。

- **在做对外投放的营销与传播物料**的时候——二维码、印刷品、短信里放不下原始 URL，短链让物料干净可读
- **在需要知道"谁点了多少"并保留吊销能力**的时候——运营活动、公告纠错，短链把点击数据与控制权留在自己手里
- **在做需要综合验收的 Web 服务练手题**的时候——它小到一天能写完，又覆盖并发、事务、权限、容器全链路

何时不用：纯内部交流、不需要统计与吊销的链接，直接发原地址更简单——少一跳依赖，也少一个需要维护的服务。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 直接发长链接 | 零成本，但难统计、难吊销 | 内部交流、无统计诉求 |
| 第三方短链平台 | 开箱即用，数据存在对方手里 | 快速起量的短期活动 |
| 自建短链服务（本实验） | 域名可信、数据与逻辑完全可控 | 长期产品能力、数据自持 |

## How It Works

这节按"缩短→跳转→过期→管理"的顺序拆机制，并解释并发断言为什么那样写。

### 唯一性：约束在数据库层，重试在应用层

随机码 8 位、每位取自 0-9a-zA-Z 共 62 个字符（空间 62⁸），让碰撞"理论上不会发生"——但并发写入的正确性不能建立在概率上：`unique=True` 建数据库层唯一约束，应用层捕获 `IntegrityError`（数据库约束冲突异常）换码重试（最多 5 次）。

自定义码被占用则明确 409——**用户语义与系统语义分开处理**（随机码撞了换一个用户无感，自定义码被占必须告知）。输出里"库中行数 = 201"那行的"唯一约束 + 重试兜底"说的就是这对组合。

### 点击计数与 302 的事务顺序

重定向端点内：查短码 → 验过期 → `clicks += 1` → commit → 返回 302。计数在响应之前 commit，保证"302 到达客户端时点击已记账"；连点 3 次断言计数=3 是并发安全的最低标准（SQLite 单写者天然串行，换 PostgreSQL 后该语义依然成立）。

### 过期语义：410 vs 404

`expires_at` 过期的短码返回 **410 Gone**（曾经存在、现已失效），不存在的返回 **404**（从未存在）。客户端（及爬虫）能据 410 做缓存/下架决策——状态码是 API 契约的一部分，"状态码即协议"在资源生命周期维度的应用。

### 管理端与公开端的权限分离

删除走 `DELETE /admin/links/{code}` + JWT 依赖（lab 12 的 get_admin 方案）；公开端点（缩短/跳转/统计）零认证。权限分离的粒度是"端点"而非"参数"——同一个资源，不同端点不同权限，避免公开接口里塞"管理员模式"参数。

### 并发断言为什么是"全部唯一"而不是"恰好 200 行"

```python
codes = set(pool.map(create_one, range(200)))
assert len(codes) == 200                       # 集合去重后仍 200 → 无碰撞
with SessionLocal() as db:
    assert db.query(Link).count() >= 200       # 库里至少 200 行（§1 还建过 1 条）
```

`codes` 用 set 收集：若发生碰撞且重试失败，元素数会少于 200——一行断言同时验证"生成成功"与"生成唯一"。库行数断言用 ≥ 而非 ==，因为 §1 的数据也在同一个库里——**断言要精确到它验证的性质，而不是顺带验证别的**。

## Pitfalls & Q&A

这节先列四个踩坑点，再答四个深入问题。

**SHORTENER_DB 在导入 app 之后才注入**：现象是测试全连到默认库；原因是 engine（SQLAlchemy 的数据库连接管理对象）在 import 时创建，环境变量晚一步就绑错库；解法是让 12-factor 的"注入时机"先于"读取时机"（demo 里调顺序后全绿）。

**TestClient（FastAPI 的进程内测试客户端）默认跟随重定向**：现象是断言 302 的用例随机失败；

原因是 httpx（TestClient 底层基于的 HTTP 客户端库）真的去请求了目标外网 URL，测试环境里这是随机失败源；解法是断言 302 时传 `follow_redirects=False`。

**SQLite 的 DateTime 不带时区**：现象是时间比较直接 TypeError；原因是 aware（带时区）与 naive（不带时区）两种 datetime 不可比；解法是全库统一 naive UTC 写读。

**容器内 sqlite 父目录不存在**：现象是容器启动即崩；原因是 `ENV SHORTENER_DB=/srv/data/...` 但镜像里没有这个目录；解法是挂载卷或 `RUN mkdir -p` 建目录二选一（本实验真实踩中）。

**Q1: 短码生成有哪些策略？各自的取舍？**
随机码（本方案，碰撞靠约束+重试）、自增 ID 转 base62（0-9a-zA-Z 共 62 字符的进制表示；有序可预测、需防遍历）、哈希截断（需处理碰撞）。核心权衡：不可猜测性 vs 短 vs 无碰撞成本。

**Q2: 重定向接口为什么要 302 而不是 301？**
301 永久重定向会被浏览器/爬虫缓存，之后即使删除/改期短码，客户端也不再回源——点击统计失效、吊销失效。短链服务必须 302（临时），把控制权留在服务端。

**Q3: 并发计数的安全做法？**
`UPDATE links SET clicks = clicks + 1`（数据库原子自增）或如本实现的单事务读改写（SQLite 串行写天然安全）。高并发下读-改-写要靠 DB 原子操作或乐观锁，不能在应用层长事务持有。

**Q4: 如果 QPS 涨到 1 万，这个服务先在哪里倒下？**
SQLite 单写者 → 换 PostgreSQL/MySQL；单进程 uvicorn → 多 worker + 容器副本；重定向查库 → 加缓存（短码→URL 是天然的缓存键值对）。每一步都能平滑演进是分层架构的回报。
