# 🏁 19 · 综合项目：短链接服务 —— 整条链路拧成一个交付物

> 终极串联：**FastAPI（队列/信号量/背压之外的能力）+ SQLAlchemy + JWT + 12-factor
> + pytest 套件**拧成一个完整可部署的服务。四个验收维度一次跑完：功能链路（缩短→302
> →点击计数）、并发健壮性（并发生成 200 个随机码无碰撞）、测试（19 条 pytest 全绿）、
> 容器化（Docker 构建 + /healthz 200）。

## What

零件都会造，交付物考验的是组装：**唯一性约束放哪一层**（数据库层的 `unique=True` + 应用层冲突重试——应用层"理论上不会撞"的随机码必须由约束兜底）、**点击计数的事务性**（302 返回前 `clicks += 1` 并 commit，连点 3 次计数=3 的断言）、**过期语义**（410 Gone 区别于 404 Not Found——"曾经存在"与"从未存在"是两种错误）、**管理端隔离**（删除走 JWT 保护的管理端点，与公开端点权限分离）。一句话心智模型：**缩短是把"长 URL + 过期时间"记进账本并领一个唯一码；跳转是凭码查账、验期、计数、302**。

## Why

每一条都有对应断言，共 19 条 pytest + 4 节集成验收。

诚实预期：

- **"库中行数 = 201"**：§1 核心链路先创建了 1 条 + 并发 200 条——断言用 ≥200 而非 ==200
- **过期时间存 naive UTC**：SQLite 的 DateTime 不带时区，全库统一 naive UTC 写读；切 PostgreSQL 时建议显式 timezone=True
- **随机码碰撞率 ~0**（62⁸ 空间）：重试逻辑是防御性设计而非必需——但"约束 + 重试"这对组合是健壮性的标准姿势
- **admin 账号硬编码在应用里**：演示用；生产从环境变量注入（lab 18 的 12-factor 原则）

### 唯一性：约束在数据库层，重试在应用层

随机码 62⁸ 的空间让碰撞"理论上不会发生"，但并发写入的正确性不能建立在概率上：`unique=True` 建数据库层唯一约束，应用层捕获 `IntegrityError` 换码重试（最多 5 次）。自定义码被占用则明确 409——**用户语义与系统语义分开处理**（随机码撞了换一个用户无感，自定义码被占必须告知）。

### 点击计数与 302 的事务顺序

重定向端点内：查短码 → 验过期 → `clicks += 1` → commit → 返回 302。计数在响应之前 commit，保证"302 到达客户端时点击已记账"；连点 3 次断言计数=3 是并发安全的最低标准（SQLite 单写者天然串行，换 PostgreSQL 后该语义依然成立）。

### 过期语义：410 vs 404

`expires_at` 过期的短码返回 **410 Gone**（曾经存在、现已失效），不存在的返回 **404**（从未存在）。客户端（及爬虫）能据 410 做缓存/下架决策——状态码是 API 契约的一部分，"状态码即协议"在资源生命周期维度的应用。

### 管理端与公开端的权限分离

删除走 `DELETE /admin/links/{code}` + JWT 依赖（lab 12 的 get_admin 方案）；公开端点（缩短/跳转/统计）零认证。权限分离的粒度是"端点"而非"参数"——同一个资源，不同端点不同权限，避免公开接口里塞"管理员模式"参数。

## Deep Dive

**为什么并发生成 200 个码的断言是"全部唯一"而不是"恰好 200 行"？**

```python
codes = set(pool.map(create_one, range(200)))
assert len(codes) == 200                       # 集合去重后仍 200 → 无碰撞
with SessionLocal() as db:
    assert db.query(Link).count() >= 200       # 库里至少 200 行（§1 还建过 1 条）
```

`codes` 用 set 收集：若发生碰撞且重试失败，元素数会少于 200——一行断言同时验证"生成成功"与"生成唯一"。库行数断言用 ≥ 而非 ==，因为 §1 的数据也在同一个库里——**断言要精确到它验证的性质，而不是顺带验证别的**。

踩坑清单：

- **SHORTENER_DB 在导入 app 之后才注入**：engine 在 import 时创建，环境变量晚一步就绑到默认库——12-factor 的"注入时机"必须先于"读取时机"（demo 里调顺序后全绿）
- **TestClient 默认跟随重定向**：断言 302 时要 `follow_redirects=False`，否则 httpx 真的去请求目标外网 URL——测试环境里这是随机失败源
- **SQLite 的 DateTime 不带时区**：aware 与 naive 比较直接 TypeError；全库统一 naive UTC
- **容器内 sqlite 父目录不存在**：`ENV SHORTENER_DB=/srv/data/...` 但没 `RUN mkdir -p`，容器启动即崩（本实验真实踩中）；挂载卷或建目录二选一

## Q&A

**Q1: 短码生成有哪些策略？各自的取舍？**
随机码（本方案，碰撞靠约束+重试）、自增 ID 转 base62（有序可预测、需防遍历）、哈希截断（需处理碰撞）。核心权衡：不可猜测性 vs 短 vs 无碰撞成本。

**Q2: 重定向接口为什么要 302 而不是 301？**
301 永久重定向会被浏览器/爬虫缓存，之后即使删除/改期短码，客户端也不再回源——点击统计失效、吊销失效。短链服务必须 302（临时），把控制权留在服务端。

**Q3: 并发计数的安全做法？**
`UPDATE links SET clicks = clicks + 1`（数据库原子自增）或如本实现的单事务读改写（SQLite 串行写天然安全）。高并发下读-改-写要靠 DB 原子操作或乐观锁，不能在应用层长事务持有。

**Q4: 如果 QPS 涨到 1 万，这个服务先在哪里倒下？**
SQLite 单写者 → 换 PostgreSQL/MySQL；单进程 uvicorn → 多 worker + 容器副本；重定向查库 → 加缓存（短码→URL 是完美的缓存键值对）。每一步都能平滑演进是分层架构的回报。
