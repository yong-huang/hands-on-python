# 22 · 缓存与限流：备忘录、击穿现场与门口取号机

> 高峰把慢后端打垮之前，你有两道防线：缓存挡住重复计算，限流挡住过量请求。
> 本实验手写 TTL 缓存与令牌桶，并用并发 20 的实测把"缓存击穿"从名词变成
> 现场数据——无锁版后端被真实计算 20 次，带锁版 1 次。

## Background

没有这两道防线时，每个请求都老老实实打后端：汇率源响应 0.3s，高峰期一秒
几百个请求就是几百次真实计算，后端先变慢、再超时、最后拒绝服务。

重复请求打垮下游是第一堵墙；个别用户疯狂刷接口挤占所有人配额是第二堵。
缓存与限流因此成对出现：缓存把"相同的计算"收敛成一次，限流把"过量的
请求"挡在门外。

## What

**TTL 缓存**给每个结果记一个过期时刻，命中直接返回，过了时刻重新计算。
**令牌桶**以固定速率往桶里放令牌，请求取到令牌才放行，桶容量就是突发上限。

可以把缓存想象成**备忘录**：问过一次的答案抄在本子上，本子上的条目过了
保质期才重问。可以把限流想象成**门口取号机**：号发完就得等下一批。但和
取号机不同的是，令牌按时间匀速补充——它限制的是长期速率，不是一刀切。

| 手段 | 语义 | 边界 |
|:--|:--|:--|
| TTL 缓存（无锁） | 未命中就算，不管并发 | 并发未命中会击穿 |
| TTL 缓存（带锁） | 同 key 并发收敛为一次 | 全局锁牺牲部分并发 |
| 令牌桶 | 突发=容量，匀速=rate | 多进程各一本账 |
| 固定窗口计数 | 每窗口重置 | 窗口边界两倍突发 |

上半是击穿对比（无锁 20 次对带锁 1 次），下半是令牌桶的放行与 429 出口——两道防线各管一件事。

## When to Use

- 数据计算贵、重复率高（汇率、配置、榜单头几页）：TTL 缓存直接把后端
  压力除以命中率。
- 对外接口、或调用有限额的第三方：限流保护自己与对方。
- 何时不用：数据强实时（下单扣库存）不能缓存；内部低频工具不必限流。

| 方案 | 复杂度 | 适用 |
|:--|:--|:--|
| 进程内 TTL 缓存 | 低 | 单实例、容忍短暂不一致 |
| 进程内令牌桶 | 低 | 单实例自我保护 |
| Redis + 分布式锁 | 高 | 多实例共享缓存 |
| 网关层限流 | 高 | 按租户/全局精确配额 |

应显著快于未命中（本机约 20ms 对 320ms）。限流段 [200×3, 429×2] 恒定。

## How It Works

**TTL 是惰性判断**：缓存不主动删过期条目，只在被读到时比对过期时刻——
过期与未命中同一条路。代价是过期条目占着内存直到下次被问。

**asyncio.Lock 为什么能收敛**：无锁版"查缓存→await 后端→写缓存"之间有
await 空档，20 个协程都在空档里查到未命中，于是各自计算（实测 20 次）。
带锁版把"查→算→写"整段锁住：第一个进来算，其余 19 个在锁上等，醒来时
缓存已就绪——后端只被真实调用 1 次。

**令牌桶的补充公式**：每次请求先按流逝时间补币
`tokens = min(capacity, tokens + elapsed × rate)`，够一枚就扣一枚放行，
不够则按缺额算出 `Retry-After`。容量给突发留余量，rate 定长期均值。

## Pitfalls & Q&A

- **锁粒度过大**：本实验的全局锁让不同 key 也互相排队。key 空间大时改
  分 key 锁（`dict[key, Lock]`），并发更好，实现更复杂。
- **击穿之外的雪崩与穿透**：缓存同一时刻集体过期是雪崩（给 TTL 加随机
  抖动）；查询根本不存在的 key 每次都穿透到后端（空值也缓存一段时间）。
- **多 worker 各一本账**：限流计数与缓存都在进程内存，`--workers 4` 就是
  四本账——生产要共享状态得上 Redis（见 lab 23 的进程模型）。
- **TTL 到期瞬间的击穿窗口**：带锁版只收敛"同时未命中"，过期瞬间的并发
  同样走锁收敛——这正是带锁版相对无锁版的价值。

**Q：为什么不直接用 fastapi-limiter / slowapi？** 它们是好选择；本实验
手写是为了把击穿与补充公式拆开看懂——库只是把这些部件装配好。

**Q：缓存该存对象还是序列化后的字节？** 本实验存 float。存复杂对象时注意
调用方拿到的是共享引用，改它等于改缓存——返回副本更安全。

**Q：Retry-After 给多少合适？** 按缺额算出的是理论值（本实验取整加 1）；
对外服务通常给固定档位（1s/60s），避免暴露内部速率细节。
