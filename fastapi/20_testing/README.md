# 20 · 测试体系：三层金字塔，红绿之间的契约

> 改一处崩三处的恐惧，靠"每次提交自动跑一遍测试"来消除。本实验用一个小购物车把
> 测试收拢成三层金字塔：纯函数直测、TestClient 行为测试、契约测试，并用一条
> xfail 演示"测试先行"的红绿节奏。读完你就能给任意 FastAPI 项目搭同款测试骨架。

## Background

没有自动化测试时，验证靠手动：改完代码打开浏览器点一遍下单、改价、删除。
三个页面点完算尽职责，第四个页面(购物车合计)全凭记性。

痛点在回归。修"合计四舍五入"的补丁把数量上限也改坏了——手动流程没覆盖它，
问题上了线才被发现；回归范围越大，点浏览器越点不动，最后干脆不点。

自动化测试因此成为工程底线：把"点浏览器"写成断言脚本，每次提交全量重放。
FastAPI 的 TestClient（把请求直接打进应用的进程内测试客户端）让这类脚本
不用起服务、不用清数据库，毫秒级跑完一整套。

## What

**测试金字塔**是把测试按"快慢与数量"分层的形状：底层单元测试最快最厚，
顶层端到端最慢最薄。本实验的三层：

| 层 | 文件 | 测什么 | 起不起 HTTP |
|:--|:--|:--|:--|
| 底层 · 单元 | test_unit.py | 纯函数 `cart_total` 的计算 | 否 |
| 中层 · 端点 | test_api.py | 校验 422、增删查、404 | TestClient 进程内 |
| 顶层 · 契约 | test_contract.py | 响应字段清单不被悄悄改 | TestClient 进程内 |

可以把金字塔想象成**体检套餐**：血常规（单元）便宜量大人人做，CT（契约）贵
但看得深。但和体检不同的是，测试每次提交都要全量重放——所以"便宜的那层"
必须占大头，否则整套拖慢提交节奏。

三层各司其职：底层最厚（纯函数直测），顶层最深（契约抓形状）；右侧夹具为中层供装配与隔离。

## When to Use

- 给已有项目补第一套测试时：先给纯函数与校验规则写单元层，收益立竿见影。
- 多人协作的接口项目：契约测试守住响应形状，重构内部不再心惊。
- 何时不用：一次性脚本、探索性原型只测核心路径即可；为每个 getter 写测试
  是把金字塔倒过来的浪费。

| 手段 | 测什么 | 代价 |
|:--|:--|:--|
| 单元测试 | 纯函数逻辑 | 最低，毫秒级 |
| 端点测试 | 请求→校验→响应的整链 | 中，需夹具隔离 |
| 契约测试 | 响应形状不被破坏 | 中，需维护契约清单 |
| 冒烟测试 | 真实服务起得来、通 | 最高，见 How It Works |

## How It Works

**夹具即依赖注入**：conftest.py 的 `client` fixture 与 FastAPI 的 `Depends`
是同一思想——用例只声明"要一个客户端"，装配交给夹具。`clean_state` 标了
autouse：每个用例开始前自动 `POST /reset`，隔离不靠用例自觉。

**TestClient 为什么快**：它把请求对象直接交给 ASGI 应用，不经过网络与端口。
代价是测不到真实服务器（uvicorn）的行为——所以工程里还有一层冒烟测试：
部署后对 `/healthz` 发一次真实请求，证明"测试全绿 ≠ 线上没事"的缺口被堵上。

**契约测试抓泄漏的机理**：契约是响应 keys 的精确集合断言（`set(item) ==
CART_ITEM_KEYS`）。实现里 `_as_out` 多给了一个 `internal_cost`，集合一比即红。

`xfail(strict=True)` 表示"现在必须失败"：若有人顺手修了泄漏却忘删 xfail，
XPASS 会被判失败，逼你正式把它转正为常规用例。

## Pitfalls & Q&A

- **模块级状态在用例间泄漏**：`_cart` 是进程内列表，上一个用例的商品会流进
  下一个用例。解法：autouse 夹具每例清场（本实验的做法）。
- **fixture 忘写 yield 后半段**：只建不拆，残留状态比没有测试更骗人。
- **契约过严卡迭代**：把每个字段都钉死会让正常演进次次红。契约只钉"对外
  承诺"的字段，内部形态用单元测试覆盖。
- **async 端点与同步 TestClient**：TestClient 能测 async 端点，但测不到
  事件循环的真实并发行为——并发正确性要靠真实服务压测（见 lab 25）。

**Q：单元测试不起 HTTP，怎么知道路由注册对了？** 不用知道——那是中层端点
测试的职责。分层就是让每层只回答一个问题，越界的问题交给上层。

**Q：xfail 的用例什么时候删？** 修掉泄漏的同一个提交里删掉 xfail。让"转正"
成为修复的收尾动作，而不是留一句注释。

**Q：契约清单维护在哪？** 就在测试文件顶部的常量里（本实验的
`CART_ITEM_KEYS`）。字段多到常量放不下时，说明响应该拆分了。
