# 25 · 压测基准：三种客户端对决，用 p99 读长尾

> 系列的收官实验：给 lab 24 的服务压上三种并发客户端，把"并发到底快多少"
> 从感觉变成读数。异步在 0.1s 等待端点上实测 60 倍加速——lab 11 的理论
> 在这里兑现成数字。

## Background

"我们的服务能扛多少并发"如果只靠猜，上线就是开盲盒。压测把这个问题变成
可重复的实验：固定请求数、记录延迟、对比分位数。

分位数是压测的语言：p50 是典型请求的延迟，p99 是"99% 的请求快于它"——
平均数会被长尾骗，p99 不会。

## What

**客户端压测**是用脚本模拟真实流量：本实验三种客户端（串行 / 线程池 /
异步）各打 100 个请求到同一服务，记录总耗时与每个请求的延迟。

可以把压测想象成**体检的跑步机**：固定配速逐级加码，看心电图的拐点在哪。
但和体检不同的是，单机回环没有真实网络抖动——数字用于对比方向，不是
生产吞吐承诺。

| 客户端 | 模型 | 呼应 |
|:--|:--|:--|
| 串行 httpx | 一发一等，基线 | —— |
| ThreadPoolExecutor(20) | 多线程并发 | lab 11 的 def 语义 |
| httpx.AsyncClient | 单线程事件循环 | lab 11 的 async 语义 |

三种客户端打两类端点：/slow 比等待重叠（差距 60 倍），/fast 比每请求开销（差距很小）——读数全部汇进右侧分位数。

## When to Use

- 上线前验证容量假设、改动后对比性能方向、给扩容决策找数据。
- 何时不用：无基线的裸压（不知道"快"是相对谁）；用生产流量直接压新版本
  （先在预发压，呼应 hands-on-python/web/18 的部署语境）。

| 指标 | 读什么 |
|:--|:--|
| 总耗时 | 吞吐方向 |
| p50 | 典型用户体验 |
| p99 | 长尾——慢的那 1% 是谁 |
| 错误率 | 压垮的前兆 |

## Quick Start

前置：fastapi 目录 `.venv` 已就绪，未创建则先在仓库根执行
`./scripts/load_resources.sh`。运行：

```bash
cd fastapi/25_benchmark && ./25_benchmark.sh all
```

真实输出（节选，`...` 处省略了中间输出；数值随机器浮动，方向恒定）：

```text
  ---- /fast ----
    串行   总耗时   0.06s | p50    0.5ms | p99    1.9ms
    线程池 总耗时   0.29s | p50   54.5ms | p99   88.0ms
    异步   总耗时   0.06s | p50   31.0ms | p99   43.2ms

```

诚实预期：/slow 上"异步与线程池都远快于串行"是断言锁定的方向（各快 2 倍
以上），具体倍数随机器浮动（本机异步 60 倍）；/fast 端点三种客户端都在
毫秒~亚秒级、无固定名次。客户端基准只看方向，不与生产吞吐对号。

## How It Works

**等待重叠是 60 倍的来源**：串行付 100 次 0.1s；异步把 100 个 0.1s 等待
叠在同一时间窗里，总耗时 ≈ 一轮等待 + 分发开销。线程池也重叠，但 20 条
线程的切换与管理开销让它在同规模下慢于事件循环（0.74s 对 0.17s）。

**p99 读长尾**：/slow 的线程池 p99（173.6ms）比 p50（142.4ms）高出三成
——线程调度抖动落在最慢的那几个请求上；异步的 p99（144.2ms）与 p50
（130.4ms）更贴近，事件循环的分发节奏更均匀。

**/fast 端点为什么无名次**：没有等待可重叠时，瓶颈是客户端自身构造请求
与解析响应的开销——这提醒我们压测结果永远取决于瓶颈在哪一侧。

## Pitfalls & Q&A

- **压测工具与被测同机**：CPU 互相抢，数字双向失真——结论只看方向，绝对
  值须隔离环境重测。
- **keep-alive 粘进程**：对多 worker 服务压测时（lab 23），单连接会粘住
  单个 worker，压的是一条进程不是整个服务——多连接或 Connection: close。
- **只看平均数**：p99 长尾才是用户投诉的来源；平均 50ms、p99 2s 的服务
  一样会被骂。
- **把回环数字当吞吐承诺**：回环无网络抖动；生产数字受带宽、LB、数据库
  多级影响，压测要按生产拓扑重做。

**Q：为什么不用 wrk/locust？** 它们是生产压测的正解（连接模型、分布式
施压都完善）；本实验用 httpx 手写是为了让"并发模型决定吞吐"的因果链
完全可见——写一遍压测再看 wrk 报表就都认识了。

**Q：p99 之后还有 p999 吗？** 有，且更刺眼。分位数取到多深取决于业务：
面向人的交互看 p99，服务间调用看 p999（重试风暴由它引爆）。

**Q：压出瓶颈后先改哪？** 先定位瓶颈在哪一侧（客户端 CPU、服务端、下游），
再对症——本实验 /fast 无名次正是"瓶颈不在并发模型"的现场例子。
